# 第 15 章：设计 Google Drive

## 简介
Google Drive 是一种基于云的文件存储与同步服务，允许用户在各种设备上存储、访问和共享文件。本章讨论如何设计一个包含以下功能的可扩展系统：
- **文件上传与下载**
- **跨设备文件同步**
- **文件共享**
- **文件修订历史**
- **编辑、删除和共享时的通知**

---

## 步骤 1：理解问题

### 关键需求
#### 功能需求：
- 上传和下载文件。
- 在多个设备之间同步文件。
- 维护文件修订版本。
- 支持带权限的文件共享。
- 在文件被编辑、删除和共享时发送通知。

#### 非功能需求：
- **可靠性：** 数据丢失不可接受。
- **同步速度快：** 避免因同步延迟而让用户失去耐心。
- **带宽效率：** 尽量减少不必要的数据使用。
- **可扩展性：** 支撑 1000 万日活跃用户（DAU）。
- **高可用性：** 在服务器故障或网络问题时依然无缝运行。

### 约束与假设
- 每个用户获得 **10 GB 免费空间**。
- 最大文件大小：**10 GB**。
- 平均文件上传大小：**500 KB**。
- 上传频率：**每个用户每天 2 个文件**。
- 总存储需求：**500 PB**。

## 步骤 2：高层设计
### 单服务器方案
一个基础设置包括：
1. **Web 服务器：** 处理上传和下载。
2. **元数据数据库：** 用来跟踪元数据，如用户数据、登录信息、文件信息等。
3. **存储目录：** 按命名空间（namespace）组织存放文件。


<div style="margin-left:3rem">
    <img src="./images/namespaces.png" alt="命名空间" width="400" />
</div>

- 设置一台 Web 服务器，并建立一个名为 drive/ 的目录作为根目录来存放上传的文件。
- 在 drive/ 目录下，有一系列被称为命名空间的目录。
- 每个命名空间包含该用户的所有已上传文件。
- 每个文件或文件夹可以通过将命名空间与相对路径连接起来进行唯一标识。


这种设计可以作为一个起点，但不足以支撑规模化扩展。

#### API
1. **向 Google Drive 上传文件：** 支持两种上传类型
    - 简单上传：适用于文件较小时。
    - 可断点续传上传（Resumable upload）：
        - 端点：https://api.example.com/files/upload?uploadType=resumable
        - 发送初始请求以获取可续传的 URL。
        - 上传数据并监控上传状态。
        - 如果上传被打断，则恢复上传。
2. **从 Google Drive 下载文件：** 要下载文件
    - 端点：https://api.example.com/files/download
3. **获取文件修订版本：**
    - 端点：https://api.example.com/files/list_revisions

### 转向分布式系统

#### 改进：
1. **分片（Sharding）：** 根据 `user_id` 将存储拆分到多台服务器上。
2. **Amazon S3：** 使用 S3 实现可扩展且冗余的文件存储，并支持跨区域复制。

    <img src="./images/replication.png" alt="复制" width="600" />
     
3. **负载均衡器：** 将流量分发到多台 Web 服务器。
4. **元数据数据库复制：** 通过数据库分片和复制来确保可用性。


#### 同步冲突：
对于像 Google Drive 这样的大型存储系统，同步冲突时有发生。
当两个用户同时修改同一个文件或文件夹时，就会产生冲突。

<div style="margin-left:5rem">
<img src="./images/sync-conflicts.png" alt="同步冲突" width="600" />
</div>

- 在该示例中，用户 1 和用户 2 尝试同时更新同一个文件，但用户 1 的文件先被我们的系统处理。
- 用户 1 的更新操作成功执行，但用户 2 遇到了同步冲突。
- 系统会呈现同一个文件的两个副本：用户 2 的本地副本和服务器上的最新版本。
- 用户 2 可以选择合并两个文件，或者用一个版本覆盖另一个版本。

### 改进后的设计
<div style="margin-left:5rem">
<img src="./images/high-level-design.png" alt="高层设计" width="500" />
</div>

1. **用户交互：** 用户通过浏览器或移动应用访问该应用。

2. **块服务器（Block Servers）：**
   - 文件被拆分为最大 **4 MB** 的块，并为每个块分配唯一的哈希值。
   - 块独立存储在云存储中（例如 Amazon S3）。
   - 文件重建涉及按特定顺序拼接这些块。

3. **云存储（Cloud Storage）：** 块存储在云存储中，以实现可扩展性和冗余。

4. **冷存储（Cold Storage）：** 不活跃的文件会被移到冷存储中以降低成本。

5. **负载均衡器：** 在各 API 服务器之间均匀分配请求，以确保高效运行。

6. **API 服务器：**
   - 处理用户认证、资料管理和文件元数据更新。
   - 管理所有与上传无关的工作流。

7. **元数据数据库与缓存：**
   - 存储用户、文件、块和版本元数据。
   - 频繁访问的元数据会被缓存，以便更快地检索。

8. **通知服务（Notification Service）：**
   - 一个**发布/订阅系统**，用于通知客户端文件的变化（新增、编辑、删除）。
   - 确保客户端能够拉取最新的更新。

9. **离线备份队列：** 临时存储文件变更信息，供离线客户端重新上线时进行同步。

### 文件上传流程

1. **文件上传：**
   - 文件由块服务器拆分为块、压缩并加密。
   - 块被上传到块服务器并存储在 S3 中。
2. **元数据上传：**
   - 客户端将元数据发送到 API 服务器。
   - 元数据以 `pending`（待处理）状态存入数据库。
3. **完成：**
   - S3 触发回调，将文件状态更新为 `uploaded`（已上传）。
   - 通知服务告知相关用户。

### 文件下载流程
当文件在其他地方被新增或编辑时，会触发下载流程。客户端有两种方式可以得知：
- 如果文件被另一个客户端修改时客户端 A 在线，通知服务会通知客户端 A。
- 如果文件被另一个客户端修改时客户端 A 离线，数据会被保存到缓存中。当离线客户端重新上线时，它会拉取最新的变更。

一旦客户端得知文件发生了更改，它首先通过 API 服务器请求元数据，然后下载块来构建文件。

1. **触发：** 通知服务告知客户端文件更新。
2. **获取元数据：** 客户端通过 API 检索更新后的元数据。
3. **下载块：** 客户端从块服务器下载更新后的块并重建文件。

### 通知服务
1. **目的：** 让客户端及时了解文件的变化。
2. **机制：** 实现**长轮询（long polling）**以进行异步通知。
3. **示例：** 当文件被新增、编辑或删除时，通知会被推送到所有相关客户端。


---

### 存储优化
1. **去重（De-duplication）：** 通过基于哈希的比较，在账号级别移除重复的块。
2. **版本控制策略：**
   - 限制保存的修订版本数量。
   - 对频繁编辑的文件，优先保留最近的版本。
3. **冷存储：** 将很少访问的文件移动到更便宜的存储方案中（例如 Amazon S3 Glacier）。

---

### 故障处理
1. **负载均衡器故障：** 备用负载均衡器接管。
2. **块服务器故障：** 待处理的任务会被重新分配给其他服务器。
3. **元数据数据库故障：**
   - 将某个从节点提升为主节点。
   - 将流量重定向到剩余的副本。
4. **云存储故障：** 使用跨区域复制来获取不可用的文件。
5. **通知服务故障：** 客户端重新连接到备用服务器。
