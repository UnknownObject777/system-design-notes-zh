广告点击计数：流水线点钞票

Ad Click Event Aggregation

一句话：每秒几万次点击，几分钟内算出每个广告被点了多少次——这是广告主付钱的依据，一张不能漏，一张不能多数。

点击：10 亿次/天 · QPS 1 万，峰值 5 万 广告规模：200 万个 新增存储：100 GB/天（3 TB/月） 端到端延迟：几分钟
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

点钞流水线银行金库每天要清点海量的钞票：传送带不停（点击事件流），点钞机逐张清点并按面值分把（聚合节点按广告计数），捆扎员把各台机器的数字汇总入账（归约节点），账房先生晚上拿总账对着原始录像逐笔核对（对账）。规矩有三：一张不能漏（漏了少收钱）、一张不能多数（重复了多收钱）、机器坏了换一台接着上次的数继续点（容错）。广告点击聚合，就是一条不许数错钱的流水线。

第一步 · 搞清问题

Facebook、YouTube、TikTok 背后是一个庞大的数字广告产业，其中有一环叫实时竞价（Real-Time Bidding，RTB）：广告位在一秒内被买卖。RTB 有两个硬要求：速度（通常一秒内完成）和准确——因为点击数直接决定广告主付多少钱。

所以这一讲的问题是：点击事件像洪水一样涌进来，怎样在几分钟内算出"每个广告被点了多少次"，而且算得准？

核心查询需求：

  1. 返回广告 X 在过去 Y 分钟内的点击次数；
  2. 返回过去 1 分钟内被点击最多的前 100 个广告，参数可配置，聚合每分钟执行一次；
  3. 支持按 ip、user_id、country 过滤。

边界情况也要提前摆上台面：事件可能迟到、可能重复、系统某部分可能故障——都要能恢复。延迟上，点击聚合端到端几分钟即可接受（数据用于计费和报告），但 RTB 本身要求小于一秒。

规模估算（Facebook / Google 级别）：

指标数值说明
DAU10 亿假设每个用户每天点 1 个广告
每日点击事件10 亿次事件总量，年同比增长 30%
广告总数200 万个需要被聚合的对象
点击 QPS / 峰值10,000 / 50,000峰值按平均值的 5 倍算
单次点击存储0.1 KBad_id、时间戳、user、ip、country
每日 / 每月新增存储100 GB / 3 TB只存原始事件就这么大

非功能需求由此定型：正确性第一（计费依据）、妥善处理迟到和重复事件、对部分故障有弹性、端到端延迟最多几分钟。

第二步 · 画出大框架

点击数据在输入和输出上都是无界数据流（unbounded stream）——它不会停。先给客户端（数据科学家、分析师、广告主）两个查询接口：

  • GET /v1/ads/{:ad_id}/aggregated_count：参数 from / to（起止分钟）/ filter（过滤策略标识，如 001 表示"非美国地区的点击"），返回这段时间的聚合计数。
  • GET /v1/ads/popular_ads：参数 count（前 N 个）/ window（窗口分钟数）/ filter，返回点击最多的广告 ID 列表。

数据模型分两层。原始数据是逐条事件（ad_id、时间戳、user、ip、country），好处是数据集完整、可过滤、可重算；坏处是太大、查询太慢。聚合数据是每分钟每桶一行（ad_id、click_minute、filter_id、count），小、快，但它是派生数据，有信息丢失。结论：两者都要——原始数据扔进冷存储（出 bug 时调试用、可回填），聚合数据存进数据库供查询。数据库选 Cassandra：原始数据侧平均 QPS 1 万、峰值 5 万，是写密集型工作负载，Cassandra 对高写入有原生支持。

高层架构，数据这样流动：

用户点击→ 广告服务→ Kafka 队列 1
原始点击事件→ Map 映射节点→ Aggregate 聚合节点→ Reduce 归约节点→ Kafka 队列 2
聚合结果→ Cassandra 聚合库→ 查询 API → 仪表盘

为什么中间要隔两个消息队列？如果用同步接收端，一个消费者崩溃就可能让整个系统停滞；换成 Kafka 异步处理，生产者和消费者彻底解耦。第二个队列的存在是为了端到端精确一次（exactly-once）的原子提交——聚合结果和"消费到哪了"一起落地，不丢不重。

中间的聚合服务用 MapReduce 框架，画成一张 DAG（有向无环图）：每个节点只做一件事，把结果发给下游。映射节点（map node）从数据源读数据、过滤、转换，按 ad_id 把事件分配到不同聚合节点；聚合节点（aggregate node）每分钟在内存里按广告计数；归约节点（reduce node）把各聚合节点的结果收拢成最终结果。它把大数据转成常规大小的数据——每秒几万条事件，压成每分钟每广告一个数字。

三个用例这样落地：用例一，广告按 ad_id % 3 分区，各聚合节点各数各的；用例二，每个节点维护一个堆（heap）数据结构，快速取出前 N 个；用例三，过滤用星型模式（star schema）——预定义过滤标准（维度 dimensions，如国家）提前预聚合好，查的时候直接读，不用临时扫原始数据。

第三步 · 深入零件（按原文步骤 3 各小节的顺序）

1流处理 vs. 批处理：选哪条数据处理路径

系统有三类：在线服务（响应客户端，指标是可用性和延迟）、批处理系统（离线，吃有界的大数据，指标是吞吐量，代表是 MapReduce）、流处理系统（近实时，吃无界流，吞吐和延迟都要，代表是 Flink）。

我们的设计是混合的：数据到达时用流处理近实时出聚合结果；历史数据备份用批处理。如果批、流两条路径都保留，叫 Lambda 架构——缺点是要维护两条路径、两套代码库。替代方案 Kappa 架构：只用单一的流处理引擎。本设计选 Kappa，因为重算也走同一条聚合服务。当聚合逻辑出了大 bug 需要重算：重新计算服务从原始存储捞数据（批处理作业）→ 发到一台专门的聚合服务，避免影响实时流量 → 结果写入第二个消息队列，再更新聚合数据库。

2时间：事件时间还是处理时间

聚合需要一个时间戳，它有两个产生点：事件时间（event time）是点击发生的时间，处理时间（processing time）是服务器处理时的时间。中间隔着消息队列和网络延迟，两者可能差很多。权衡很直白：

  • 事件时间：聚合更准确；但客户端的时钟可能不准，时间戳甚至可能是恶意伪造的。
  • 处理时间：服务器时间戳可靠；但事件迟到时，它就被归错了窗口。

计费场景准确性优先，选事件时间，然后解决迟到问题：给聚合窗口故意多留一段"水印"（watermark）——窗口多等一会儿再关闭。水印短，遗漏迟到事件的概率大但延迟低；水印长，遗漏少但延迟高。注意：无论水印多长，遗漏的可能性始终在。为这种低概率事件继续优化没有意义，正确的兜底是一天结束时做对账（reconciliation）。

3聚合窗口：四种切时间的方式

窗口函数有四种：翻转（固定）窗口（tumbling window）——每分钟一个格子，互不重叠；跳跃窗口（hopping window）——格子固定但会重叠跳；滑动窗口（sliding window）——随当前时间滑动；会话窗口（session window）——按用户行为间隙切段。本设计：广告点击计数用翻转窗口（"第 N 分钟的点击数"）；Top-N 查询用滑动窗口（"过去 M 分钟内点击最多的"）。

4投递保证：一张都不能丢、不能重

投递保证有三档：最多一次（at-most-once）可能丢；至少一次（at-least-once）可能重复；精确一次（exactly-once）不丢不重。大多数系统"至少一次"就够用——重复一点点没关系。但本系统不行：很小的百分比差异就是数百万美元的出入。所以必须用精确一次。

5数据去重：重复从哪来，怎么灭

最常见的数据质量问题是重复，来源有两个。客户端：可能重发同一个事件，恶意的重复交给风险引擎（risk engine）处理。服务器故障：聚合节点宕机，上游没收到确认，事件被重发——典型例子是偏移量 100 被处理并发送后确认丢失，于是 100 被再处理一次、再发一次。

解法的演进：把上次见到的偏移量存进 HDFS/S3？有隐患——如果存储偏移量之后结果还没发到下游，偏移量却已经记下，那批结果永远到不了下游。稳妥做法是存偏移量 + 与下游交互，做成原子的，这需要实现一个分布式事务。原文作者补了一招：如果下游系统以幂等（idempotent）方式处理聚合结果，就不需要分布式事务了。

6系统的扩展：三个零件各自长大

消息队列、聚合服务、数据库三者解耦，可以独立扩展。

  • 扩展消息队列：生产者不加限制，随便扩；消费者靠消费者组（consumer group）加人扩，但要预先创建足够的分区；数千个消费者时，再平衡（rebalancing）可能耗时很长，挑非高峰做；还可以按地理位置拆主题，如 topic_na、topic_eu。
  • 扩展聚合服务：加节点就能扩映射-归约节点；单节点内用多线程提吞吐，或用 Apache YARN 之类的资源提供者上多进程。选项一更容易，选项二在实践中更常用、更可扩展。
  • 扩展数据库：Cassandra 原生支持用一致性哈希（consistent hashing）水平扩展——加一个新节点，数据自动在所有虚拟节点间重新平衡，不需要手动分片。

还有热点问题：某个广告特别火，点击全涌向一个聚合节点怎么办？资源管理器给它追加资源——原节点把事件拆成 3 组，每个聚合节点处理 100 个，结果写回原节点，原节点就不至于过载。更复杂的高级打法还有全局-局部聚合（Global-Local Aggregation）和拆分去重聚合（Split Distinct Aggregation）。

7容错：机器会坏，数不能丢

聚合节点在内存里处理数据——节点一宕机，已处理的数据就没了。第一道防线是 Kafka 的消费者偏移量（consumer offset）：新节点接手后从上次中断的地方继续。但 Top-N 聚合还有额外的中间状态要保。办法是给正在进行的聚合每分钟打快照（snapshot）。节点宕机后，新节点读取最新已提交的偏移量 + 最新快照，接着把作业跑完。

8数据监控与正确性：给数钱的人配个监工

聚合数据用于计费，必须上严格的监控。三个指标：延迟（Latency）——跟踪不同事件的时间戳，看端到端延迟；消息队列大小——队列突然变长说明要加聚合节点，而 Kafka 是分布式提交日志，没有"队列大小"，要看 records-lag 指标；聚合节点的系统资源——CPU、磁盘、JVM。

外加一道日终保险：对账（reconciliation）流程是个批处理作业，每天结束时跑——根据原始数据重新计算聚合结果，和聚合数据库里存的实际数据比对。对不上，就说明流水线某处出了问题。

9替代设计：面试里的另一种答法

泛化的系统设计面试不要求你懂大数据软件的内部原理——讲清思维过程和权衡，比背工具名字更重要。一条现成的替代路线：点击数据存 Hive，上面加一层 ElasticSearch 加速查询；聚合直接在 OLAP 数据库里做，比如 ClickHouse 或 Druid。能用成熟的轮子，就别什么都自己造。

权衡与坑

这一讲的真话：
  • 事件时间和处理时间没有完美解：客户端时钟可能错、可能被伪造；服务器时间对迟到事件又不准。选事件时间，就要一辈子跟迟到事件作斗争。
  • 水印是"多等一会儿"的艺术：短了漏数，长了拖延迟；而且无论多长都不能保证零遗漏，最终只能靠日终对账兜底。
  • 精确一次很贵：要么实现分布式事务，要么全链路做幂等——天下没有免费的"不丢不重"。
  • 星型模式查得快，但过滤维度一多，桶和记录数会爆炸。
  • Lambda 架构要养两条处理路径、两套代码库；Kappa 架构省了一套，但重算时必须给实时流量让路（专门的聚合服务）。
  • 数千消费者的再平衡很慢，要在非高峰做；超级热门的广告会打爆单个聚合节点，热点处理是绕不开的特殊情况。
  • 存偏移量和存结果如果分两步，中间崩了就是新的不一致——"原子"二字值千金。
记住 3 点
  • 这是计费系统：准确性压倒一切，所以 exactly-once + 去重 + 日终对账三件套一个不能少。
  • Kafka 队列负责缓冲解耦，MapReduce DAG（映射 → 聚合 → 归约）负责把无限的事件流压成每分钟的小数字。
  • 队列、聚合服务、数据库解耦后各自独立扩展；热点广告单独加餐，监控盯 records-lag。
