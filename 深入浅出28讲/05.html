一致性哈希：围成圈分糖果

Consistent Hashing

一句话：加一台或减少一台服务器时，只动一小部分数据，而不是全部重排。上一讲把数据切成了片，这一讲解决"这片到底该放哪台机器"才会让集群敢随便加减机器。

哈希空间：0 ~ 2^160-1 哈希函数：SHA-1 加机器：只动一小部分键 用在：DynamoDB · Cassandra · Discord
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

分糖果老师把一万颗糖编上号，撒在一个大圆环上，一群同学围着圈坐。规则只有一条：每颗糖归"从自己位置出发顺时针遇到的第一个同学"。每个同学负责自己面前到下一个同学之间的那一段弧。现在插班来一个新同学，他只从右手边邻居手里接管一小段弧的糖，其他同学手里的糖一颗不动。一致性哈希就是把服务器和同学一样排成圈，加减机器只动相邻那一小段。

第一步 · 搞清问题

集群里有 N 台服务器，一个 key（缓存键、数据行）进来，该存到哪台？最直觉的写法是取模：serverIndex = hash(key) % N。key 散得匀，服务器负载也匀，看起来没毛病。

毛病出在 N 会变。机器会坏、流量会涨，加一台减一台是家常便饭。而取模哈希里，N 是公式的一部分，N 一变，几乎所有 key 算出来的下标都变了：

场景传统取模哈希的后果
服务器数量 N 固定运行良好，键均匀分布
新增一台服务器大多数键被重新分配，引发大面积缓存未命中
移除一台服务器大多数键搬家，负载过载，数据库被打穿

所以这一讲的问题是：怎么设计映射规则，让 N 变化时只有一小部分键重新分布？需求来自所有会加减节点的分布式系统：缓存集群、分片数据库、CDN、负载均衡器。目标两个：重新分布的量最小；数据在各台机器上尽量均匀，别造出热点。

第二步 · 画出大框架

一致性哈希把"选服务器"从一次取模，变成在环上的一次寻找。数据（key）这样流转：

key→ 哈希函数 f（SHA-1）→ 哈希环 0 ~ 2^160-1→ 顺时针找下一台服务器→ 读写落到那台

三个零件各司其职：哈希函数负责把任意 key（或服务器的 IP、名称）稳稳地映射到环上的一个点，与服务器数量完全无关；环提供了一种"顺序"，让"下一台"这个说法成立；查找规则只说一句"顺时针遇到的第一个服务器"，简单到没法更简。正因为映射里不出现 N，加减机器才不会掀翻整张表。

第三步 · 深入零件（按原文小节顺序）

1再哈希问题（Rehashing Problem）

先看清敌人。传统方法 serverIndex = hash(key) % N 在服务器池大小固定时工作得很好；一旦新增或移除服务器，模数 N 变了，大多数键被重新映射——缓存集体失效，请求涌向数据库，系统又慢又危险。这就是再哈希问题：服务器数量变化时，大多数键被重新分布，效率低下、负载过载。

2一致性哈希的定义

定义一句话：一致性哈希确保服务器新增或移除时，只有一小部分键被重新映射。它最大限度减少扰动，天然支持水平扩展。后面几节就是把这句话拆开：环怎么搭、服务器怎么放、key 怎么找、加减机器时边界在哪。

3哈希空间与哈希环（Hash Ring）

这解决"键和服务器怎么放在同一个坐标系里"。取一个哈希函数（比如 SHA-1），它的输出空间是 0 到 2^160-1。把这条线首尾相连，就得到一个环。用同一个函数 f：key 被哈希到环上的点；服务器按自己的 IP 或名称也被哈希到环上的点。两类点共用一把尺子，"谁离谁近"才有意义。

4服务器查找（Server Lookup）

这解决"一个 key 到底归谁管"。规则一条：从 key 在环上的位置出发，顺时针遍历，遇到的第一台服务器就是它的归属。每台服务器实际上负责"从它自己（沿顺时针）到下一台服务器之间"的整段弧。查找只走邻居，跟环上一共多少台机器无关。

5新增与移除服务器

这是重头戏：为什么只有一小部分键搬家。新增服务器时，新节点插进环上某处，它只接管"自己到逆时针方向前驱节点"之间那一段弧上的键，其余键纹丝不动。移除服务器时，它负责的整段弧整体移交给顺时针方向的下一台服务器，别的弧不受影响。两种操作都只扰动一个邻居，这就是"最小化重新分布"的来源。

6虚拟节点（Virtual Nodes）

基础方法有两个毛病：各服务器分到的分区大小不匀；键的分布不匀，有的机器明显更忙。原因是服务器就那几个点，纯属随机落位，难免有的挤有的空。解法是给每台服务器在环上放多个均匀分布的虚拟节点——一台服务器扮好几个角色。虚拟节点越多，键的分布越均衡，因为虚拟节点数量增加，标准差越小。代价是节点元数据更多，数量要权衡。

7受影响的键：边界到底画在哪

运维最想知道的其实是"这次要迁移多少数据"。原文给了精确的边界：新增服务器时，受影响的键位于新节点与其前驱节点之间——例子里 s4 上环，沿环逆时针找到的前驱是 s3，那么 s3 与 s4 之间的键重新分布到 s4。移除服务器时，受影响的是被移除节点与其前驱之间的键——例子里 s1 被移除，逆时针找到前驱 s0，s0 与 s1 之间的键重新分布到 s2（s1 的顺时针下一个）。记住方向：永远是一段弧，不是一个集合。

8一致性哈希的优势

收个尾，三条都是前面推出来的：最小化重新分布——只有一小部分键被重新分配；可扩展性——支持水平扩展，加减机器不再是大手术；缓解热点问题——配合虚拟节点把数据分布做匀，避免个别服务器过载。

9实际应用

这不是纸上算法，它撑起了不少有名的系统：Amazon DynamoDB、Apache Cassandra 用它做数据分片；Discord 用它调度海量连接；Akamai CDN 用它把内容分配到边缘节点；Google 的 Maglev 负载均衡器也用它做流量分发。学这一个算法，等于把半个互联网的分片底座看明白了。

权衡与坑

这一讲的真话：
  • 基础方法（一台机器一个点）有两个坑：分区大小不均和键分布不均——不加虚拟节点，热点自己会冒出来。
  • 虚拟节点不是越多越好：节点越多越均衡，但元数据和维护开销也越大，数量得按标准差和成本一起权衡。
  • 加减机器只解决"搬多少"，不解决"谁来搬"：迁移期间旧节点还在服务，读写路径都要能容忍短暂的边界变化。
  • 取模哈希在服务器数量固定时依然好用，别为了算法而算法——什么时候 N 真的会动，才需要一致性哈希。
记住 3 点
  • 把 key 和服务器用同一个哈希函数放上环，顺时针遇到的第一个服务器负责它。
  • 加减机器只动相邻一段弧——受影响的永远只是"新节点（或被删节点）与前驱之间的键"。
  • 分区不匀、负载不匀，靠虚拟节点解决：节点越多标准差越小，但开销越大。
