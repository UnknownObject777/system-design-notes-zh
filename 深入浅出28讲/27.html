数字钱包：记日记的账房

Digital Wallet · 每秒百万笔转账的账房先生

一句话：每秒一百万笔转账，账要平、历史要能查、还能从头重放——这一讲把支付平台里那个最不能出错的钱包服务，从一台 Redis 一路改到分片的 Raft 集群。

规模：100 万 TPS 可用性：99.99% 关键件：2PC · TC/C · Saga · 事件溯源 · Raft
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

账房先生老式钱庄的账房先生管钱有两条铁律：一是每笔钱都记日记账，谁出一块、谁进一块，一行一行写下来，当天进出必须轧平；二是账本只追加、不改写，错了不涂改，另起一行记冲正。查账的人随时可以搬张凳子，从第一页开始把日记账重新誊一遍，任何一天的总数都能重新算出来。数字钱包干的正是这件事，只是账房先生从一个人变成了一万台机器。

第一步 · 搞清问题

支付平台大多配一个钱包服务：用户把资金存在应用内，可以支付商品、提现，也可以向其他钱包用户转账——走内部账本比走外部支付通道（payment rails）更快、更便宜。这一讲聚焦其中最核心的一个动作：两个钱包账户之间的余额转账。

面试里先问清楚规模和要求，需求清单很短，但每条都很硬：

  • 只做钱包间的余额转账，不涉及外汇兑换，也不覆盖收单等其它操作。
  • 100 万 TPS——每秒一百万笔转账。
  • 可靠性 99.99%，且必须具备事务性保证（transactional guarantee）：账必须平，不能钱从 A 扣了却没到 C。
  • 可重现（reproducibility）：对账（reconciliation）只能发现差异，查不出原因；我们要的是能从头重放数据、重建整个历史。这也直接回答了审计的三连问：任意时刻的余额是多少？历史余额对不对？代码改了之后逻辑还对不对？

规模估算一上来就泼了冷水。传统云上的关系型数据库单节点大约只撑得起 ~1000 TPS；而每笔转账包含两笔分录（leg）——借方扣、贷方加，各算一次写，所以 100 万笔转账实际是 200 万次写。单节点越猛，需要的节点越少：

单节点 TPS所需节点数
10020,000
1,0002,000
10,000200

结论：设计的第一个目标不是"堆机器"，而是把单节点的 TPS 压榨上去，节点数才能降得下来。

第二步 · 画出大框架

把整套系统压成一条数据流，一笔转账请求这样流动：

客户端→ Saga/TC-C 协调者→ 钱包服务（无状态）→ 命令 FIFO 队列→ 状态机（验证 → 生成事件）→ 事件列表（Raft 复制）→ 余额状态（RocksDB）⇢ 只读状态机 → 反向代理推回响应

请求先进协调者，被拆成两个操作（A 减 1、C 加 1）；每个操作作为命令（command）进入 FIFO 队列，由状态机（state machine）验证后转成事件（event）追加进事件列表；事件落库更新余额状态；只读状态机把结果推回。为什么分这么多层？因为每一层只对自己的职责负责：队列管顺序，状态机管正确性，Raft 管不丢，RocksDB 管快，CQRS 读侧管查询——拆开了，每层才能各自做到极致。

第三步 · 深入零件（按原文步骤 2–3 的顺序）

1API 设计：一个端点，一个幂等键

接口刻意收敛到只有一个：POST /v1/wallet/balance_transfer，把 from_account、to_account、amount、currency 连同 transaction_id 一起提交。amount 用字符串传，避免浮点精度丢失；transaction_id 是幂等键——同一笔转账网络重试多少次，账本上也只能出现一次。响应里带上 status 和 transaction_id，客户端凭它查结果。

2内存分片：Redis 集群 + Zookeeper

最朴素的方案：钱包应用为每个账户维护余额，数据结构就是 map<user_id, balance>，用内存 Redis 实现。单个 Redis 节点扛不住 100 万 TPS，就把集群切成多个分区，按 accountID.hashCode() % partitionNumber 定位分区；分区数量和节点地址交给 Zookeeper 存——它是高可用的配置存储。钱包服务本身无状态（stateless），随便水平扩容。但这个方案有个致命伤：余额分落在两台 Redis 上，转账无法原子执行——扣 A 和加 C 之间断了线，账就坏了。这逼出了下面的分布式事务。

3两阶段提交（2PC）：先问能不能，再说做不做

经典办法是在分片的关系型数据库上跑两阶段提交（two-phase commit，2PC）：协调者（钱包服务）照常读写多个数据库，准备提交时先让所有数据库 prepare；全都回"是"才发提交，任何一个回"否"就全部中止。思路简单，但代价明确：锁争用（lock contention）让性能很差——prepare 期间锁一直占着；而且协调者是单点故障（single point of failure）。在 100 万 TPS 的目标下，2PC 只能当垫脚石。

4Try-Confirm/Cancel（TC/C）：把一次事务拆成两次

TC/C 是 2PC 的变体，配合补偿性事务（compensating transactions）工作。关键区别：2PC 里第一阶段事务没完成，锁悬着；而 TC/C 第一阶段结束时每个本地事务已经提交或已经取消——两个阶段是两个独立的事务。以 A 转 C 一美元为例：

阶段操作账户 A账户 C
1尝试（Try）余额 -$1NOP（不做事）
2确认（Confirm）NOP余额 +$1
2取消（Cancel）余额 +$1（冲正）NOP

Try 阶段先把 A 的钱扣下来；两个阶段的数据库都回"是"就走 Confirm，让 C 加钱；任何一步失败就走 Cancel，把 A 扣的钱加回去——加回去这个动作就是"补偿"。对比着记：2PC 第二阶段是提交/取消所有未完成的事务；TC/C 第二阶段是按需执行新事务，或者反转已提交的事务。TC/C 与数据库无关，只要数据库支持事务就行；代价是分布式事务的复杂度全部涌进了业务逻辑。

5TC/C 的故障模式：阶段状态表与"先扣后加"

协调者中途崩溃了怎么办？靠阶段状态表（phase status tables）：在数据库分片内原子地记下每条分布式事务的 ID 和内容、Try 阶段的状态（未发送/已发送/已收到响应）、第二阶段的名称（Confirm 还是 Cancel）及其状态，还有一个乱序标志。协调者重启后读这张表，接着往下走。

更微妙的是一致性窗口：Try 和 Confirm 之间，账面上 A 少了一美元、C 还没多——状态短暂不平衡。可以接受的前提是：总能从这个状态恢复，且用户不能利用中间状态去消费。这靠一条纪律保证：永远先扣减、后增加。Try 阶段在 A 扣钱、C 收 NOP 是唯一合法选择；先给 C 加钱再扣 A 是危险的（用户可能立刻把钱花掉，之后扣款失败），两边同时动又不具备原子性。

还有乱序执行：数据库可能先收到 Cancel 再收到 Try。处理办法正是那张表里的乱序标志——先到的 Cancel 把标志置上，后到的 Try 一看标志已设，直接返回失败。

6Saga：一串本地事务，配上往回走的补偿

Saga 是微服务架构里做分布式事务的标准姿势：所有操作排成一个序列，各自在本地数据库里独立提交，依次执行；某一步失败，就掉头往回走，对已经做过的每一步执行补偿操作，一直回到起点。协调方式有两种：编排（Choreography）——各服务订阅事件、各干各的，但业务逻辑被拆进多个服务、靠异步消息串起来，难调试；编配（Orchestration）——单个协调者指挥所有服务按序干活，复杂性被收敛到一处。数字钱包选编配。

7事件溯源（Event Sourcing）：不存余额，存历史

审计三连问——任意时刻的余额？历史余额对不对？代码改了逻辑还对不对？——由事件溯源统一回答。它由四个概念组成：

  • 命令（command）：来自现实世界的意图，比如"A 转 B 一美元"。命令可能失败（IO 错误、状态无效、外部不确定性），所以要有全局顺序，进 FIFO 队列；一条命令可以产生零个或多个事件。
  • 事件（event）：系统内已经发生的事实，比如"已将一美元从 A 转到 B"。事件是史实，同样进 FIFO 队列保序。
  • 状态（state）：事件作用的结果，比如"账户 → 余额"的键值存储。
  • 状态机（state machine）：驱动整个过程——验证命令、应用事件、更新状态。它必须确定性（deterministic）：不读外部 IO、不依赖随机性，给同样的事件序列必产出同样的余额。

落到钱包上：转账请求就是命令，进 Kafka 之类的队列；状态机从队列读命令、从数据库读余额、验证后为每个账户生成两个事件，再逐个应用、更新余额。最大的红利是可重现性：所有状态更新都存成不可变的追加历史，历史余额永远可以从头重放事件重建——因为事件列表不可变、状态机确定，任何中间状态都保证能重放出来。于是审计三问都有了答案：重放到感兴趣的时间点、从头重算全部事件验证正确性、拿不同版本的代码跑同一批事件比对结果。查询余额则由 CQRS 接管：另起多个只读状态机，基于不可变事件列表回答历史查询，与写路径彻底分开。

8高性能事件溯源：把 Kafka 赶出去

外部队列和数据库意味着网络往返，100 万 TPS 吃不消。优化思路是一切本地化：命令和事件直接追加（append）到本地磁盘——只做追加的写对磁盘极快；再用 mmap 一石二鸟：数据落本地盘，又自动缓存在内存里，省掉重新加载。状态也搬到本地文件系统，用 RocksDB（基于文件的本地存储引擎）：它采用日志结构合并树（log-structured merge-tree，LSM），为写优化；读性能靠缓存补。最后，定期把快照（snapshot）存成大二进制文件放进 HDFS 这类分布式文件存储——重放到某个状态不必每次从头来，从最近的快照接着放就行。

9可靠的事件溯源：只给事件列表上 Raft

本地化了，服务就变成有状态的——机器一挂，数据跟着没。先想清楚什么数据值得花可靠性成本：状态和快照都能从事件列表重放重新生成，而事件列表没法从命令列表重新生成（命令是非确定性的）。结论：只需保证事件列表不丢、且各副本内相对顺序一致。方案是Raft 一致性算法：一个活跃领导者（leader）、若干被动跟随者（follower），领导者挂了有跟随者接任，只要过半节点在线系统就继续跑。Raft 保证所有节点的事件列表相同，各节点再各自更新自己的状态。

10分布式事件溯源：反向代理、推送与分片 Raft 组

单机再猛也有顶：单个 Raft 组容量有限，终要分片 + 分布式事务；CQRS 模式下客户端轮询也慢——频率低了不实时，频率高了压垮查询服务。两步补救：引入反向代理（reverse proxy），代用户发命令、代用户轮询，一次请求还能捎回多个用户的数据，负载大减；再进一步，让只读状态机在响应就绪时主动把结果推回反向代理，用户感受到的就是实时更新。最后的形态：多个 Raft 组分片，由编排者（orchestrator）用 TC/C 或 Saga 在它们之上做分布式事务。一笔转账的完整生命周期：用户 A 把 A-1、C+1 两个操作发给 Saga 协调者 → 协调者在阶段状态表建记录 → 算出命令该去哪个分区 → 分区 1 的 Raft 领导者验证命令、转成事件、复制到组内节点 → 事件同步到只读状态机，把响应推回协调者 → 协调者记下操作 1 成功，再对 C+1 重复同样流程 → 全部成功，结果告知客户端。

权衡与坑

这一讲的真话：
  • 内存 Redis 分片快，但不是持久化存储，也无法原子执行跨分片转账——别拿它当账本。
  • 2PC 性能差（锁争用）且协调者是单点故障；它只适合当理解分布式事务的起点。
  • TC/C 和 Saga 都存在部分不一致的可见窗口；纪律是先扣后加，绝不能反过来，也不能两边同时动。
  • TC/C 能并行、Saga 只能线性——选谁取决于延迟要求；代价是复杂度全部进了应用代码。
  • 本地化（mmap、RocksDB）换来单节点性能，但服务变有状态；忘了 Raft 复制，就是忘了可靠性。
  • CQRS 下轮询不实时，高频轮询会压垮查询服务；反向代理和推送能缓解，但链路更长、组件更多。
  • 命令是非确定性的：事件列表不能从命令列表重建，所以可靠性只保事件列表——这条想错了，审计的地基就塌了。
记住 3 点
  • 转账 = 两笔分录（leg），先扣后加是唯一安全的尝试顺序；补偿是正常流程，不是异常流程。
  • 事件列表是唯一真相源：状态、快照都能重放重建，事件不能；给事件列表上 Raft，就同时拿到审计和可靠性。
  • 路线演进：内存 Redis → 关系库 + 分布式事务（2PC/TC-C/Saga）→ 事件溯源 → 本地化 + Raft 复制 → 分片 Raft 组。
