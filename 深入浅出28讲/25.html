排行榜：自动排队机

Real-time Gaming Leaderboard

一句话：百万玩家实时冲榜，查前十名和我排第几都要飞快。难点不在"存下分数"，而在"排名永远现成"——每次得分后，榜单自己保持有序。

规模：2500 万 MAU · 500 万 DAU 得分峰值：2500 QPS 单月存储：约 650 MB 涨 10 倍：65 GB · 25 万 QPS
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

擂台积分榜游戏厅办月度擂台赛：每月换新榜，赢一局名字旁加一颗星，星星多的名字自动往前挪，永远不用工作人员下班后排一次队。想看前十？榜单最上头一眼扫完。想知道自己排第几？机器直接报号，还能顺带给你看前后各四个人。Redis 的有序集合（sorted set）就是这样一台"自动排队机"——数据进去就是排好序的，查名次只是报个数，不用现数。排行榜系统的全部设计，就是围着这台机器打转。

第一步 · 搞清问题

给一款在线手机游戏做排行榜。面试时先把问题问清楚，每一条都决定了后面的设计：

  • 分数怎么算？每赢一场比赛得 1 分，规则极简。
  • 谁上榜？所有玩家，不只前几百名。
  • 榜有没有时效？每月开一场新锦标赛，同时开一张新榜；旧榜进历史存储。
  • 要看什么？前 10 名 + 我自己的排名；加分项是我前后各四名。
  • 同分怎么办？排名相同，先接受并列；有时间再讨论用"最近一次比赛时间"打破平局。
  • 要实时吗？要。赢一场马上反映在榜上，不接受批量算好的历史结果。

功能需求三条：显示前 10 名；显示指定用户的排名；显示某用户前后各四名（加分项）。非功能需求：分数实时更新、更新实时可见，外加常规的可扩展、可用、可靠。

再拍脑袋算一笔账（原文数字）：

指标数值
月活 / 日活2500 万 MAU / 500 万 DAU（估算时按 5000 万 DAU 算）
平均 / 峰值在线50 用户/秒 · 峰值 250 用户/秒
得分写入 QPS每人每天 10 场 → 500 QPS，峰值 2500
前 10 名读取 QPS每人每天打开一次 → 50 QPS
单月存储ID 24 字符 + 分数 16 位 = 26 字节 × 2500 万 ≈ 650 MB

结论：写多读少（2500 : 50），总量不大（650 MB），但"查排名"这个操作对普通数据库非常不友好。记住这两个特征，选型就有了方向。

第二步 · 画出大框架

API 三个就够：

  • POST /v1/scores——传 user_id 和 points，更新分数。只允许游戏服务器调用，客户端不能直接调。
  • GET /v1/scores——返回前 10 名，带 rank 和 score。
  • GET /v1/scores/{user_id}——返回某用户的分数和排名。

数据这样流动：

客户端（赢了一场比赛）→ 游戏服务：验证胜负有效→ 排行榜服务→ Redis 有序集合（本月榜）
玩家查询→ 排行榜服务→ 前 10 名 / 我的排名· MySQL：用户资料 + 比赛记录（兜底重建用）

为什么要隔出"游戏服务"这一层？因为分数必须是赢来的。让客户端自己上报分数，等于让玩家自己填成绩单——原文点名了风险：中间人攻击，玩家架个代理就能随意改分。所以写入路径上必须有一个信得过的裁判：服务器验证胜利有效，才代客户端调排行榜服务。对由服务器托管游戏逻辑的游戏，连这一步都省了——胜负本来就是服务器算的，顺手记一分。

数据模型有两条候选路：关系型数据库（MySQL）和 Redis。NoSQL 作为备胎留在第三步讨论。先各自走一遍，看看"查我排第几"这关它们各是怎么过的。

第三步 · 深入零件（按原文顺序）

1关系型数据库方案：先感受"为什么不够"

用户少时最省事的做法：一张排行榜表，每月一张（原文备注：其实加一个 month 列更合理，免得每月维护新表）。用户赢一分，第一次先 INSERT，之后 UPDATE leaderboard SET score=score+1 WHERE user_id='mary1934'。

取前 10 名也不难：在 score 上加索引，ORDER BY score DESC LIMIT 10，不用全表扫描。真正的麻烦是查"我排第几"：得跑一条嵌套查询——数出所有分数比我高的人数，那个数加一就是我的排名。这在内部等于对全表做计数排序，行数上到百万级就彻底跑不动。关系库能存榜，但算不出排名——这就是要换零件的原因。

2Redis 方案：一个结构顶三个查询

Redis 是内存数据存储，快，而且自带一个刚好对口的数据结构：有序集合（sorted set）。它内部一头用哈希映射存 user_id → score，另一头用跳表（skip list）把分数按顺序串起来。关键是：数据始终保持有序——写入时就排好了队，读的时候根本不用排序。

跳表是什么？一个有序链表加多级索引。原文的直观例子：64 个节点里找一个值，朴素链表平均要遍历 62 个节点，跳表只要 11 个。代价是增删查都是 O(logN)，换来的是任何规模的榜都能秒回。

四个命令撑起整个服务：

  • ZADD——用户不在就插入，在就更新分数。O(logN)。
  • ZINCRBY——分数直接加给定值，新用户从零起。O(logN)。赢一场就是 ZINCRBY leaderboard_feb_2021 1 'mary1934'。
  • ZRANGE / ZREVRANGE——按分数取一段。O(logN+M)，M 是返回条数。取前 10 名： ZREVRANGE leaderboard_feb_2021 0 9 WITHSCORES。
  • ZRANK / ZREVRANK——查某用户排名。O(logN)。

加分项也顺手解决了：先用 ZREVRANK 拿到我的名次，再 ZREVRANGE leaderboard_feb_2021 357 365 把前后各四名一起取回来。

规模核一遍：最坏情况当月 2500 万 MAU 全参与，26 字节 × 2500 万 ≈ 650 MB；就算跳表开销让存储翻倍，现代 Redis 集群也轻松装下。2500 QPS 的写入峰值，单台 Redis 也罩得住。每月建新榜，旧榜挪进历史存储。

兜底不能少：起一个 Redis 副本，服务器崩了不丢数据；开 Redis 持久化再上一道保险；MySQL 里建两张辅助表——一张存用户名、显示名等资料，一张存每次赢比赛的记录，基础设施出大事时能拿它重建整张榜。另外一个小优化：前 10 名的用户信息被高频访问，值得单独缓存一份。

3云服务还是自己管

这解决"谁来养运维"的问题。自己管：Redis 存榜，MySQL 存用户资料，用户资料量大时再给它配一层缓存。上云：AWS API Gateway 把 API 调用路由到 AWS Lambda 函数——无服务器（serverless），按需运行、自动扩展，不用管服务器和扩容配置。原文作者的建议很直接：从零开始做这款游戏，就用云这套。

4Redis 的扩展：分片的两种切法

单机方案在 5000 万 DAU 内都够用。但假设涨 10 倍到 5 亿 DAU：存储要 65 GB，QPS 到 25 万，单机吃不下了，必须分片（sharding）。两种切法，差别很大。

按分数范围分区：比如 [0-1)、[1-100)、[100-900)、[900-1000] 各放一个分片，应用代码里维护 user_id 到分片的映射（放在 MySQL 或另一个缓存里）。取前 10 名只需查最高分片 [900-1000]；算我的排名 = 我在本分片内的排名 + 其他所有分片里分数比我高的人数——后者是 O(1) 操作，用 info keyspace 命令直接拿到每个分片的总记录数。

Redis Cluster 哈希分区：像一致性哈希（consistent hashing）那样把数据散到各节点。麻烦在于：取前 10 名要向每个分片各取前 10，再在应用层合并；K 一大，延迟就涨，而且随分片数量一起涨；更致命的是没有直接办法算某个用户的排名。所以原文作者倾向固定范围分区。

两个运维要点：写入量大的 Redis 节点，内存按需求量的两倍分配，给快照留地方；用 redis-benchmark 压测自己的部署，用数据说话。

5替代方案：NoSQL（DynamoDB）

如果诉求是"海量写入 + 分区内按分数高效排序"，DynamoDB、Cassandra、MongoDB 都值得看。原文选了 DynamoDB：全托管、性能可靠，还能用全局二级索引（global secondary index）查询主键以外的字段。

设计要点：把分数做成排序键（sort key），按分数查才扩得动。但按月分区会造出热点分区——人人只看当月，旧月吃灰。对策是写入分片（write sharding）：给每个键用 user_id % num_partitions 附加一个分区号，把写入摊开。分区数是核心权衡：分片越多写越强，但读要把所有分片扇出收集（scatter-gather）一遍再聚合，分片越多读越慢——定多少，只能 benchmark 说了算。

这条路的硬伤和老问题一样：算不出精确排名.规模真到了那一步，可以退一步告诉用户百分位——跑一个 cron 作业定期分析分数分布，比如"10th percentile = score < 100，20th = score < 500……90th = score < 6500"，用户至少知道自己在大约前百分之几。

权衡与坑

这一讲的真话：
  • 让客户端自己报分数 = 让玩家自己填成绩单，中间人攻击一打一个准。写入只能信游戏服务。
  • 关系型数据库能存榜，但"我排第几"是嵌套 COUNT 查询，行一多就垮——别拿 MySQL 硬扛百万玩家的实时排名。
  • Redis Cluster 哈希分区没有直接算排名的办法；取前 K 名要全分片扇出合并，K 大、分片多，延迟就压不住。
  • 范围分区反过来要在应用层维护 user_id → 分片映射——多一本账，多一份心事。
  • 分片（write sharding）分区数是个跷跷板：写扩展上去了，读的 scatter-gather 就重；选多少只能靠基准测试。
  • NoSQL 方案给不出"你排第 6"，只能给"你大约在前 20%"——百分位是精确排名的降级品。
  • Redis 会崩：副本 + 持久化 + MySQL 留底，三保险；大规模宕机时用脚本遍历 MySQL 的 WAL 记录重建整张榜。
  • 写入量大的 Redis 节点内存要给两倍余量，否则快照没地方放。
记住 3 点
  • 排行榜 = 一个有序集合：写入 ZINCRBY O(logN)，读前十 ZREVRANGE、查名次 ZREVRANK，一个结构全包。
  • 要分片时按分数范围分区，别用哈希分区——前十和名次都还算得出来。
  • 分数只能由游戏服务写入；客户端直连写榜，榜就脏了。
