限流器：门口的闸门

Rate Limiter

一句话：每人每分钟只能来几下——限流器就是服务器的闸门，防挤爆、防捣乱、保公平：超额的请求拦在门外，正常用户永远进得来。

限流算法：5 种 部署位置：3 选 1 计数器：存 Redis 被拦请求：HTTP 429
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

地铁闸机早晚高峰的地铁进站闸机：不管你是谁、跑多快、多着急，闸机只按自己的节奏放人——一秒一个，行就是行，不行就拦在门外。你兜里再有急事，它也不破例，但也没冤枉谁：每个人面前都是同一套规则。限流器就是服务器门口的闸机：请求来了先过闸门，闸门心里记着数——"这个用户这一分钟已经来了 60 次？"对不起，拦下，明确告诉他"你超了，请稍后再来"。

第一步 · 搞清问题

没有闸门会怎样？三种死法都很常见：被捣乱——恶意脚本死循环调接口，把你打到资源耗尽（DoS 攻击）；被挤爆——活动一开，流量瞬间暴涨，服务器过载，正常用户跟着陪葬；被烧钱——大量没必要的请求白吃服务器资源，账单蹭蹭涨。限流器要守住的，就是每个调用方在单位时间内的请求次数这条线。

限流的好处，原文列了三条：

  1. 防止 DoS 攻击——阻止过量调用，避免资源被耗尽。
  2. 降低成本——限制不必要的请求，减少服务器开销。
  3. 防止过载——过滤掉过多的请求，稳定服务器性能。

再看这个系统本身要满足什么。规模假设：这是一个服务端 API 限流器，跑在分布式的大规模系统里，要同时执行多条限流规则（不同接口、不同用户，配额各不相同）；实现形态二选一——独立服务，或直接写成应用级代码；请求被限流时，必须通知用户，不能闷声吞掉。具体需求原文给了六条：

需求意味着什么
精确的请求限流说 100 次就是 100 次，不能多放，也不能误杀
极低的延迟闸门不能比业务还慢，每次检查都得快到无感
低内存占用要记成千上万个调用方的计数，数据结构必须省
支持分布式多台机器共享同一份计数，不能各记各的
清晰的异常处理被限流的请求收到明确答复（HTTP 429），而不是超时或挂起
高容错性限流器自己出问题时，不该把业务一起拖死

第二步 · 画出大框架

闸门装在哪儿？原文给了三个位置：

  1. 客户端实现——不可靠，客户端可以被滥用、被绕过，等于让乘客自己数自己。
  2. 服务端实现——更受青睐，便于控制、更可靠。
  3. 中间件（API 网关）——灵活的方案，可统一集成限流功能，一处判流，处处生效。

选位置的指导原则：评估现有技术栈，选高效的方案；根据业务需求选合适的算法；微服务架构可以直接用 API 网关；资源有限时，甚至可以买商业方案。数据（请求）这样流转：

客户端→ 限流中间件（闸门）→ Redis 计数器→ 放行 → API 服务器

中间件查完计数器，按规则分流：没超额的请求放行进 API 服务器；超额的直接返回 HTTP 429 和"你被限流了"的提示，根本不进业务逻辑。为什么把闸门放在中间件这层？因为判一次就够——写在每个接口里，规则一改要动全身；放在门口，所有流量先进同一道闸，规则集中管理，业务代码干干净净。

第三步 · 深入零件（按原文第 1–9 节的顺序）

1令牌桶（Token Bucket）：攒筹码，花一个过一个

解决什么问题：既要限住平均速度，又允许合理的突发——用户偶尔一秒内连点几下，不该被误杀。

做法：一个桶，以固定速率往里面放令牌；每个请求消耗一个令牌，桶空了请求就等或被拒。两个参数：桶容量（允许突发多少）和补充速率（平均放行多快）。比如容量 10、每秒补 2 个：平时攒着，突来 10 个请求一把全放，之后就得跟着补充速率走。优点：易于实现、节省内存、支持流量突发。缺点：两个参数得仔细调参——桶太大形同虚设，太小又误杀正常用户。

2漏桶（Leaking Bucket）：进得快，出得匀速

解决什么问题：让放行的流量像漏水一样匀速，保护后面的服务不被突发冲垮。

做法：请求进入一个 FIFO 队列，以固定速率从队列里取出处理——进水管可以汹涌，出水管永远匀速。优点：节省内存、流出速率稳定。缺点：突发流量会把队列堆长，新到的请求被延迟。真实世界的实现：uber-go/ratelimit。

3固定窗口计数器（Fixed Window Counter）：按分钟翻页计数

解决什么问题：最省事的"数次数"办法，适合对精度要求不高的场景。

做法：把时间切成固定窗口（比如每分钟一格），每格一个计数器；窗口内请求数超配额就拒绝，新窗口开启计数清零。优点：实现简单、对特定场景高效。缺点：窗口边界的流量尖峰会漏——限制每分钟 100 次，59 秒处来 100 次全放行，下一分钟第 1 秒又来 100 次又全放行，两秒实际过了 200 次，超额的请求就这样通过了。

4滑动窗口日志（Sliding Window Log）：记住每一次

解决什么问题：固定窗口的边界漏洞，用精确换来填补。

做法：给每个调用方记一份时间戳日志，窗口随到随滑：每来一个新请求，先把早于当前窗口起点的时间戳清掉，再数剩下的次数决定是否放行。优点：限流精确，是真·滚动窗口。缺点：内存消耗高——时间戳一条条存，调用方多、请求密，日志很快就爆。

5滑动窗口计数器（Sliding Window Counter）：折中的艺术

解决什么问题：固定窗口太糙，滑动日志太贵，能不能两头兼顾？

做法：结合固定窗口与滑动日志两种方法——按当前窗口已过去的比例，把上一个窗口的计数加权折算进来，和当前窗口的计数相加，平滑尖峰。优点：节省内存、能够处理流量突发。缺点：近似计算，边界处可能不够严格。

6高层架构：计数器放 Redis

解决什么问题：计数要读写得快，还得让多台限流器看到同一份数。

原文的流程三步走：① 客户端向中间件发送请求；② 中间件检查 Redis 中的计数器；③ 根据限制条件处理或拒绝请求。数据存储用内存缓存（如 Redis）——计数器是典型的"高频小数据"，Redis 读写快，天然是它的家。

7分布式环境：大家共用一本账，会打架

解决什么问题：多台限流器同时查、同时改同一个计数，数就数乱了。

挑战是竞态条件（race condition）和同步问题：两台机器同时看到"99 次"，各自放行一个，实际就超了。解法：用 Redis 里的锁、Lua 脚本或有序集合（sorted set）——核心是采用集中式数据存储实现同步，让计数操作原子化。

8性能优化：闸门自己也要快

解决什么问题：限流器要求极低延迟，那它自己就得处处省时间。

两条原文给的招：多数据中心架构，让请求离计数器近一点，检查延迟就低一点；使用最终一致性模型进行同步——计数差一个半个没关系，宁可让各中心的数短暂漂移，也别让强一致拖慢闸门。

9监控：闸门不是设完就完事

解决什么问题：规则合不合理，不看数据就是拍脑袋。

原文一句话：定期分析以确保算法的有效性，并根据需要调整规则。看两样东西：限流触发的频率（是不是老误伤正常用户）和实际流量曲线（该挡的挡住没有）。触发率异常高，可能是配额太紧或有人在刷；挡完流量还是过载，可能是配额太松。

权衡与坑

这一讲的真话：
  • 固定窗口在边界处会放行超额请求：两个窗口的尖峰叠加，两秒实际通过 2 倍配额。
  • 滑动窗口日志精确，但内存消耗高——调用方一多，时间戳日志就成了负担。
  • 漏桶会延迟突发请求；令牌桶参数调不好，要么形同虚设，要么误杀良民。
  • 滑动窗口计数器是近似计算，对"严格一分钟只能 N 次"这种硬要求不够用。
  • 分布式下有竞态条件：两台限流器同时看到 99 次、各自放行，计数就失真——锁、Lua 脚本、有序集合各有各的代价。
  • 限流器自己也是一道关口：它慢了，全站堵门口；它挂了，要么全放行（等于没限流），要么全拒（全站宕机）。
记住 3 点
  • 限流就是给每个调用方定配额：闸门挡住超额请求，明确返回 HTTP 429。
  • 五种算法没有全能王——要突发选令牌桶，要匀速选漏桶，要简单用固定窗口，要精确用滑动日志，要折中用滑动窗口计数器。
  • 计数放 Redis，分布式环境靠锁 / Lua 脚本 / 有序集合防竞态；规则上线后还得监控、要调。
