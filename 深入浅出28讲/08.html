短链接：给网址起小名

URL Shortener · 短码生成与重定向

一句话：把老长的网址压成几个字符，点它就能跳回去。功能上这就是 TinyURL 干的事，难点不在"能跳"，而在每天 1 亿个新短码还不能重号。

写入：1 亿个/天 读写比：10 : 1 规模：3650 亿条 · 365 TB 短码：7 字符 ≈ 3.5 万亿空间
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

快递取件码你把一件大行李存进快递柜，柜台不给你行李本身，只回你一张小票：6 位取件码。任何人凭这个码，都能在柜子里找到你的行李。短链接一模一样：把又长又乱的原网址"存"进数据库，发一个几个字符的短码当小票；别人点这个码，服务器查柜、领出原网址，把浏览器支过去。整个系统就是一台"网址快递柜"，核心难题只有一个：每天 1 亿张小票，不能发重号。

第一步 · 搞清问题

原始网址常常长到没法看：带一堆参数的链接塞进短信、微博、二维码里，又丑又占地方。这一讲要做的就是 TinyURL 那种服务：给它一个长网址，它返回一个尽可能短的唯一短码；别人点短码，浏览器跳回原网址。

拆开看，系统要同时满足三件事：URL 缩短（生成短码）、重定向（点短码跳回去）、高可扩展性（流量大了扛得住）。原文给的需求和规模假设：

指标假设
短 URL 生成量每天 1 亿个请求
服务年限10 年容量
读写比例约 10 : 1（读远多于写）
总记录数约 3650 亿条
总存储约 365 TB
短码长度7 个字符（够用且不丑）

对外接口只有两个，简洁得不像话：

  1. 缩短：POST api/v1/data/shorten，参数 {longUrl: ...}，返回 shortURL。
  2. 重定向：GET api/v1/shortUrl，返回对应的 longURL，让浏览器跳过去。

真正有意思的是背后的算术：一天 1 亿个、存 10 年，就是 3650 亿条、365 TB——所以"怎么发号"和"怎么存"才是这一讲的主菜。

第二步 · 画出大框架

把读写两条路画成一张图，数据这样流动：

用户→ Web 服务器（无状态 ×N）→ 写：ID 生成器 → Base 62 编码→ 数据库· 读：先查缓存→ 301 / 302 重定向

两条路分开，是因为流量结构不对等：读写比 10:1，十个请求里九个是"点短码跳转"。写路径（缩短）要解决的问题是发号不重复——先由分布式 ID 生成器发唯一 ID，再编码成短码落库；读路径（重定向）要解决的问题是快——热门映射放缓存，命中就不用碰数据库，最后按 301 或 302 把浏览器支回长网址。

Web 层刻意做成无状态：它只负责接请求、查库、转发，不保存任何"记忆"，这样流量涨了加减服务器就行。状态全在数据库和缓存里，那是第 1 讲就立下的规矩。

第三步 · 深入零件（按原文小节顺序）

1URL 重定向：301 还是 302

这解决"点了短码之后，浏览器该怎么跳"。两个状态码，一字之差，后果不同。301 重定向：告诉浏览器"这个短码永久对应那个长网址"，浏览器会把结果缓存下来，之后同一短码不再来问短链服务——省服务器，但点击统计也从此丢了。302 重定向：临时跳转，浏览器每次都要回来问——能精确统计点击次数，适合做分析，代价是读流量全落在服务上。选型是业务题，不是技术题。

2URL 缩短：哈希函数的两条军规

这解决"长网址怎么变成短码"。做法是用哈希函数（Hash Function）把长网址映射成短码，但它必须满足两条：每个 longURL 都被哈希成唯一的 hashValue；每个 hashValue 都能映射回对应的 longURL。前者保证不重号，后者保证跳得回去——两条缺一，快递柜就乱了。

3数据模型：一张三列表

这解决"映射存哪儿"。把 <shortURL, longURL> 的对应关系存进关系型数据库，表结构只有三列：id（主键）、shortURL、longURL。不折腾花哨存储，因为需求朴素：按短码查原网址，一行 SQL 的事。365 TB 听着吓人，但每条记录就几十字节，关系型数据库加缓存扛 10:1 的读绰绰有余。

4哈希函数之一：Base 62 转换

这解决"怎么把号码变成字符串"。字符集用 [0-9, a-z, A-Z]，共 62 个可用字符（所以叫 Base 62）。给每个网址分配一个唯一 ID，把 ID 做 62 进制转换，得到的字符串就是短码。原文的例子：ID 2009215674938 → Base 62 转换后 → zn9edcu。算笔账：7 位字符最多有 62⁷ ≈ 3.5 万亿个唯一短码，装下 3650 亿条需求还有近十倍余量。

5哈希函数之二：哈希 + 冲突解决

这解决"不用 ID 怎么直接压码"。另一条路：拿 CRC32、MD5 或 SHA-1 这类哈希函数直接对长网址算哈希，取结果前 7 个字符当短码。问题是哈希值撞车——两个不同网址算出同一个短码。补救办法：撞了就递归地追加一个预定义字符串，再哈希，直到不撞为止；缺点是成本高。布隆过滤器（Bloom Filter）是省钱的判重工具：它能快速告诉你一个短码"一定不存在"或"可能存在"，把绝大多数查库确认挡在内存里。

6方案对比：两条路摆上台面

这解决"选哪条路"。两条路线对比如下：

哈希 + 冲突解决Base 62 转换
短码长度固定不固定，随 ID 增长变长
唯一 ID 生成器不需要需要
冲突可能冲突，要解决不会冲突
预知下一个短码做不到（不依赖 ID）ID 按 1 递增就能猜——安全隐患

原文示例系统选了 Base 62：无冲突、流程直，代价是必须配一个分布式 ID 生成器——那正是上一讲（第 7 讲）的主角。

7URL 缩短流程：写路径四步走

这解决"来一个缩短请求，内部按什么顺序动"。流程是：

  1. 先查 longURL 是否已存在于数据库中（同一个长网址重复缩短，不该发两张小票）。
  2. 已存在，直接返回现有的 shortURL。
  3. 不存在，用分布式 ID 生成器生成唯一 ID。
  4. 用 Base 62 把 ID 转成 shortURL，把 <id, shortURL, longURL> 这条映射存进数据库。

8URL 重定向流程：读路径三步走

这解决"点短码之后内部怎么找路"。流程是：

  1. 用户点击某个 shortURL。
  2. 查 <shortURL, longURL> 映射：先查缓存求快；缓存没有，再查数据库。
  3. 拿到 longURL，把用户重定向过去（301 或 302）。

读写比 10:1 的全部分量都在第 2 步：读路径必须短，热点映射必须留在内存里。

9限流器：防刷票的保安

这解决"有人拿脚本疯狂 shorten 怎么办"。加限流器（Rate Limiter），按 IP 设置请求限制，超限直接拒。没有它，1 亿/天是容量，有它，1 亿/天才只是正常业务量。

10可扩展性：两层各自扩

这解决"流量再涨十倍怎么办"。Web 层无状态，加服务器就扩，减服务器就缩，和前两讲一个套路；数据库层上复制（Replication）和分片（Sharding）：复制分摊读压力，分片分摊数据量。365 TB 早晚要多机分摊，这一步是预留的台阶。

11分析：点击数据是隐藏资产

这解决"白跳的流量凭什么浪费"。收集点击率、来源和时间戳：谁发的链接、什么时候被点、点了多少次。短链服务天然站在流量入口上，这些数据拿来做业务洞察，是附赠的金矿。

12高可用性与可靠性：柜子不能塌

这解决"机器挂了小票还能不能取件"。靠数据库复制和容错设计兜底：主库倒了从库顶上，保证服务的一致性和可靠性。短链是基础设施，别人把链接发出去了，你这儿就必须 24 小时取得出货。

权衡与坑

这一讲的真话：
  • 301 和 302 是来回扯的绳：301 被浏览器缓存后，点击统计永远丢了；302 每次都要查服务，读压力实打实。想省钱还是想数清楚，只能选一个。
  • 哈希取前 7 位必然撞车；递归追加字符串能解，但成本高，而且越撞越慢。
  • 布隆过滤器会说谎：它只能告诉你"一定不存在"或"可能存在"，"可能存在"必须再查库确认，不能直接当结论。
  • Base 62 若 ID 按 1 递增，任何人都能猜出下一个短 URL，顺藤摸瓜遍历别人的链接——这是原文点名的安全隐患。
  • 缩短前先查"这个长网址有没有缩短过"，在 3650 亿行的表上不是免费操作，去重本身就要花心思。
记住 3 点
  • 发号只有两张牌：哈希 + 冲突解决（长度固定但会撞）或唯一 ID + Base 62（无冲突但要配 ID 生成器、还可能被猜号）。
  • 10:1 的读多写少系统，先把读路径做短：缓存命中就不要碰数据库。
  • 301 省服务器、302 保统计——这是业务决策，不是随手填的状态码。
