唯一 ID：不发重的学号

Unique ID Generator

一句话：几万台机器同时发号，全宇宙唯一，还能按时间排大小。每条 tweet、每个订单都要一个这样的 ID，这一讲就是造发号器。

硬指标：64 位数字 ID 吞吐：10,000+ ID/秒 方案：Twitter Snowflake 分段：41 + 5 + 5 + 12 位
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

学号一个大学城几万人同时报到，每人进门就要立刻领一个全校唯一的学号，学号还要能看出谁先报到谁后报到。让教务处开一张总单子挨个填，队伍能从南门排到北门（集中发号，又慢又单点）。Snowflake 的做法是把学号切成几段：年份 + 校区 + 报到处 + 流水号。每个报到处自己填自己的流水号，互不商量，流水号从 1 往上数——校区不同、窗口不同，号永远撞不上；年份在前，号天然按时间排好序。唯一和有序，都是靠"分段"换来的，不是靠排队。

第一步 · 搞清问题

单机时代这事好办：数据库一条 auto_increment 搞定，因为只有一个"发号窗口"。可到了分布式环境，机器是几百上千台，每台都想自己发号，自增键立刻撞上两堵墙：扩展性（加一台机器怎么错开已有的号？）和同步（跨数据中心怎么对表？）。

所以这一讲要造的发号器，得同时满足下面几条：

需求原文的硬指标
唯一任何机器、任何时刻发出去的号不能重复
形态必须是数字，且塞得进 64 位
有序按日期可排序，随时间递增（但不要求严格 +1）
吞吐每秒生成 超过 10,000 个 ID

"不严格 +1"这条很值得琢磨：它放开了"号码必须连续"的执念——只要晚发的号比早发的大，中间跳号完全没关系。这个松弛条件，正是后面 Snowflake 方案能成立的地基。

第二步 · 画出大框架

原文先把候选路线摆上桌，再逐条过堂。数据（发号请求）的流向取决于走哪条路：

应用：要一个新 ID→ 路线 A：多主库轮流发（有中央协调）/ 路线 B：票据服务器集中发（有中央协调）/ 路线 C：Snowflake，每台机器本地发号→ 拼五段：时间戳 · 机房 · 机器 · 序列号→ 64 位 ID

前两条路的共同点是存在中央协调者：要么几台数据库约定步长轮流发，要么一台专职发号服务器挨个派。协调者一存在，"加机器"和"挂一台"立刻变成全局难题。Snowflake 的思路是把发号权下放到每台 Web 服务器手里：各发各的，机器之间零协商，唯一靠号段错位来保证，时钟靠 NTP 来对表。哪条路走得通，第三步逐条验证。

第三步 · 深入零件（按原文候选方案 1–4 的顺序）

1多主复制（Multi-Master Replication）：还是想让数据库自增

解决什么问题：团队最顺手的方案仍是数据库自增，能不能改改用下去？做法：开 k 台数据库做主，每台都用 auto_increment，但把步长（step）调成 k——第 1 台发 1、1+k、1+2k……，第 2 台从 2 起步，第 3 台从 3 起步。每台错开一格，号不撞。

坑也写在原文里：难跨数据中心扩展；ID 不总随时间递增——同一时刻三台库各发各的，后发请求的号可能比先发的还小，排序性没了；加机器、减机器要重排所有人的步长，动静很大。

2UUID（通用唯一标识符）：彻底不要协调

解决什么问题：既然协调麻烦，干脆取消协调——每台服务器独立生成 128 位全局唯一标识符，机器之间互不通信。优点很硬：无需协调、随 Web 服务器轻松扩展。

但对不上我们的需求单：128 位直接超出 64 位红线（存储翻倍、索引变大）；更致命的是 ID 无法按时间排序，连"是不是数字"都保证不了。需要一个"按日期可排序"的系统，UUID 直接出局。

3票据服务器（Ticket Server）：一台专职取号机

解决什么问题：就要数字 ID，就要简单。做法：一台集中式数据库服务器专职发号，来一个请求就递增一位、发一个号，像银行老式的取号机。小系统里它确实简单可靠，出的也确实是数字 ID。

死穴是单点故障：取号机一挂，全系统都领不到号，业务停摆。而且在多服务器环境里同步本身就是难点。它赢在简单，输在命悬一线。

4Twitter Snowflake：把号切成五段

解决什么问题：前三种要么有中央协调，要么超宽无序。Snowflake 的回答是把 64 位 ID 切成五段，每段只负责一件事：

段位数干什么
符号位1恒为 0，可用于区分有符号数和无符号数
时间戳41自定义纪元（epoch）起的毫秒数。Twitter 默认纪元是 1288834974657，对应 UTC 2010 年 11 月 4 日 01:42:54。这一段保证 ID 按时间有序
数据中心 ID5最多标识 2^5 = 32 个数据中心
机器 ID5每个数据中心内最多 32 台机器
序列号12同一毫秒、同一台机器内自增，每毫秒最多 2^12 = 4096 个 ID；毫秒一过就归零

发号流程完全是本地的：看一眼当前毫秒 → 填进时间戳段 → 填上本机的机房号和机器号 → 序列号自增一格；同一毫秒内第 4097 个请求就只好等下一毫秒。机器之间零协调，为什么不撞号？因为任意两台机器要么时间戳不同，要么机房号/机器号不同，要么序列号不同——三个"不同"必居其一。原文给它三条优点：可扩展（多服务器上每秒处理 10,000+ 个 ID）、时间有序、去中心化（无单点故障）。

权衡与坑

这一讲的真话：
  • 整个方案建立在一个隐含假设上：各服务器的时钟是同步的。时钟一旦漂移甚至回拨（NTP 纠偏、虚拟机休眠都会触发），时间戳段会"往回走"，可能发出比旧 ID 还小的号。原文的对策是用网络时间协议（NTP）把时钟漂移压到最小——但"最小"不是"零"，回拨防护要自己补。
  • 五段长度是此消彼长的零和：序列号让位给时间戳，单机吞吐上限就降；机器位加多，时间戳位就短，纪元的可用年限跟着缩短。必须按场景调（原文叫"段长度调整"）。
  • 发号器是咽喉要道，挂了下游全瘫，所以高可用不是可选项：要有冗余和故障转移机制。
  • 回头再看三条落选路线，死穴各不相同：多主加减机器要重排步长、ID 还不保序；票据服务器是单点；UUID 超宽且完全无序。
记住 3 点
  • 唯一性来自分段：时间、地点、序号各占一段，机器之间零协调也不撞号。
  • 时间有序靠时间戳段，水平扩展靠机器本地发号——两头都想要，就别选中央协调。
  • 时钟是命门：NTP 校时、段长按场景调、发号器做冗余，三件事一件不能省。
