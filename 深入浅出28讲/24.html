对象存储：图书馆的合订本

S3-like Object Storage · 存天文数字的文件

一句话：存天文数字的文件，坏多少台机器都不许丢，还要越存越省——这就是对象存储的赌局：用性能换持久性、容量和成本。

规模：100 PB / 年 持久性：6 个 9（99.9999%） 可用性：4 个 9（99.99%） 对象数：约 6.8 亿个
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

合订本老图书馆订报纸：如果一张报纸用一个文件盒装，几年下来就是几亿个盒子，找一份报纸得翻天。图书馆的做法是把一个月的报纸按顺序装订成厚厚的合订本，再留一张目录卡片："某月报 · 合订本 B 架 · 第 42 页"。读者先翻卡片，再按卡片取本、翻到那页。合订本一旦装订就不能改页，错了只能换一本新的（不可变）。对象存储一模一样的路数：内容按到达顺序写进少数几个大文件，名字和位置记在目录卡片上，读的时候先查卡、再取本。

第一步 · 搞清问题

存储系统其实分三大类：块存储（Block storage）是裸设备（HDD、SSD），60 年代就有，服务器把原始块格式化成文件系统用；文件存储（File storage）盖在块存储上，提供文件夹和文件的抽象；对象存储（Object storage）走另一条路——牺牲性能，换高持久性、超大容量、低成本，面向"冷"数据（归档、备份），没有目录层级，数据平铺在扁平结构里，靠 RESTful API 访问。Amazon S3、Google GCS 都是这类。

要造的这个服务，需求是：存储桶（Bucket）创建、对象上传/下载、版本控制、列出桶里的对象。数字要跟面试官对齐：

  1. 容量：每年 100 PB；大对象小对象都要存得高效。
  2. 持久性：6 个 9（99.9999%）——100 万个对象里每年只允许丢 1 个。
  3. 可用性：4 个 9（99.99%）。
  4. 存储效率：可靠性和性能不降的前提下，成本越低越好。

瓶颈大概率出在磁盘容量和每秒 I/O 数（IOPS）上。粗算一笔账：一块 7200 转的 SATA 盘每秒只能做 100–150 次随机寻道；对象按大小分三档，取各档中位尺寸做估算：

对象档位占比中位大小说明
小对象20%0.5 MB（< 1 MB）量大，伤 inode 和磁盘块
中等对象60%32 MB（1–64 MB）主力档位
大对象20%200 MB（> 64 MB）适合分片上传

100 PB（10^11 MB）的空间按 40% 使用率摊下来，大约装 6.8 亿个对象；每条元数据 1 KB，光元数据就要 0.68 TB。也就是说：名字和内容必须分开存，否则账房比货仓还大。

第二步 · 画出大框架

动手前先看清对象存储的四个脾气：对象不可变——只能删或整体替换，不能改；本质是键值存储——对象的 URI 就是键，发个 HTTP 调用就能取内容；一次写入、多次读取——LinkedIn 的研究说 95% 的操作是读；大小对象通吃。这四点决定了后面所有设计。

它的理念和 UNIX 存文件如出一辙：inode 记文件名，数据块散在磁盘各处，先查 inode 再取内容。对象存储把这套拆成两家——元数据存储记"名字"，数据存储存"内容"，两家各自独立扩展。请求这样流转：

客户端→ 负载均衡器→ API 服务（无状态）→ IAM（认证授权）＋ 元数据存储（名字 → UUID）＋ 数据存储（UUID → 内容）

四个模块各司其职：负载均衡器把请求摊到服务的多个副本上；API 服务是无状态服务器，居中协调，对着元数据存储、数据存储和 IAM 三个后端发号施令；身份与访问管理（IAM）是认证、授权、访问控制的总闸；数据存储只认对象 ID（UUID），存取实际内容；元数据存储记桶和对象的信息。为什么 IAM 要独立出来？因为权限逻辑是所有请求的公共入口，独立成服务才能一处改、处处生效。

上传走 PUT /bucket-to-share/script.txt：API 服务先问 IAM"这人有没有写权限"，再把对象数据交给数据存储，拿到一个 UUID；最后调元数据存储，建一条含 object_id、bucket_id、桶名和其他元数据的新记录。下载更简单：先查 IAM 的读权限，再从元数据存储取 UUID，按 UUID 去数据存储捞内容返回。桶里没有真正的目录，但可以用"桶名/前缀/"拼出逻辑层级，假装有文件夹。

第三步 · 深入零件（按原文冲刺 1–2 的顺序）

1数据存储：路由、放置与数据节点

这一层要解决的问题：100 PB 的内容摊在几千块盘上，谁来决定一块新数据放哪台机器？怎么读回来？答案是把"指路"和"存货"拆开，再加一个"管账的"：

  • 数据路由服务（Data routing service）：对 API 服务提供 RESTful 或 gRPC 接口。它无状态，加机器就扩容。三件事：问放置服务"该存哪台数据节点"、从数据节点读数据、把数据写进数据节点。
  • 放置服务（Placement service）：决定某对象落在哪些节点上，手里握一张虚拟集群映射表（virtual cluster map）——集群的物理拓扑图；还定时向所有数据节点发心跳（heartbeat），把失联节点从映射表里摘掉。它是关键服务，要养 5 或 7 个副本的集群，用 Paxos 或 Raft 共识算法同步——7 节点可以容忍 3 个同时出故障。
  • 数据节点（Data node）：真正存数据的地方。每个节点跑一个守护进程，心跳里汇报两件事：我管着几块盘（HDD 或 SSD）、每块盘上存了多少数据。

写入的完整流程：API 服务把对象转给数据存储 → 路由服务发给主数据节点 → 主节点先落本地，再复制到两个次级节点，复制成功才返回 → UUID 回到 API 服务。两个细节值得记住：复制组用一致性哈希（consistent hashing）按 UUID 确定性地选出；主节点"先复制、后应答"，宁可慢一点也要强一致性——这是设计选择，不是碰巧。

2数据如何组织：把碎片装订成合订本

最省事的存法是一个对象一个文件。可行，但小对象一多就出事：文件系统的块通常 4 KB，一个 0.5 MB 的对象独占整块的零头，块被大量浪费；文件多意味着 inode 多，操作系统扛不住海量 inode，而且 inode 本身有数量上限。

解法就是合订本：预写日志（WAL，write-ahead log）把许多小对象顺次追加进少数几个大文件，一个文件写满几 GB 就换新文件。代价：对同一文件的写入必须串行化，多核同时写会互相等待——缓解办法是把文件绑到特定核上，错开写，避免锁竞争（lock contention）。

3对象查找：数据节点里的小账房

许多对象挤进一个文件后，新问题：怎么找到"对象 X 在合订本 B 的第几页"？需要一张映射表，每行四个字段：object_id、filename（在哪个文件）、file_offset（从哪个字节开始）、object_size。这张表可以放基于文件的 RocksDB，也可以放关系型数据库——因为访问模式是低写入、高读取，关系型数据库表现更好。

部署有两条路。独立部署：单独一个集群、独立扩展、所有节点共用——但要大力扩这个集群服务所有请求，而且数据节点到数据库之间多了一跳网络延迟。原文选了第二条路：把数据库塞进数据节点内部，因为节点只关心自己盘上的账，互不干扰；轻量的 SQLite 正合适。更新后的写入流程变成：对象追加到 /data/c 文件末尾，紧接着在映射表里插一行新记录——两步，缺一不可。

4持久性：副本不够，还要纠删码

6 个 9 的持久性意味着要审查每一种坏法。盘整个死掉好办，复制就行；真正阴险的是一次事故拖垮同一个故障域（failure domain）里的一片机器——同一机架、同一数据中心、同一张网。所以副本必须跨机架、跨数据中心、分离网络地摆。按 HDD 年故障率 0.81% 算，三份副本正好够到 6 个 9。

但三副本要 200% 的存储开销——存 1 PB 实际占 3 PB。于是请出纠删码（erasure coding）：像 RAID 一样加校验位，丢了几块能用剩下的算回来。用 8+4 方案：8 份数据 + 4 份校验，12 块盘散到不同故障域，挂 2 块（甚至按组合挂 4 块）都能重建。对比很干脆：复制开销 200%、纠删码只要 50%；纠删码能到 11 个 9 的持久性（Backblaze 的数据），复制是 6 个 9。代价也有三笔：读的时候要从多个位置收集数据，访问更慢；生成和存校验位要更多计算；实现难度高得多。原文的结论：延迟敏感的数据用复制，追求成本和持久性用纠删码。

5正确性校验：给每页纸做指纹

盘没死透，但存的某个区域悄悄坏了，这种半伤最难发现。办法是校验和（checksum）：文件内容的哈希值，读出来对不上就是坏了。原文为每个文件、每个对象都存一份校验和；8+4 纠删码下读一个对象，要把 8 份数据逐一取回、逐一验指纹，全对才拼内容。这也是纠删码读更慢的又一个原因。

6元数据数据模型：对象表怎么分片

元数据层要支持三种查询：按名字找对象 ID、按名字增删对象、按前缀列出桶里的对象。桶表（buckets table）很小——用户能建的桶数有限——单机装得下，但为了读吞吐还是要做扩展。真正头疼的是对象表：6.8 亿行，单机装不下，只能分片（sharding）。分片键 candidates 有两个：按 bucket_id 分，负载均匀，但大多数查询都带对象名/桶名，会被拖慢，而且同一桶的对象挤在一起反而制造了热点（一个桶可能有数十亿对象）；原文选了 hash(bucket_name, object_name)，因为查询大多基于名称。选它就要咽下后果：按前缀列对象这件事，变得更慢了。

7列出桶中的对象：用一张冗余表换列表速度

不分片时，按前缀列对象就是一句 SELECT * FROM object WHERE bucket_id = "123" AND object_name LIKE 'abc/%'。分片之后这句要广播到所有分片、在内存里聚合结果——而且分页难做：各分片命中的数量不同，得为每个分片维护各自的 limit/offset，拼页会拼错。

原文的取舍很果断：对象存储本来就不为"列目录"优化，牺牲列表查询的性能。再进一步：单独建一张反规范化（denormalized）的列表专用表，按 bucket_id 分片——列表查询被锁死在单个数据库实例里，速度立刻够用。数据冗余一份，换来一类查询从"全集群广播"变"单机秒杀"。

8对象版本控制：删除只是写了一条新记录

对象不可变，那"改"和"删"怎么办？答案：不删不改，只追加。版本控制靠一个 TIMEUUID 类型的 object_version 列实现，按它排序就是版本历史；每个新版本都生成一个新的 object_id。删除更妙：写一个新版本，object_id 特殊标记为"已删除"——查询碰到它就返回 404。数据其实还在，想恢复随时能捞回来。整条时间线就是一张只增不减的表。

9优化大文件上传：切块，各走各的

200 MB 的大对象一次 PUT，网络一抖就全重来。解法是分片上传（multipart upload）：客户端先发起分片上传，服务返回一个 upload_id；再把大文件切成若干分块，带着 upload_id 各自独立上传；每传完一块，数据存储返回一个 etag（该分块的 md5 校验和）；全部传完后客户端发"完成"请求，附上 upload_id、分块编号和全部 etag，数据存储据此把分块重新组装成对象——这一步可能要几分钟，完成后才应答。中途失败的分块、传完就作废的旧分块，都得有人收尸——这就引出下一个零件。

10垃圾回收：收尸、腾地、压实

垃圾有三种来源：惰性对象删除（只打了删除标记、数据还在盘上）、孤儿数据（传到一半放弃的分块）、损坏的数据（没通过校验和验证的）。垃圾回收器负责把它们占的地收回来，而且收得干干净净：复制方案下，主节点和副本节点要同步删；8+4 纠删码下，12 个节点全部要删——漏一个，持久性账就算不平。

真正腾空间靠压缩（compaction）：垃圾回收器把文件里还活着的对象从旧文件（data/b）拷进新文件（data/d），拷完用数据库事务更新 object_mapping 表，让指针指向新位置；旧文件整体删除。为避免越压越碎，文件长到超过一定阈值才触发压缩。这和 LSM-tree、HBase 的 compaction 是同一个思路：顺序写、后台整理、用空间换顺序。

权衡与坑

这一讲的真话：
  • 主节点"先复制、后应答"选了强一致性，就放弃了更低的写延迟——反过来选也成立，但要明说，别含糊。
  • WAL 合订本把随机写变成顺序写，代价是同文件写入必须串行，多核要靠"文件绑核"错开，锁竞争躲不掉只能拆。
  • 对象映射表独立成集群要扛住所有请求、多一跳网络延迟；塞进节点里用 SQLite，换来的是每节点一份小账、难以全局查。
  • 纠删码省 50% 开销、持久性更高，但读更慢、计算更贵、实现难得多——这不是免费的午餐。
  • 按 hash(bucket_name, object_name) 分片救了查询，坑了列表：前缀扫描要广播所有分片，只能再冗余一张反规范化表来补。
  • 分片上传留下的孤儿分块、删除标记留下的"僵尸数据"，不收尸就会悄悄吃掉你的容量预算。
记住 3 点
  • 对象存储 = 元数据 + 数据分家：名字查 UUID，UUID 取内容，两家各自水平扩展。
  • 小对象不要一对象一文件：WAL 顺序追加进大文件，映射表记账；持久性靠跨故障域复制，省钱靠纠删码（8+4，50% 开销）。
  • 不可变是底牌：版本控制、删除标记、分片上传、垃圾回收，全都是"只追加、后台收尸"这一种玩法变出来的。
