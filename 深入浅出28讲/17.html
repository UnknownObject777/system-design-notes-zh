附近好友：叮，朋友在你身边

Nearby Friends

一句话：好朋友走进你 5 英里内，你的手机立刻叮一声。位置每 30 秒更新一次，10 亿用户的手机都在实时对表——这一讲就是这张实时雷达网怎么织。

目标：10 亿用户，1 亿日活 附近：5 英里半径（可配置） 位置更新 QPS：33.4 万 pub/sub 转发：1400 万次/秒
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

晚自习教室晚自习，每个人都每 30 秒在教室后墙的小黑板上写下自己的座位号。值日生盯着黑板：谁的好友坐进了五排以内，就立刻给那个人递一张纸条。朋友多的，纸条递得多；朋友值日生全教室几百个座位，只负责跟自己熟的人对表。附近好友系统就是一间超大教室：黑板是位置缓存，递纸条是 pub/sub，值日生就是 WebSocket 服务器。

第一步 · 搞清问题

上一讲是"附近的位置"，位置基本不动；这一讲是"附近的好友"，位置每时每刻都在变。要解决的问题：用户开着 App，随时知道哪个好朋友正在自己附近、他多久前更新过位置。面试里要先问清几件事：多远算"附近"？答：5 英里，可配置。按直线距离还是绕路算？答：直线。多少用户？答：10 亿用户，10% 用这个功能，即 1 亿日活、1,000 万并发。要不要存历史位置？要，对机器学习有价值。不活跃的好友 10 分钟内消失行不行？行。GDPR 先不管，求简。

功能需求就两条：好友列表带距离和时间戳；列表每隔几秒刷新一次。

非功能需求也三条，但都很"实时"：低延迟（位置更新要快到人没走出两条街）、可靠性（丢一两个点没关系，系统别挂）、最终一致性（各副本差几秒可以接受，不要求毫秒级一致）。

规模估算，原文的数字：

项数值说明
附近半径5 英里可配置；直线距离
位置刷新间隔30 秒人步行慢，不用更频繁

第二步 · 画出大框架

为什么不能点对点（peer-to-peer）直连？手机网络忽断忽续，又省电优先，自己管连接不现实。所以要一个共享后端来扇出（fan-out）：收位置更新、找出谁该收到、距离超了就不发。

移动客户端→ 负载均衡器→ REST API 服务器/ WebSocket 服务器（有状态）→ Redis 位置缓存＋ Redis pub/sub→ 用户数据库＋ 位置历史数据库

分工的理由：REST API 服务器管杂事——加好友、改资料，传统请求-响应就够。WebSocket 服务器是有状态的长连接服务器，位置更新和推送都走它，它还在客户端初始化时"播种（seed）"附近好友的位置。Redis 位置缓存只存每个活跃用户的最新位置，条目带 TTL，过期即不活跃，天然限内存。Redis pub/sub是轻量消息总线，每个用户一个频道，谁的好友动了就广播给谁。位置历史数据库（如 Cassandra）专职记历史，供分析用，不参与实时路径。

一条位置更新的旅程：客户端 → 负载均衡器 → 它的 WebSocket 长连接 → 写位置历史库 → 更新位置缓存（服务器内存里也留一份，方便算距离）→ 往 Redis pub/sub 的本人频道发布 → 订阅了这个频道的好友们的服务器收到 → 算一遍距离，只把 5 英里内的转发出去。平均每人 400 个好友、10% 在线，所以每收一条更新要转发约 40 次。

WebSocket 侧有五条例程：周期位置更新、接收好友更新、初始化（发位置换附近好友列表）、订阅新好友、取消订阅（好友上线/下线时）。数据模型很轻：缓存里是 user_id → lat, long, timestamp 映射；历史表就这四列。

第三步 · 深入零件（按原文深入设计的 6 个小节）

1每个组件怎么扩

这解决"每个零件到千万并发还扛不扛得住"的问题。API 服务器最好办：自动扩缩组（autoscaling groups）加多复制几个实例。WebSocket 服务器横向扩也容易，但拆机器时要优雅：先在负载均衡器里标"排空（draining）"，不接新连接，等老连接走完再下线。客户端初始化是一条固定流水线：取好友 → 订阅他们的频道 → 从缓存读位置 → 转发给客户端。用户数据库按 user_id 分片，用户/好友数据最好包成专门的服务和 API，交给专门的团队。位置缓存多起几个 Redis 节点就能分片，TTL 同时给内存总量上了闸，但写入压力依旧大。Redis pub/sub用了一个关键事实：建好的频道没人订阅就不占内存，所以给所有用户预分配频道，免得"用户上线要新建频道并通知一堆服务器"这种连锁麻烦。

2Redis pub/sub 集群：真正的硬骨头

这解决"1400 万次/秒的推送，单机撑不住"的问题。频道内存约 200GB，两台各 100GB 的 Redis 就够装。但量才是问题：每秒约 1,400 万次推送，单机约 10 万次/秒，至少要 140 台 Redis 服务器，必须是分布式集群。集群靠服务发现组件（ZooKeeper 或 etcd）记录哪些服务器活着、哪个频道在哪台机器上；WebSocket 服务器把这份哈希环数据缓存在内存里省查询。扩缩容交给每日任务按历史流量执行，平时超量配置（overprovision）顶住峰值。Redis 集群在这里算有状态存储：频道要维护状态，扩缩时还得协调订阅者搬家。三个坑：大量重新订阅请求涌来；搬频道会漏掉少量位置更新（此场景可接受，但挑流量低谷操作）；用一致性哈希（Consistent Hashing）把搬走的频道数压到最小——第 5 讲的工具在这直接派上用场。

3添加 / 移除好友

这解决"好友关系一变，订阅关系跟着变"的问题。附近好友只是大应用的一个功能，好友事件发生时，移动客户端注册回调，主动向 WebSocket 服务器发消息：加好友就订阅对方频道，删好友就退订。逻辑很薄，但它是"社交图"和"实时管道"之间的接缝。

4好友很多的用户

这解决"少数大 V 拖垮个别服务器"的问题。先设上限：每人好友总数封顶，Facebook 的上限是 5000。"鲸鱼（whale）"用户所在的那台 WebSocket 服务器负载会偏高，只要服务器池够大、负载分得匀，就扛得住。别忘了第一步的估算正是从"400 好友"来的——上限护住了"人均 400 好友"这个估算假设。

5附近的随机陌生人

这解决面试官追问："能不能偶尔在地图上看到附近的陌生面孔？"做法：按 geohash 建一个 pub/sub 频道池，谁落在哪个 geohash 就订阅哪个频道，收这个格子里的陌生人位置更新。人在格子边界上怎么办？同时订阅相邻的几个 geohash，把跨界的情况兜住。格子越大越省订阅，噪音也越多，粒度是个权衡。

6Redis pub/sub 的替代方案：Erlang

这解决"不想被 Redis 集群的运维绑住"的问题。Erlang 天生为分布式设计：在一个分布式 Erlang 应用里同时开数百万个互相通信的小进程，WebSocket 连接和 pub/sub 频道用同一套模型搞定，省掉一层中间件。代价是人才：Erlang 太小众，招到好开发者不容易。技术选型，一半是选生态。

权衡与坑

这一讲的真话：
  • 1400 万次/秒的 pub/sub 转发是真正的瓶颈：至少要 140 台 Redis，单机方案直接出局。
  • 扩缩容期间会漏掉少量位置更新，只能靠挑流量低谷＋一致性哈希把损失压低，消灭不掉。
  • WebSocket 服务器有状态：下机器必须先"排空"，硬拔等于把连着的人踢下线。
  • 位置数据允许最终一致，所以能全走缓存和内存；换成本子一样要求强一致，这套设计就得重做。
  • "鲸鱼"用户和 geohash 边界是两个容易漏算的角落：负载均衡和跨界订阅都要提前想。
记住 3 点
  • 手机不适合点对点：共享后端扇出，WebSocket 管连接，Redis 管位置与广播。
  • 规模两笔账：写入 33.4 万 QPS × 转发 40 次 = 每秒 1,400 万次推送，集群加一致性哈希是必需品。
  • 位置数据只要求最终一致：TTL 缓存、允许丢点、挑低谷扩缩容——需求松一寸，设计轻一丈。
