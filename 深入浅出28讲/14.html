YouTube：视频的搬运与变身

Design Youtube · 视频上传、转码与流媒体分发

一句话：几亿人上传和看视频，关键是两件事——转码流水线把原始视频"变身"成各种规格，再精打细算省下 CDN 的钱。

20 亿月活跃用户（2020） 每天观看 50 亿个视频 假设：DAU 500 万 · 日存 150 TB CDN 成本：$150,000 / 天

先打个比方

快递总仓你开了一家全国性的大卖场。卖家把货寄到总仓，总仓把每件货重新打包成各种规格——小袋装、家庭装、礼盒装（这就是转码），再按销量分发：爆款铺进全国各地的分仓，买家就近取货，又快又省运费；冷门货留在总仓，谁下单谁发货。视频网站的玩法一模一样：上传是收货，转码是重新打包，CDN 是分仓，运费就是带宽账单。

第一步 · 搞清问题

这一讲要造的不是"能放视频的网站"，而是一个能同时伺候上传和观看两头的巨型系统。设计目标有五条：上传速度快、播放流畅、能切画质、基础设施成本低、高可用高可靠。

先看它有多大（2020 年的数据）：20 亿月活跃用户，每天观看 50 亿个视频，37% 的移动互联网流量来自 YouTube，支持 80 种语言，2019 年广告收入 151 亿美元。规模一上来，最贵的东西立刻显形：带宽。

再做一组估算假设，把成本算出来：

假设数值说明
日活跃用户（DAU）500 万系统设计的估算基准
平均视频大小300 MB—
单个视频上传上限1 GB—
每日新增存储150 TB原始视频进 Blob 存储
CDN 成本估算$150,000 / 天500 万 × 5 个视频 × 0.3 GB × $0.02（按 Amazon CloudFront 计价）

最后一行是全场最刺眼的数字：一天 15 万美金的 CDN 账单。所以这一讲的一半篇幅，其实都在回答"怎么把这笔钱省下来"。

第二步 · 画出大框架

对照原文的高层架构图，七个组件各司其职：

客户端（手机 / 电脑 / 电视）→ API 服务器（上传与元数据）→ 原始存储（Blob）→ 转码服务器群→ 转码后存储→ CDN→ 观看端
API 服务器 → 元数据数据库（标题、描述、大小）

分工的逻辑很朴素：视频流本身不经过 API 服务器——播放直接从 CDN 拉，API 只处理"除了看视频以外的一切"：上传请求、元数据更新。数据分两类走两条路：视频文件进 Blob 存储，元数据进数据库，两者并行，谁也不等谁。

上传的完整链路：视频先进原始 Blob 存储，转码服务器把它转成多种格式；转码一完成，兵分两路——转码后的视频送去转码后存储、再分发到 CDN；同时"转码完成"事件进入完成队列（completion queue），完成处理器（completion handler）据此更新元数据、通知用户"你的视频可以看了"。元数据上传也是并行的：客户端同时发请求，带上文件名、大小、格式。

播放链路更短：视频通过边缘服务器（edge server）直接从 CDN 传输，延迟最低。流媒体协议有好几种——MPEG-DASH、Apple HLS、Adobe HDS，不同协议支持不同的视频编码和播放器，所以转码才要一种视频转出多种格式。

第三步 · 深入零件（按原文第 1–12 节的顺序）

1视频转码：为什么要"变身"

原始视频为什么不能直接发？三个理由：省存储——原始文件太大，转码压缩后省空间；保兼容——手机、电视、浏览器各有各的脾气，一种格式喂不饱所有设备；适配网速——Wi-Fi 上看 4K、地铁里看 480P，画质要跟着网络状况走。转码是上传后必经的第一道工序。

2容器与编解码器：视频文件的两层结构

拆开一个视频文件，里面是两样东西。容器（Container）像包装盒，把视频、音频、元数据封在一起，比如 MP4、AVI；编解码器（Codecs）是压缩和解压缩的算法，比如 H.264、VP9。盒子决定能不能装，算法决定压得多狠、画质剩多少——转码就是换盒子、换算法的组合。

3有向无环图（DAG）模型：把一道大工序拆成流水线

转码在计算上又贵又慢，一个视频从头压到尾要好几个小时。解法：有向无环图（DAG, Directed Acyclic Graph）。它把编码、缩略图生成、水印这些任务画成一张依赖图——谁先谁后、谁能并行，一目了然，视频处理因此可以高度并行。原始视频先被拆成视频、音频、元数据三路：视频送去编码（转成分辨率、编解码器、比特率各不相同的版本），缩略图可由用户上传也可系统自动生成，水印则是叠在画面上的身份标识。

4预处理器（Preprocessor）：先切小块，再排工序

流水线的第一道工位，管四件事。视频拆分：把视频流按画面组（Group of Pictures, GOP）对齐切成更小的片段——GOP 对齐是为了让每个片段都能独立解码；旧客户端也按 GOP 对齐来拆。生成 DAG：它根据客户端程序员写的配置文件生成任务图，流水线排产不是写死的。留后手：GOP 和元数据存进临时存储，万一编码失败，系统拿这些持久化的数据重试，不用从头再来。

5DAG 调度器（DAG Scheduler）：排产的工段长

它把 DAG 图拆成一个个任务阶段，丢进资源管理器的任务队列。阶段 1 先分出视频、音频、元数据；到了阶段 2，视频再拆成两个并行任务：视频编码和缩略图生成。调度器不管"谁来干"，只管"先干什么、后干什么、什么可以一起干"。

6资源管理器（Resource Manager）：派活的调度室

它负责资源分配的效率，手下是三个队列加一个调度器：任务队列（待执行任务的优先队列）、工作进程队列（各工作进程利用率信息的优先队列）、运行队列（正在运行的任务和执行它的工作进程）；任务调度器从队列里挑最优的任务/工作进程配对，指挥被选中的工作进程开工。哪台机器空、哪个任务急，都在这里算清楚。

7任务工作进程、临时存储与输出：干活的和暂存的

任务工作进程（Task Workers）是真正执行转码的工人，不同的工人跑不同的任务。临时存储放重试要用的中间数据——选哪种存储系统，取决于数据类型、大小、访问频率和生命周期。输出就是包装完毕、随时可以分发到 CDN 的转码后视频。

8速度优化一：并行上传，断点续传

上传慢是用户流失的头号原因。把大视频拆成小块并行上传，传得更快；某一块失败了只重传那一块，天然支持断点续传——1 GB 的视频传了一半断网，不用从头再来。

9速度优化二：就近上传与消息队列

两条。其一，分布式上传中心：用离用户近的 CDN 节点当上传入口，视频少跑半程冤枉路。其二，并行处理：各环节用消息队列（Message Queue）解耦——存储、转码、通知各干各的，一个环节不用等另一个环节，整条流水线高度并行，突发流量也被队列接住慢慢消化。

10安全优化一：预签名 URL（Pre-Signed URLs）

上传入口必须验明正身。服务端给授权用户签发一个带过期时间的预签名 URL，用户拿着它直接往 Blob 存储传视频——没签名的请求一律拒之门外。好处是上传流量绕开 API 服务器直进存储，还天然带了权限和时效双保险。

11安全优化二：视频保护的三件套

防盗版三招并用：DRM 系统（数字版权管理），例如 Apple FairPlay、Google Widevine，按平台和播放器各配各的；AES 加密，内容本身加密传输和存储；水印，把身份标识烙在画面上，泄露了能追到人。

12成本节约：从 $150,000 里抠钱

针对第一节那张天价账单，原文给了四记组合拳：只让热门视频走 CDN，冷门视频由高容量服务器直接提供，CDN 流量瞬间瘦身；冷门视频按需编码，没人看的视频不提前转码，省存储省算力；按地区分发，根据热度把视频拷到离观众近的地方；自建 CDN 并与 ISP 合作，绕开 CloudFront 的零售带宽价，把最大的那块成本打下来。

权衡与坑

这一讲的真话：
  • CDN 是最贵的零件：每天 $150,000，比存储贵一个量级——架构的大半决策都是围绕"少让 CDN 干活"做的。
  • 只让热门视频走 CDN，意味着长尾视频要看运气：回源播放的延迟和体验，就是省下来的那笔钱。
  • 转码计算昂贵又耗时，但拆得越碎并行度越高、失败重试越便宜——GOP 对齐和临时存储是给流水线上的保险，省不得。
  • 错误处理分两类：可恢复错误（上传、转码、资源分配失败）就重试；不可恢复错误（视频损坏）停止处理、返回错误码——别对着坏文件无限重试。
  • 安全是乘法不是加法：预签名 URL 管上传入口，DRM / AES / 水印管内容本身，少一环就漏。
记住 3 点
  • 上传两条线并行：视频进 Blob 存储，元数据进数据库；播放只认 CDN，API 服务器不碰视频流。
  • 转码是一座流水线工厂：GOP 切块 → DAG 排产 → 资源管理器派活 → 工作进程并行干，失败靠临时存储重试。
  • CDN 账单决定架构：热门走 CDN、冷门回源、没人看的不预转、最终自建 CDN 联手 ISP——省钱就是设计。
