信息流：朋友圈怎么送达

News Feed System

一句话：你发了帖子，好友的动态页怎么立刻出现它。发出去只是存一条数据，难的是把它"扇出"到几千个好友的首页——这一讲拆解 Facebook / Instagram / Twitter 时间线背后的两条流水线。

规模：1000 万日活（DAU） 好友上限：5,000 人 排序：逆时间序 缓存：五层分工
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

小区公告栏你写了一则便条，交给小区物业（发帖）。物业把它复印成很多份，贴到每位好友楼下的公告栏上（扇出）——这叫"送上门"。早高峰大家出门，顺手看一眼自家公告栏最新的几条，就是刷信息流。可小区里有一位大明星，几万粉丝都贴满？物业会贴不起。于是对明星只在他自己楼下贴一份原件，谁想看谁自己跑一趟（拉取）。整个新闻流系统，就是把"复印贴条"这件事做成每秒几万次还不出错的工程。

第一步 · 搞清问题

目标是设计一个信息流系统（News Feed System）：持续展示来自社交关系的更新（状态、照片、视频、链接），比如 Facebook 的信息流、Instagram 的信息流、Twitter 的时间线。面试里先把需求钉死：

  1. 平台：Web 端和移动端 App 都要支持。
  2. 功能：用户能发帖子；用户能在自己的信息流里看到好友发的帖子。
  3. 排序：为了简单，按逆时间顺序（reverse chronological order）排，新的在前。
  4. 内容：帖子里可以带文本、图片和视频。

规模假设：

指标假设
日活跃用户（DAU）1000 万
单个用户好友上限5,000 人
排序方式逆时间序
帖子内容类型文本 / 图片 / 视频

注意这个数字组合有多狠：一个用户发帖，理论上要触达最多 5,000 个好友的首页。日活千万意味着"刷"的请求量是"发"的很多倍——这个不对称，直接决定了后面的架构走向。

第二步 · 画出大框架

高层设计里有两条独立的流水线：一条负责"发"（写入），一条负责"刷"（读取）。先把它们分开，是这一类系统最重要的直觉。

流水线一：信息流发布（Feed Publishing）——你点了"发布"之后：

用户→ 负载均衡器→ Web 服务器（认证）→ 帖子服务→ 数据库 + 缓存→ 扇出服务 → 好友的信息流缓存→ 通知服务

流水线二：信息流构建（News Feed Building）——你打开 App 刷新时：

用户→ 负载均衡器→ Web 服务器→ 信息流服务→ 信息流缓存（拿帖子 ID）→ 数据库 / 缓存（拿帖子详情）

两条流水线靠 API 划界：发布走 POST /v1/me/feed（参数是 content 和身份令牌 auth_token），检索走 GET /v1/me/feed。为什么要分成"扇出写入"和"按 ID 现取"两段？因为读的频率远高于写：把"组装好友帖子"的活提前在写入时干完，读取时就只剩一次缓存查找——用写方的成本，换读方的速度。扇出服务（Fanout Service）和五层缓存，就是为这个分工而生的零件。

第三步 · 深入零件（按原文顺序）

1Web 服务器：先验身份，再掐垃圾

这是发布流水线的第一道门，解决"这请求可信吗"的问题。两件事：用 auth_token 对发帖人做身份认证；然后实施速率限制（rate limit），防止有人刷垃圾信息把扇出服务打爆。认证和限流放在 Web 层，后面的服务就能假定进来的请求都是干净、有主的。

2扇出服务：推，还是拉？

这是本讲的灵魂问题：你发的帖子，什么时候出现在好友的信息流里？三种方案，各有取舍：

  • 写时扇出（Fanout on Write）：发帖那一刻，就推送（push）到所有好友的信息流缓存。优点：实时更新，刷的时候检索飞快。缺点：好友多的用户发帖，资源开销巨大——大明星一条帖子要写入几万份缓存。
  • 读时扇出（Fanout on Read）：发帖只存一处；好友刷新时，才现拉（pull）他关注的人的帖子，现场聚合。优点：不活跃用户不占资源，发帖零扇出成本。缺点：信息流检索慢，刷一次要现场算。
  • 混合方案（Hybrid Approach）：大多数普通用户用推送模型；对拥有大量社交连接的用户（名人、大 V）改用拉取模型。这是大型社交网络的实际选择——把贵的操作留给少数能扛的人。

3扇出的五步流水线：一份帖子如何复制五千份

扇出服务具体怎么干活？原文给了一条五步流水线：

  1. 获取好友 ID：从图数据库（graph database）里检索发帖人的好友列表。
  2. 从缓存中过滤好友：查缓存里的用户设置，排除被屏蔽的好友、或按个人分享偏好不该看到的人。
  3. 发送到消息队列：把过滤后的好友列表连同新帖子的 ID 一起丢进消息队列（message queue），异步处理。
  4. 扇出工作进程（Fanout Workers）：工作进程从队列取出任务，更新信息流缓存。关键细节：缓存里存的是 <post_id, user_id> 映射，不是完整的用户对象和帖子对象——为了省内存。
  5. 存储到信息流缓存：把新帖子 ID 追加到每位好友的信息流缓存里。并且设一个可配置的上限，只保留最近的帖子——大多数用户只看最新内容，这样内存消耗始终可控。

注意这里三个"为什么"：为什么要消息队列？发帖不能等五千次写缓存完成，入队即返回，削峰又解耦。为什么只存 ID？一份帖子详情几 KB，五千万份就是灾难，ID 只有几个字节。为什么设上限？信息流本质是"只看最新"，老帖子留在数据库，缓存只留热的那截。

4信息流检索与五层缓存：各存各的，互不抢道

读取侧（刷信息流）的性能，几乎全靠缓存架构撑起来。原文把它分成五层，每层只干一件事：

缓存层存什么为什么单独一层
信息流缓存（News Feed Cache）帖子 ID 列表刷信息流先拿 ID，最快
内容缓存（Content Cache）帖子详情，热门帖子放热缓存按 ID 批量取详情，不碰数据库
社交图谱缓存（Social Graph Cache）用户关系数据扇出时要反复查好友关系
操作缓存（Action Cache）用户操作：点赞、回复、分享高频写，单独缓存缓冲
计数缓存（Counter Cache）点赞数、回复数、粉丝数数字更新极频繁，不能每次写库

刷一次信息流的真实路径：信息流服务先从信息流缓存取回一页帖子 ID，再拿这批 ID 去内容缓存（和数据库兜底）取详情，拼装返回。五层分家的理由和第 1 讲的缓存道理一致：访问模式不同、失效策略不同，混在一起就会互相污染。

5关键优化：跑得快、扛得住、看得见

原文最后给了一盘"锦上添花"的优化清单，分四类：

  • 扩展性：数据库水平扩展和分片（sharding）；用只读副本（read replica）扛高流量的读查询；Web 层保持无状态，随便加减机器。
  • 缓存：频繁访问的数据放内存；用多层缓存降延迟、减轻数据库负担。
  • 可靠性：用一致性哈希（Consistent Hashing）把请求均匀分到各服务器；消息队列解耦组件、缓冲突发流量。
  • 监控：盯 QPS（每秒查询数）和延迟；盯缓存命中率，低了就该调配置。

这四类没有一项是"新零件"，全是前 10 讲的工具在这里落地：分片和无状态来自第 1 讲，一致性哈希是第 5 讲，消息队列、限流、监控也各有专章。信息流系统的难点不在零件新，而在把它们缝成两条不互相拖累的流水线。

权衡与坑

这一讲的真话：
  • 纯推送模型对大明星用户是灾难：一条帖子扇出几万份缓存，写时扇出（Fanout on Write）的成本和好友数成正比。
  • 纯拉取模型对活跃用户是折磨：每次刷新都要现场聚合，读时扇出（Fanout on Read）的检索速度上不去。
  • 混合方案不是免费午餐：同一条信息流里，普通好友的帖子是推来的、名人的帖子是拉来的，两套逻辑要在一页里合并排序，复杂度转移到了读取侧。
  • 信息流缓存只存 <post_id, user_id> 且只留最近一段——一旦上限、失效策略没调好，用户会看到"信息流断层"，而数据库本身没问题。
  • 过滤（屏蔽、隐私偏好）必须在扇出前做完：先扇出再删，等于白写几千份缓存。
记住 3 点
  • 信息流系统拆成两条流水线：发布（写时扇出）和构建（按 ID 现取）——用写方的成本，换读方的速度。
  • 扇出没有完美方案：普通人用推（Fanout on Write），名人用拉（Fanout on Read），混合落地。
  • 缓存存 <post_id, user_id> 映射，五层分工——内存寸土寸金，别让完整对象进信息流缓存。
