面试四步走

System Design Framework · 系统设计面试框架

一句话：45 分钟里按固定四步答题：范围 → 高层 → 深挖 → 总结，不慌不忙不跑偏。题目再陌生，套路是熟的。

全程：45 分钟 路线：4 步框架 深挖阶段：10–25 分钟，弹性最大
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

看病好医生看病从来不是上来就开刀。先问诊：哪里不舒服、多久了、吃过什么药——把病情问清楚；再给初步判断和检查方案，和病人商量着定；确认之后才动真格的治疗，专攻要害；最后开医嘱：注意什么、什么时候复查、严重了怎么办。系统设计面试一模一样的四步：问诊、定方案、下刀、开医嘱。跳过任何一步，病人（面试官）心里都会打鼓。

第一步 · 搞清问题

这一讲解决的不是"某个系统怎么设计"，而是一个更前置的问题：面对一道模糊的开放题，45 分钟怎么花才不翻车？系统设计面试模拟的是真实工作场景：题目故意没说清，考的不只是技术，还有协作、沟通和处理模糊需求的能力。所以第一个要治的毛病是抢跑——题目刚听完就画框图，方向错了越画越亏。

第一步的任务：把模糊的题目逼成清晰的需求。做法是两个动作：

  1. 提澄清问题（Clarifying Questions）：最重要的功能是什么？系统要支撑多大的规模？面向 Web、移动端还是两者？有没有已有的技术选型或约束？问题问得好，本身就是批判性思维的展示，不露怯，反而加分。
  2. 记录假设（Assumptions）：把商量出来的假设写在白板或纸上，后面每一步都对照着用，免得自己推翻自己。

原文给的示范是"设计一个信息流系统"，连问四句：是移动应用、Web 应用还是两者？一个用户可以有多少好友？信息流里要不要包含图片和视频？按不按时间倒序排列？同一个"信息流"，四个答案不同就是四道不同的题。

开答之前，先把 45 分钟的时间账摆出来——这就是本讲唯一的"估算"：

阶段建议用时干什么
理解问题、确定范围3–10 分钟问澄清问题，写假设
高层设计、获得认可10–15 分钟画方框图，走查用例
深入设计10–25 分钟攻关键组件，谈瓶颈
收尾总结3–5 分钟回顾决策，指出改进方向

注意第二步和第三步之间是弹性地带：面试官点头快，深挖就多给时间；高层设计就被挑战，就得回头补。

第二步 · 画出大框架

需求清楚了，先别抠细节。用方框图把关键组件摆出来——客户端、API 服务、数据库、缓存、CDN——让面试官一眼看到数据从哪进、到哪去：

客户端（Web / 移动端）→ API 服务→ 缓存 / CDN/ 数据库

拿原文的信息流系统来说，高层设计可以再拆成两条流程：发布流程——把帖子写进数据库，并填充好友的信息流；拉取流程——把好友的帖子聚合起来，按时间倒序展示。两条线分清楚，后面深挖才知道挖哪里。

这一步还有两个动作，同样不能省。一是做粗略估算（Back-of-the-Envelope）：用第 2 讲那套信封背面的算法，确认这个框图装得下题目给的规模约束，别把只能撑一万人的设计画给一亿人用。二是走查用例（Walk-through）：挑一两个典型场景从图里走一遍，把边界情况翻出来，顺便验证自己的假设站得住。每画一块，都回头问一句面试官"这样合理吗"——把面试官当队友，而不是考官，框架图画完时，方向应该已经达成了共识。

第三步 · 深入零件（深挖 · 最佳实践 · 时间管理）

1深入设计：先攻关键组件

第三步是全场的主战场（10–25 分钟都花在这里）。原则只有一条：聚焦与问题最相关的组件，而不是平均分力。每个题目有自己的"题眼"：URL 短链服务，重点谈哈希函数怎么设计；聊天系统，重点谈怎么降低延迟、怎么处理在线/离线状态；信息流系统，就回到第二步拆好的两条线，深挖发布与拉取流程。题眼挖得深，面试官才看得见你的深度和适应性。

2深入设计：谈瓶颈，也懂收手

挖细节时要主动讨论瓶颈：哪里可能出现性能问题，对应的解法是什么——是加缓存、加队列还是分片。但另一半同样重要：把握细节的分寸。面试官要的是实用、可扩展的方案，不是处处镀金。一个无关紧要的组件展开十分钟，只会挤掉收尾的时间。能深挖，也能判断哪里不该深挖，这本身就是判断力。

3最佳实践 · 该做的（Dos）

原文给了一份"应该做"的清单，五条：

  • 提出问题：钻进解决方案之前，先把歧义澄清掉。
  • 积极沟通：思考过程说出来，让面试官跟着你的思路走。
  • 反复迭代：把面试官当协作者，根据他的反馈不断修设计。
  • 展现灵活性：主动给替代方案，比较优劣，而不是一条路走死。
  • 聚焦关键组件：时间有限，火力集中在系统的核心部分。

4最佳实践 · 不该做的（Don'ts）

反面清单更短，但条条致命：

  • 避免过早给方案：需求还没理解就动手设计，方向错了全部白搭。
  • 不要沉默：闷头画图不吭声，面试官无法给你的思考过程打分。
  • 避免过度设计：方案要实用、可扩展，不是零件堆得越多越好。

5时间管理：给每一步上闹钟

s1 那张时间表真正用起来，靠三个心锚：10 分钟时，澄清问题该问完了，假设该写下来了；15 分钟时，方框图该画完、共识该拿到，面试官摇头就得立刻回头补；25 分钟是深挖的警戒线，一到点就要往回收，把最后 3–5 分钟留给收尾。时间管理的本质是按阶段推进：当前阶段的任务没做完，宁可砍范围，也不带着烂尾进下一阶段。

权衡与坑

第四步收尾，很多人不当一回事，其实它是白捡的分。做三件事：总结设计——把主要的设计决策和取舍复述一遍；识别瓶颈——坦承系统还有什么限制；指出改进方向——比如这套设计从 100 万用户扩到 1000 万用户要怎么走，服务器故障、网络出问题时靠什么错误处理机制兜底。说完这些，面试才是一个有头有尾的闭环。

这一讲的真话：
  • 最大的坑是抢跑：需求没问清就画框图，画得越快，错得越远。
  • 第二大坑是镀金：过度设计等于告诉面试官你分不清主次。
  • 沉默是最隐蔽的坑：不说话，再对的答案也拿不到过程分。
  • 时间失控几乎都发生在深挖阶段——没有"25 分钟必须收尾"的闹钟，就没有收尾。
  • 框架不是死顺序：面试官打断你追问细节时，要敢于跳步再回来，别死守流程图。
记住 3 点
  • 先问清楚再动手：澄清问题是加分项，不是露怯；假设写下来，全程照着走。
  • 先拿认可再深挖：方框图达成共识之前，一毫米细节都别展开。
  • 给收尾留 3–5 分钟：复述决策、指出瓶颈、给出 100 万到 1000 万的路。
