从一台电脑到一百万用户

Scaling · 从零扩展至百万级用户

一句话：一个小网站怎样一步步长大，伺候得了一百万个用户。这一讲是全套课程的总路线图：后面 27 讲的每个零件，都会在这条路上找到位置。

目标：百万级用户 路线：12 级台阶 关键词：负载均衡 · 缓存 · CDN · 分片
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

小吃摊你开了一家小吃摊：一个人又炒菜又收钱又记账。客人多了，先把炒菜和记账分两个人；再多了，开分店，门口站个指挥员把客人分流到空摊位；菜谱印好散发到各分店；账本原本自己抄几份；最后开遍全城，还有中央厨房统一配菜。网站长大，完全一样的路数。

第一步 · 搞清问题

这一讲不是"一上来就设计一个百万级系统"，而是回答一个更真实的问题：用户从 1 个涨到 1,000,000 个的路上，会依次撞到哪几堵墙？每堵墙该怎么翻？

成长路上的四堵墙，按出现的顺序：

  1. 机器跑不动——用户太多，一台服务器的 CPU 和内存不够了（计算瓶颈）。
  2. 数据库成瓶颈——所有数据都存在一台机器上，读写都挤它（数据瓶颈）。
  3. 读不过来——典型网站读多写少，数据库被"看"压垮，而不是被"写"压垮。
  4. 又远又大——全球用户离服务器太远（延迟高）；数据大到一台机器存不下（容量上限）。

所以设计目标就是：每撞一堵墙，加一类零件，而且尽量不改写程序——一次解决一类问题，步步为营。

第二步 · 画出大框架

把 12 级台阶压成一张成长地图，数据（用户的请求）这样流动：

用户→ 负载均衡器→ 无状态的 Web 服务器 ×N→ 缓存/ CDN/ 消息队列→ 数据库（主从 → 分片）

读请求优先命中缓存和 CDN（最快），拿不到再走数据库；写请求进主库；慢任务丢进消息队列慢慢做；数据库从"一主一从"逐步走到"多片集群"。每一步什么时候引入，就是第三步的内容。

第三步 · 深入零件（按原文第 1–12 节的顺序）

1单服务器：一切挤在一台机器里

最开始：Web 程序、数据库、缓存全在一台机器上。用户通过域名找到 IP，DNS 是电话簿。这阶段谈"架构"没意义，因为所有请求都流向同一台机器——它就是全系统的单点。

2数据库分离：第一件事是分家

用户一多，程序和数据库互相抢资源。解法也最直接：两台机器，一台只跑 Web 程序，一台只存数据。两边从此可以各自升级、各自扩，互不拖累。这是所有扩展的第一步。

3垂直扩展 vs 水平扩展：选方向

垂直扩展＝给一台机器加内存换更好的 CPU，像把小吃摊扩成大酒楼。简单，但单个机器有上限，而且越到顶配越贵。水平扩展＝加更多普通机器，像开连锁分店。便宜、上限高，但复杂——多了一台机器，就多了"谁来分发流量""状态存哪里"这些新问题。大系统的方向永远是水平扩展，接下来十一步都是在给水平扩展打补丁。

4负载均衡器：门口的指挥员

多台 Web 服务器前面放一个负载均衡器，把流量均匀分下去；哪台病了，就把它从名单里摘掉，客人自动去别家。没有它，加再多服务器也只有一个入口，瓶颈依旧。它还顺便提供了 SSL 终结、安全防护这些门口服务。

5数据库复制：一本真账，多本复印

读请求远多于写请求，那就把数据库复制成多份：主库只负责写，从库负责读——读写分离。从库越多，读的能力越强；某台从库挂了，读流量去别台，系统无感。主库挂了麻烦些：要从从库里选一个新"真账"（故障转移）。大多数网站走到这一步，读压力就基本解了。

6缓存：把最热的数据放在手边

二八定律：80% 的读集中在 20% 的数据上。把这 20% 放进内存缓存（比如 Redis），读请求大部分不再碰数据库。要点有四个：哪些数据值得缓存（读多写少的）、过期时间怎么设（缓存不是越新越好，是有策略地失效）、缓存击穿怎么办（查不存在的数据也缓存一个"空"）、缓存和数据库不一致怎么办（写操作后删掉对应缓存）。缓存服务器也要做复制和分片，否则它自己成了单点。

7CDN：把静态内容搬到用户家门口

图片、视频、CSS、JS 这些静态文件不常变，复制一份放到分布各地的 CDN 节点。用户访问时，DNS 把他指到最近的节点，延迟大幅降低，源站流量大减。内容更新时，通过 CDN 的失效接口刷新对应文件。

8无状态 Web 层：让服务器"不记事儿"

水平扩展的隐形障碍是"状态"：如果登录信息存在某台 Web 服务器的内存里，那台机器对用户就不可替代——这正好违背了"随便加机器"的初衷。解法：把会话（session）之类的状态从 Web 层搬出去，放进所有机器都能访问的共享存储（比如 Redis）。从此 Web 服务器随便加减，请求落到哪台都一样——这也是自动化扩容的前提。

9多数据中心：开分店到别的城市

一个机房会停电、会断网。跨城市部署多个数据中心，用 GeoDNS 把用户路由到最近的健康中心。代价是新问题：用户在两个中心之间移动时数据要同步，而同步有延迟——多副本数据的一致性策略（第 6 讲细讲）在这里第一次变得绕不开。

10消息队列：让慢任务排队等

有些操作慢且不急：比如照片 App 上传后要重新缩放图。让 Web 服务器把任务写进消息队列就立刻返回"上传成功"，后台的消费者慢慢处理。效果有三：解耦（发布者和处理者互不认识）、削峰（突发流量进队列排队，不被压垮）、异步（用户不用等慢操作）。

11日志、指标与自动化：给系统装上仪表盘

机器多了以后，"系统现在健不健康"本身成了难题。三件套：错误日志（哪个接口老报错）、服务器指标（CPU、内存、QPS）、自动化（负载高了自动加机器、出故障自动重启）。没有可观测性，前面十步堆出来的系统就是盲飞的飞机。

12数据库扩展：最后的硬骨头

前面的招都用完，数据还是大到一台机器装不下，只剩两条路。垂直分片：按功能拆库，用户库、商品库各回各家，简单但同类数据还是会涨爆。分片（Sharding）：把同一张表按规则切开，比如按用户 ID 取模分到 16 台机器。分片引入一堆新麻烦：分片键选不好会数据不均；大明星用户的数据全挤在一片上（名人问题）；跨片的 JOIN 做不了，得提前把数据反规范化（冗余一份）。所以它是最贵的一步，能晚则晚。

权衡与坑

这一讲的真话：
  • 缓存和数据库是两本账，必然有一致性窗口；缓存集群自己也会成为新的单点。
  • 分片之后再想换分片键，等于把图书馆重新搬一次家——分片键的选择几乎不可逆。
  • 名人问题：10 万粉丝的大 V 发一条动态，若数据全在一片，那一片就会被拖垮。
  • 每加一层零件，运维复杂度就涨一截；不是所有系统都需要走完全部 12 级台阶。
记住 3 点
  • 扩展的顺序：分离 → 水平加机器 → 读写分离 → 缓存/CDN → 无状态 → 多机房 → 分片。
  • 水平扩展的前提是无状态：状态搬出去，机器才能随便加减。
  • 每步只解决一类瓶颈，别一上来就分片——那是最后的硬骨头。
