酒店预订：最后一间房归谁

Hotel Reservation System

一句话：抢订最后一间房，绝不能让两个人同时订到，还允许适度超售。这一讲的难点不在流量有多大，而在并发之下账本必须分毫不差——订出去的房间，一间也不能多。

规模：5000 家酒店 · 100 万间客房 预订：日均约 24 万笔 · 平均 TPS≈3 库存表：约 7300 万行 超售上限：110%
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

演唱会抢票热门演唱会开票那一刻，十万人同时点"购票"。售票网站要办三件事：先告诉你还有没有票；你点下去的一瞬间把名额扣下来，别人就抢不到了；你网卡连点十次，也只出一张订单。酒店预订一模一样，只是"票"变成了"某家酒店、某种房型、某一天的一间房"。而且剧院为了对付退票，敢多卖 10% 的票——这就是超售。这一讲讲的，就是让这套动作在高并发下不出错。

第一步 · 搞清问题

这一讲要设计的，是一个类似万豪国际（Marriott International）的酒店预订网站。同一份设计也适用于 Airbnb、机票预订、电影票预订——凡是要"把有限的座位卖给大量并发用户"的系统，骨架都相通。

设计前先向面试官澄清范围，原文的对话浓缩成六条：

  • 规模：5000 家酒店，共 100 万间客房。
  • 付费：预订时全额付款，不是到店再付。
  • 渠道：只有网站和 App，不支持电话。
  • 取消：允许。
  • 超售：允许超售 10%——酒店预期有客户会取消，所以故意多卖。
  • 聚焦范围：酒店页面、客房详情、预订、管理后台，外加支持超售；房价每天都在变。

非功能需求两条：旺季要能扛住高并发——大量客户同时抢同一家酒店；延迟中等即可——预订最好快，但系统花几秒钟处理也能接受。

粗略估算，把直觉变成数字：

指标数字怎么算
日预订量约 24 万笔100 万间 × 70% 入住率 ÷ 平均入住 3 天
平均预订 TPS约 324 万 ÷ 一天约 10⁵ 秒
预订页浏览约 30 QPS每步转化率 10%，3 步漏斗
客房详情页浏览约 300 QPS预订页浏览 × 10

看出来了吗？平均 TPS 只有 3，这个系统的难点从来不在"量"，而在"对"——平均闲着，旺季扎堆，而扎堆的时候最后一间房绝不能卖给两个人。

第二步 · 画出大框架

高层设计选了微服务架构。请求这样流转：

用户 / 管理员→ CDN（静态资源）→ 公共 API 网关（限流 · 鉴权）→ 酒店服务/ 房价服务/ 预订服务（管库存）→ 支付服务

每个服务为什么单独存在：

  • 酒店服务（Hotel service）：提供酒店和客房详情。这类数据基本不变，可以激进地缓存。
  • 房价服务（Rate service）：提供未来每天的价格。单拆出来，因为价格每天在变，而且有趣的一点是——价格取决于当天的入住率，它和静态的客房信息不是一类数据。
  • 预订服务（Reservation service）：系统的心脏。接预订请求、订房，并在预订和取消时更新客房库存。
  • 支付服务（Payment service）：处理支付，成功后更新预订状态。
  • API 网关：公共网关管限流和身份验证；管理功能走内部 API，藏在 VPN 后面，只对授权人员可见；酒店管理服务负责退款、取消支付这类运营操作。服务之间通信用 RPC 框架，比如 gRPC。

对外的 API 是标准 RESTful 三组端点：酒店（增删改查）、客房（增删改查）、预订（查历史、查详情、下单、取消）。预订请求里带一个 reservationID，它不是普通字段，是幂等键（Idempotency Key）——防止重复下单的关键，第三步细讲。

数据库选关系型数据库。理由：这是读多写少的系统，NoSQL 的写优化用不上；关系库提供 ACID 保证，没有它，负库存、重复扣款这些事故拦不住；数据结构清晰，关系模型最好表达。

第三步 · 深入零件（按原文深入设计的顺序）

1改进的数据模型：按"房型 × 天"记账

初版数据模型按"具体某一间房"建模，适合 Airbnb，不适合酒店——客人订的是"大床房"这种房型，不是 302 号房，房号到店才分。所以预订 API 改成提交 roomTypeID 和 roomCount，表结构跟着换：四张表——room（客房信息）、room_type_rate（价格）、reservation（预订记录）、room_type_inventory（库存）。

最有意思的是 room_type_inventory：每个（hotel_id, room_type_id, date）一行。两个关键列：total_inventory 是客房总数减去暂时下架的；total_reserved 是该房型当天已订出的。行由每日 CRON 作业预先填充。查可用性就是一句 SQL：选出日期范围内每一天的这两列，逐天检查 total_reserved + 要订间数 ≤ 110% × total_inventory——超售就藏在这 110% 里。

容量估算：5000 家酒店 × 20 种房型 × 2 年 × 365 天 ≈ 7300 万行。不多，一个数据库服务器就够，加读副本做高可用即可。若预订历史太大：老数据挪冷存储，只留当前和未来；真要分片，按 hash(hotel_id) % servers_cnt 切——因为查询永远带 hotel_id。

2并发问题①：同一个用户连点两次"预订"

网络一卡，用户双击"完成预订"，可能就下了两单。前端在点击后禁用按钮？不够——用户关掉 JavaScript，按钮照样能再点。正解是幂等 API：填完信息先全局唯一生成一个预订订单 ID（reservationID），提交时带上；第二次点击发出的是同一个 ID，后端一查就认出是重复预订。最后一道保险：reservationID 列加唯一约束（Unique Constraint），数据库层面直接拒绝第二条同 ID 记录落库。幂等的意思：同一个操作调用多少次，效果都等于执行一次。

3并发问题②：两个人抢最后一间房

更难的问题：用户 1 和用户 2 同时订同一间房。在非串行化的隔离级别下，两个事务各自检查库存——都看见 100 间房里 total_reserved 是 99，都通过；事务 2 先扣库存提交，事务 1 看到的还是 99，也扣也提交。两个事务都成功了，房间卖出去两间，这就是超卖。

原文的预订逻辑分两步：第一步 SELECT 查出范围内的每一天，任何一天不满足 total_reserved + n > 110% × total_inventory 就回滚；第二步 UPDATE room_type_inventory SET total_reserved = total_reserved + n，然后提交。问题就出在两步之间没有护栏。三条护栏：悲观锁、乐观锁、数据库约束。

4方案一：悲观锁（Pessimistic Locking）

思路：改记录之前先锁死，别人排队等。MySQL 里用 SELECT ... FOR UPDATE，锁住选中的行直到事务提交。优点：防止应用程序更新正在被修改的数据；容易实现；数据争用严重时有效。缺点也硬：多个资源同时锁可能死锁；某个事务锁太久，其他所有排队的事务全被拖住；查询命中的行越多、事务越长，杀伤力越大。作者因为可扩展性问题，不推荐这条路。

5方案二：乐观锁（Optimistic Locking）

思路：赌冲突很少，不锁，事后校验。表里加一个 version 列：读出行时记下版本号；更新时版本号加 1 一起写回；若库里的版本已经不是刚才那个，说明有人抢先改过，这次更新被拒绝，业务层重试。推荐用版本号而不是时间戳——服务器时钟可能不准。优点：不在数据库里拿锁；防止编辑过期数据；争用低时是首选。缺点：并发一高，大量更新失败回滚，性能反而掉。本系统平均预订 TPS 只有 3，乐观锁正是作者眼里的好选择。

6方案三：数据库约束（Database Constraint）

思路和乐观锁相近，但护栏下沉到数据库：CONSTRAINT check_room_count CHECK((total_inventory - total_reserved) >= 0)——库存减成负数的事务直接判违例。优点：实现简单；争用小时效果很好。缺点：争用高时同样大量失败；约束不像应用代码那样容易做版本管理；不是所有数据库都支持。因为足够简单，这也是酒店预订系统的另一个好选择。

7可扩展性：如果 QPS 大 1000 倍

面试官的追问：这套系统如果被 booking.com 那种量级使用怎么办？QPS 可能大 1000 倍。先看瓶颈在哪：所有服务都是无状态的，复制就能扩；难的是有状态的数据库。一条路是分片（Sharding）：按 hotel_id 切（所有查询都按它过滤），QPS 30,000 分到 16 个分片，每片 1875 QPS，在 MySQL 集群的承受范围内。

另一条路是缓存：用 Redis 缓存客房库存和预订。key 形如 hotelID_roomTypeID_{date}，value 是该日可用房数；设 TTL，过期日期的数据自动清掉。缓存和数据库之间靠 CDC（Change Data Capture，变更数据捕获）异步同步——Debezium 是常用的选择，它把数据库的变更读出来流进 Redis。代价是缓存和库之间总有不一致窗口：页面显示"还有房"、下单却被数据库拦下，用户得刷新。作者认为可接受——数据库是最后防线，总会挡住无效预订；何况就算没有缓存，犹豫太久的人也会撞上房刚被订走的现实。

8服务间的数据一致性：别把账本拆开

单体应用用共享关系库，靠数据库事务，"扣库存 + 写订单"天然原子。本设计选了混合方案：预订和库存 API 由同一个服务处理，共用关系库，继续吃 ACID 的红利。面试官可能质疑：纯微服务里每个服务该有自己的数据库。那样的话，跨服务的操作就没法原子了。两条名路：两阶段提交（Two-phase commit, 2PC）——跨节点原子提交的协议，但性能差，单个节点延迟会阻塞所有节点；Saga——一串本地事务，任何一步失败就触发补偿事务（回滚动作），走最终一致。跨服务一致性是真难题，会显著抬高系统复杂度——所以值得掂量：为"纯"微服务付这个成本，值不值？

权衡与坑

这一讲的真话：
  • 悲观锁可能死锁，锁久了拖垮所有排队的事务——作者明确不推荐，别在抢房这种高争用场景用它。
  • 乐观锁和数据库约束在并发飙高时会大量回滚，性能反而更差；"防超卖"和"高吞吐"在这里是打架的。
  • 允许超售 10% 的前提是"预计会有人取消"；真到了没人取消的旺季，就得有人到店无房——业务上必须有兜底流程。
  • Redis 缓存和数据库之间天然有不一致窗口，页面可能显示有房却订不上。好在数据库会拦下无效预订，错的不入账，只是体验打折。
  • 纯微服务每个服务一个库，一致性立刻变难：2PC 阻塞、Saga 复杂。把预订和库存塞进同一个库，是有意识的务实妥协。
  • 7300 万行的库存表看着吓人，其实单库就能扛；别为不存在的瓶颈提前分片。
记住 3 点
  • 订房系统的核心不是 QPS，是并发正确性：最后一间房只能归一个人。
  • 库存按（酒店， 房型， 天）记账；超售就是一行算术：total_reserved + n ≤ 110% × total_inventory。
  • 防重复下单靠幂等键 + 唯一约束；防超卖靠乐观锁或数据库约束；跨服务的账本别轻易拆，Saga 是最后的招。
