股票交易所：毫秒定胜负的拍卖行

Stock Exchange

一句话：每秒 21 万笔订单涌进来，比快、比公平——撮合顺序错一拍，就是真金白银的纠纷。

规模：100 个品种 · 每天 10 亿订单 峰值 QPS：215,000（开盘最高） 延迟目标：端到端数十微秒 可用性：99.99%（每天仅 8.64 秒）
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

百米决赛把交易所想成一场百米决赛：几百名选手（订单）挤在起跑线，发令枪一响，谁先撞线全靠高速摄像判到千分之一秒——慢一毫秒，名次就不同。每一帧录像按顺序编号封存（序列号），赛后能一帧不差地回放仲裁（确定性重放）；谁先偷看了计时屏（提前收到行情），谁就破坏了比赛公平。交易所要做的，就是把这场决赛每秒钟办 21 万次，且一次都不能判错。

第一步 · 搞清问题

这一讲要造的不是普通网站，而是一台不得出错、不得迟到的撮合机器：买单卖单进来，按价格和先后排队，对上就成交，全程毫秒以内。订单状态错一格、成交顺序乱一拍，都是真钱上的纠纷。

先和面试官对齐需求（原文的需求澄清问答）：

  1. 交易什么——只交易股票，不碰期权、期货。
  2. 什么订单——只支持限价单（Limit Order），操作只有下单和撤单，不做改单。
  3. 什么时间——只覆盖正常交易时段，不支持盘后。
  4. 用户要什么——实时收到成交回报，实时看到订单簿。
  5. 风险检查——做简单的，比如限制一个用户一天最多交易 100 万股苹果股票。
  6. 钱包——下单前先确保资金充足，未完成订单的钱先冻结，订单了结才解冻。

规模假设与非功能需求，数字全部来自原文：

项目假设
交易品种约 100 个（symbol）
同时交易用户数万名
每日订单量10 亿笔
交易时段09:30–16:00，共 6.5 小时
平均 QPS10 亿 ÷ 6.5 ÷ 3600 ≈ 43,000
峰值 QPS5 × 平均 ≈ 215,000（开盘时段显著更高）
可用性≥ 99.99%，每天停机不能超过 8.64 秒
延迟端到端毫秒级，重点盯 99 百分位

除了性能，还有几条硬约束：容错和快速恢复（把事故影响圈住）、安全合规（账户体系 + KYC 身份验证 + 防 DDoS）。

第二步 · 画出大框架

先补一点业务常识（原文的"业务知识 101"）。散户不直连交易所，而是走经纪商（Broker）——Robinhood、Fidelity 这类中介；机构客户用专门的交易软件下大单，还要拆单，避免一笔巨单惊动市场。订单分两种：限价单（Limit）指定价格，可能等不到对手，也可能只成交一部分；市价单（Market）不指定价格，立刻按市价成交。行情上，买价（Bid）是买方肯出的最高价，卖价（Ask）是卖方肯收的最低价；行情分三层——L1 报最优买卖价和数量，L2 报多个价格档位，L3 报每个档位的挂单量和排队量。机构之间传订单用 FIX 协议，一根管道走全场。

高层架构上，一条订单这样流动（对照原文的高层设计图）：

客户→ 经纪商→ 客户端网关→ 订单管理器→ 排序器→ 撮合引擎（订单簿）→ 成交（Fill）→ 回报客户
旁路：撮合引擎 → 市场数据发布者 → 数据服务 → 订阅者 旁路：撮合引擎 → 报告器 → 数据库（合规 / 结算）

主链上每一站分工明确：客户端网关（Client Gateway）做验证、限流、身份认证——它守着大门，但必须保持轻量，因为它在关键路径上；订单管理器（Order Manager）按风险管理器（Risk Manager）的规则做风险检查，再查钱包、冻结资金，然后把订单发给排序器——为了减少带宽，只传必要字段；排序器（Sequencer）给每个入站订单和出站成交盖上序列号；撮合引擎维护每个品种的订单簿，对上就各产生一条成交。

两条旁路不在关键路径上，延迟要求完全不同：市场数据流程里，撮合引擎把成交流发给市场数据发布者（Market Data Publisher），它重建订单簿和 K 线图，交给数据服务推给订阅的经纪商——行情晚 100 毫秒无所谓；报告流程里，报告器（Reporter）从订单和成交中收集字段（client_id、price、quantity、order_type、filled_quantity、remaining_quantity）写入数据库，管交易历史、税务报告、合规报告、结算——这条路上准确性比延迟重要。

对外接口很朴素（原文的 API 设计，RESTful 走网关和经纪商之间，机构客户另用专有协议满足低延迟）：

接口作用关键字段
POST /v1/order创建订单symbol / side / price / quantity；返回 id、filledQuantity、remainingQuantity、status（new/canceled/filled）
GET /execution查成交结果symbol / orderId / startTime / endTime
GET /marketdata/orderBook/L2查 L2 订单簿symbol / depth；返回 bids、asks
GET /marketdata/candles查 K 线resolution（窗口秒数）；返回 open/close/high/low

数据三类：产品（Product）描述品种属性，不常变，服务 UI；订单（Order）是买入/卖出指令，成交（Execution）是撮合后出站的执行结果——关键路径上它们全部在内存里跑，靠排序器持久化和恢复。订单簿（Order Book）按价格档位组织，数据结构要满足：O(1) 查某档位及档位间成交量、快速增删成交、查最优买卖价、遍历档位。K 线图（Candlestick）按时间窗口聚合成开/收/高/低价加成交量，内存只留最近一段，其余落盘，实时分析用内存列式数据库（如 KDB），收盘后转存历史库。

第三步 · 深入零件（按原文深潜 1–10 节的顺序）

1性能：把延迟从毫秒砍到微秒

解决什么问题？交易所的延迟是按微秒竞争的。照前面的模块图走，服务之间隔着网络，排序器还要写磁盘，端到端只有数十毫秒；目标是数十微秒，差三个数量级。两条路：减少关键路径上的任务数；缩短每个任务的耗时（少碰网络、少碰磁盘）。手段很激进——关键路径上一切不相干的职责全剥掉，连日志记录都移除；然后把所有组件塞进一台巨型服务器，进程之间不走路网络，用 mmap（把磁盘文件映射进应用内存的 UNIX 系统调用）当事件总线；再把文件建在 /dev/shm（共享内存）里，磁盘访问为零。最后一招：关键任务写成一个 while 循环（应用程序循环，application loop），绑死在一个 CPU 核上——不上下文切换，也没有多线程抢锁（无锁，lock-free）。

2事件溯源：只记变化，不记结果

解决什么问题？订单管理器最难的是状态转换管理：新单、部分成交、全成、撤单，错一步账就对不上。事件溯源（Event Sourcing）的思路是：不存"当前状态"，只存一条不可变的状态转换记录（事件），当前状态任何时候都能从头重放出来。这天然契合交易所——排序器本来就要给事件编号，主实例崩了，副本拿同一份事件流重放，状态一模一样。落到设计上：外部域经 FIX 协议到客户端网关；订单管理器接收新订单事件，校验后更新内部状态，转发给撮合核心；撮合成功就生成 OrderFilledEvent 经 mmap 发出；其他组件订阅事件存储，各做各的处理。再抠一点：把订单管理器打包成库（library），所有组件人手一份副本，省掉为管订单而跨进程调用。此时排序器的角色也变了：不再是事件存储本身，而是一个单一写入者（single writer）——先把事件排好序，再转发进事件存储，单写者天然没有写冲突。

3高可用性：每天只许停机 8.64 秒

解决什么问题？99.99% 的可用性摊开算，就是每天最多停机 8.64 秒。做法分两层：先识别架构里的单点，给撮合引擎这类关键服务配待命状态的备份实例，故障检测和切换全部自动化。无状态组件（如客户端网关）好办，加机器水平扩展；有状态组件麻烦些：副本都可以处理入站事件，但只有领导者（leader）发布出站结果。怎么知道主死了？发心跳。这套机制只在单机边界内有效；放大到整机，就设热/温副本整机切换。副本之间复制事件存储，用可靠 UDP（Reliable UDP）——比 TCP 快。

4容错性：连备份也挂了怎么办

解决什么问题？温实例也宕机是低概率事件，但交易所输不起。大型科技公司的答案：把核心数据复制到多个城市的数据中心，防自然灾害。动手前要回答四个问题：主实例挂了何时切、切到谁、恢复时间（RTO，恢复时间目标）是多少、哪些功能允许降级运行。手段有三：混沌工程（Chaos Engineering）主动制造故障暴露边界情况——因为一个 bug 可能同时搞死主备；切换先手动执行，摸清故障模式再自动化；选主用领导者选举（如 Raft），靠任期（term）决定谁说了算。最后一条底线是损失容忍度：情况变严重之前能丢多少数据？这决定备份频率。对交易所来说，数据丢失不可接受——所以备份要频繁，再靠 Raft 复制把丢数据的概率压到最低。

5撮合算法：心脏的跳动逻辑

解决什么问题？成交怎么算出来的，必须快且准。原文的伪代码逻辑：每条入站事件先查序列号，对不上预期的 nextSequence 直接报错拒绝（OUT_OF_ORDER）——这是确定性的闸门；再校验 symbol、price、quantity，然后按类型分派。新单：买单去对手方的卖簿撮合，卖单去买簿；撤单：在 orderMap 里查不到就说明已成交，拒绝（CANNOT_CANCEL_ALREADY_MATCHED），查到就摘除并标记 CANCELED。撮合 match() 在对手方簿里沿价格档位的订单队列逐笔取，成交数量取两边较小值，更新已成交量，生成成交（fill），直到剩余数量（leavesQuantity）归零。同一档位上谁先谁后？FIFO（先进先出）——先到先得，朴素即公平。

6确定性：同一个输入，永远同一个结果

解决什么问题？主备切换后，副本必须算出和主一模一样的订单簿，否则两边的账对不上。功能确定性靠排序器保证：事件实际发生的物理时间不重要，按序列号顺序处理才重要。延迟确定性是另一条要持续追踪的线：盯 99 甚至 99.99 百分位的延迟。尖峰从哪来？典型例子是 Java 的垃圾回收器（GC）事件——这也是为什么这类系统对语言和运行时极其挑剔。

7市场数据发布者优化：环形缓冲区与缓存行

解决什么问题？撮合结果要变成全市场看得懂的订单簿和 K 线，而且不能反过来拖慢撮合。内存不是无限的，K 线只保留一部分，客户想要更细的粒度就付更高的价。这里有两个硬核优化：环形缓冲区（Ring Buffer，circular buffer）——固定大小、首尾相连的队列，空间预分配不现分配，而且天然无锁；缓存行填充（padding）——让序列号独享一整条缓存行（cache line），不和别的变量挤在一起，避免伪共享（false sharing）拖慢并发读写。这套数据结构同时用在市场数据服务重建订单簿时。

8分发的公平性与多播：大家必须同时收到

解决什么问题？如果有人比别人早几毫秒收到行情，他就能抢先下单、割后知后觉者的韭菜——这直接破坏市场公平。所以行情发布要用基于可靠 UDP 的多播（Multicast）。网络传输三兄弟：单播（Unicast）一个源对一个目的地；广播（Broadcast）一个源对整个子网；多播（Multicast）一个源发给跨子网的一组主机。理论上，多播让所有订阅者同时收到。但 UDP 不可靠，包可能到不了每个人——用重传来增强。

9托管（Colocation）：付费的"近水楼台"

解决什么问题？物理距离就是延迟，晚一毫秒就可能抢不到单。交易所直接提供托管（Colocation）：把经纪商的服务器放进交易所自己的数据中心。延迟大幅降低，这就是一项 VIP 服务——原文里的托管引擎（colo engine）就是这种租给经纪商、放在交易所机房里的交易引擎服务器。

10网络安全：守住面向公网的大门

解决什么问题？交易所有服务暴露在互联网上，DDoS 是真实威胁。组合拳：隔离——公网服务和私有服务分开，DDoS 打不垮撮合内核；缓存层存更新不频繁的数据；URL 硬化——优先用 https://my.website.com/data/recent 这种可缓存的静态形态，少用 ?from=123&to=456 这种查询串，因为前者更易于缓存；再配允许列表/阻止列表（allowlist/blocklist）和速率限制（rate limiting）削峰。

权衡与坑

这一讲的真话：
  • 单机架构是拿"所有鸡蛋放一个篮子"换微秒级延迟——所以热备、温备、跨城复制一层都不能省；且交易所数据丢失不可接受，备份频率要按损失容忍度倒推。
  • UDP 多播快，但不保证送达；丢包靠重传补。"所有人同时收到行情"是理论目标，工程上永远存在残余的不对称。
  • 关键路径上连日志都剥掉了——换来延迟，也换来运维盲区，只能靠旁路流程和独立的可观测性系统补。
  • 微秒优化都有代价：绑核、无锁环形缓冲区、避开 GC 的语言和运行时选择，牺牲的是开发效率和通用性。
  • 领导者选举在单机边界内简单可靠；跨服务器要靠 Raft 的任期，网络分区时"谁说了算"（脑裂）仍是难题。
  • 订单簿和 K 线全在内存：不限制内存中的数量、不及时落盘，迟早 OOM。
记住 3 点
  • 排序器是节拍器：序列号定死处理顺序，撮合才可重放、主备才一致——确定性就是交易所的命。
  • 关键路径只撮合：风险检查、报告、行情全走旁路；单机 + mmap + 绑核无锁，把端到端压到数十微秒。
  • 公平比快更难：行情多播同发防抢跑，托管是付费特权，99.99% 意味着每天只有 8.64 秒可停机。
