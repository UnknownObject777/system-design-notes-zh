键值存储：全班共用的大字典

Key-Value Store

一句话：存千亿词条、坏几台机器也不丢数据的大字典。整个系统只有两个动作：存进去 put(key, value)，凭钥匙取出来 get(key)——但要把这本字典做成全班的、扛得住停电断网的，得靠一整套零件。

数据模型：put(key, value) / get(key) 键值对：<10 KB 强一致条件：W + R > N（典型 N=3，W=R=2） CAP：三选二，CA 不存在
本讲导航 先打个比方 第一步 · 搞清问题 第二步 · 画出大框架 第三步 · 深入零件 权衡与坑 记住 3 点

先打个比方

快递柜你去过小区的快递柜：存件时系统发你一个取件码，取件时输入取件码，柜门啪一声弹开——你从不关心包裹放在第几层第几格。键值存储就是这只柜子：put(key, value) 是存件，get(key) 是凭码取件。柜子多到摆满全城，就要分区摆放（按小区布柜机）；重要包裹在几个柜机各存一份（副本）；某个柜机断电了，别的柜机照常开门（容错），等它修好再把积压的件还回去。这一讲就是把一只柜子做成全市联网的柜子系统。

第一步 · 搞清问题

这一讲要造的东西：一个分布式键值存储（key-value store）。它是非关系型数据库，数据就是一个个键值对（key-value pair），每个键唯一，凭键取值。接口小得可怜，只有两个：

  • put(key, value)：插入数据。
  • get(key)：检索数据。

接口简单，要求一点也不简单。原文的设计特性逐条列出来：

需求说明
键值对大小较小，<10 KB
数据规模支持大数据量——多到一台机器装不下
可用性高：部分节点宕机，系统照常响应
扩展性自动扩缩容，机器加减不用停机
一致性可调：在强一致与最终一致之间按需选择
延迟低

单机版做不到吗？做不到。单台服务器的内存有限，装不下"大数据量"。所以这一讲的真正题目是：怎么把一只柜子拆成全城联网的一群柜子，还不丢件、不错件、取得快。

第二步 · 画出大框架

照原文的最终架构图，客户端的一次请求这样流动：

客户端 get / put→ 协调器 Coordinator→ 一致性哈希环上的节点→ N 台副本（跨数据中心）→ 提交日志 / 内存缓存 / SSTable

客户端只认两个简单 API：get(key) 和 put(key, value)，不需要知道后面有多少台机器。协调器（coordinator）是客户端和集群之间的代理：它把 key 哈希到环上，找到该负责的节点，写请求还要沿环顺时针找出前 N 台副本一起写。

为什么这样切模块？因为每一块只背一个责任：哈希环管"数据撒得匀"，副本管"坏一台不丢"，日志和缓存管"单机内部又快又稳"。系统完全去中心化——每台节点职责相同，加节点、移节点全自动进行，不存在单点故障（single point of failure）。下面第三步，把每个零件拆开看。

第三步 · 深入零件（从单机一路走到最终架构）

1单服务器版：一张哈希表打天下

先看起点。单机键值存储用一个哈希表（hash table）把键值对放在内存里，put 和 get 都接近瞬时。内存不够还想挤，有两招优化：数据压缩；把不常访问的冷数据挪到磁盘上。但哈希表再大也长在一台机器的内存里——内存有上限，这就是分布式方案存在的理由。

2CAP 定理：分布式世界的三选二

数据一上多台机器，就撞上 CAP 定理。三个保证：一致性（Consistency）——所有客户端同时看到相同的数据；可用性（Availability）——部分节点宕机，系统仍能响应每个请求；分区容错性（Partition Tolerance）——网络断了，系统还能跑。CAP 说：三个最多同时拿两个。网络故障不可避免，分区容错必须留着，所以 CA 系统在现实里并不存在。分区真发生时只剩一道选择题：选 CP（银行系统就是这类），阻塞写入，宁可不服务也不给错数据；选 AP（最终一致性那一路），继续接受读写，哪怕读到旧数据，等分区恢复再把数据同步过去。

3数据分区：一致性哈希上岗

千亿条键值对，怎么均匀撒到几百台机器？用一致性哈希（Consistent Hashing）——第 5 讲的主角，这里直接上岗。两个好处：服务器增减时只挪动一小部分数据，自动扩缩容；靠虚拟节点（virtual node）兼容机器的强弱差异——一台机器的虚拟节点数量和它的容量成正比，大机器多背几个点，小机器少背几个。

4数据复制：沿环顺时针数 N 台

分区解决"放得下"，复制解决"坏一台不丢"。每个键的数据复制到 N 台服务器。挑哪 N 台？从 key 在环上的位置出发，顺时针遍历，取环上的前 N 台来存副本。摆放还有一条纪律：副本放进不同的数据中心——这样扛得住的不只是机器故障，是整个机房级别的灾难，而且虚拟节点满天飞的情况下可靠性更高。

5一致性：法定人数共识（Quorum Consensus）

副本一多，新问题跟着来：写到几台算成功？读到几台才敢返回？答案是一组叫法定人数共识（Quorum Consensus）的规则：N 是副本总数；W 是写法定人数（write quorum），一次写必须拿到 W 个副本确认才算成功；R 是读法定人数（read quorum），一次读必须等到至少 R 个副本响应。关键规则就一条：W + R > N，就能保证强一致性，典型配置是 N = 3、W = R = 2。

这几个数字是延迟与一致性之间的跷跷板：R = 1 且 W = N，为快速读取优化；W = 1 且 R = N，为快速写入优化；W + R ≤ N，两边都快，但强一致性没了。一致性本身还分三档：强一致性（Strong Consistency）——读到的总是最新写入的结果；弱一致性（Weak Consistency）——后续的读可能看不到最新值；最终一致性（Eventual Consistency）——给足时间，所有更新都会传播，所有副本终会一致。

6不一致怎么办：向量时钟（Vector Clock）

AP 路线里，两个副本可能被同时修改：服务器 1 改了名字，服务器 2 也改了名字，两个修改并行发生，得到互相冲突的值，记作版本 v1 和 v2。怎么分辨谁新谁旧、谁该留谁该合并？用版本控制加向量时钟（vector clock）：把每次修改都当成一个不可变的新版本，并给每个数据项挂一串 [服务器, 版本] 对，形如 D([S1, v1], [S2, v2], …, [Sn, vn])。数据在某台服务器 Si 被改时：Si 已在时钟里，对应计数器加 1；不在，就新增一条 [Si, 1]。

比版本靠两条规则：版本 X 的所有计数器都小于等于 Y 的对应计数器，X 就是 Y 的祖先（ancestor），可以直接被覆盖；Y 里至少有一个计数器比 X 小，两个版本就是兄弟（sibling）——冲突实锤。检测到冲突后，系统不替你瞎猜，而是交给应用程序特定的逻辑或客户端干预来调和数据。代价两条：客户端的复杂度上升了；时钟条目只增不减，得靠裁剪（trimming）策略压住它的大小。

7故障检测：Gossip 协议与心跳

想处理故障，先得可靠地知道谁病了。只听一台服务器说"它挂了"是不够的——通常要至少两个独立的信息来源，才能宣告一台服务器宕机。具体做法用 Gossip 协议：每个节点维护一份成员名单（成员 ID + 心跳计数器 heartbeat counter），定期把自己的心跳计数器加 1，并随机发给一群节点互相通气；某个成员的心跳超过预定义的时间没涨，就被判离线。像村口传闲话，人人都小声跟邻居交换消息，坏消息最终全村皆知，而且没有中央广播台。

8临时故障：宽松法定人数与带提示的移交

节点只是暂时离线（重启、网络抖动），不能干等它回来。宽松法定人数（Sloppy Quorum）：不强制原来那 W 台确认，而是在哈希环上选前 W 个健康服务器接着处理写、前 R 个健康服务器处理读，离线的先跳过——法定人数的要求被"借"到了健康节点上，可用性保住了。

带提示的移交（Hinted Handoff）负责还账：这些代班节点把本该属于宕机服务器的变更记下来，等它恢复上线，再把变更推回去追赶，副本间的一致性补回来。一个管"顶班"，一个管"补课"，临时故障就闭环了。

9永久故障：Merkle 树高效对账

节点彻底死了又回来，或副本长期各长各的，两边差了多少？逐条比对太慢，要传的数据量也太大。Merkle 树（默克尔树，又称哈希树）就是为高效对账而生的：叶子节点存各数据块的哈希值，非叶节点存其子节点的哈希值，一路汇到顶上的根哈希（root hash）——根就是整份数据的"指纹"。构建分四步：把键空间切成一个个桶（bucket）；用均匀哈希（uniform hashing）对桶里每个键求哈希；每个桶合成一个单一哈希值；逐层合并桶哈希，算出更上层的哈希，最终得到根哈希。

对账时先比两个副本的根哈希：一致，收工；不一致，就递归往下比子哈希，一层层定位到具体是哪个桶脏了，只同步不一致的那部分数据。三个优点全来自这个"只补不一样的"：高效（传输量小）、可扩展（数据集再大也对得起）、可靠（副本最终一致）。

10数据中心故障：把副本撒到多个机房

单机故障之上还有机房级灾难。对策在第 4 节就埋了伏笔：把数据复制到多个数据中心，一个机房整体挂了，别的机房照常服务。这是可用性设计的最后一道防线——节点故障靠 sloppy quorum 扛，机房故障靠跨机房副本扛。

11写路径：先记账，再落盘（Cassandra 架构）

单机内部，一条写请求怎么走完？以 Cassandra 架构为例，顺序是：第一步，把写入持久化到提交日志（commit log）——这是防丢的账本，机器崩了还能照着回放；第二步，数据进内存缓存（memory cache）——走到这步写就可以返回成功了，所以快；第三步，内存满了，再把数据批量刷新到磁盘上的 SSTable（Sorted String Table，有序字符串表）。为什么绕这一圈？磁盘随机写慢、顺序写快：日志顺序追加保命，内存即时响应保快，SSTable 有序落盘，给读路径铺路。

12读路径：布隆过滤器指路

读先查内存缓存——命中就直接返回，全程不碰磁盘。没命中就得去磁盘上的 SSTable 里找，可 SSTable 不止一个，逐个翻太贵。布隆过滤器（Bloom Filter）负责指路：先用它快速判断这个数据可能在哪个 SSTable，把候选缩到极小的范围，再检索并返回。它存在的理由就一个字：快——用一点点误判的代价，换掉全表扫描的时间。

13最终架构：人人平等的环

所有零件拼起来：客户端只通过两个简单 API 通信——get(key) 和 put(key, value)；协调器（coordinator）是客户端与键值存储之间的代理；节点通过一致性哈希分布在环上；数据在多个节点上复制；系统完全去中心化，节点的添加和移动自动进行；每台节点承担相同的一组职责——没有单点故障。这一讲的大字典，到此装订完成。

权衡与坑

这一讲的真话：
  • CAP 的紧箍咒摘不掉：网络分区不可避免，CA 系统现实里不存在；分区真发生时，只能在一致性（阻塞写入）和可用性（可能返回旧数据）之间二选一。
  • Quorum 是跷跷板：R=1 + W=N 读快，W=1 + R=N 写快，W+R≤N 两边都快但强一致性没了——没有"又快又强"的免费午餐。
  • 向量时钟把账记给了客户端：冲突检测与调和的复杂度被推给应用程序；时钟条目随更新不断增长，trimming 裁剪策略没设计好就会失控。
  • 判死要慎重：一个节点说另一个节点挂了不算数，至少两个独立信息来源——误判会引发不必要的副本迁移和数据搬移。
  • 宽松法定人数只是"借宿"：数据暂时寄住在健康节点上，宕机节点恢复后必须靠 hinted handoff 把变更推回去，否则一致性窗口一直敞开。
记住 3 点
  • 键值存储只有 get/put 两个动作，难的是两件事：数据撒得匀（一致性哈希 + 虚拟节点）、副本摆得对（沿环顺时针取前 N 台、跨数据中心）。
  • 一致性是可调的旋钮：W + R > N 换强一致（典型 N=3，W=R=2），拿延迟换正确性；分区发生时，一致性 vs 可用性只能二选一。
  • 故障分临时和永久：临时靠 sloppy quorum 顶班 + hinted handoff 补课，永久靠 Merkle 树对账——只同步不一致的那部分。
