# 第 26 章：支付系统

## 引言
在本章中，我们将设计一个**支付系统**，它支撑着所有现代**电子商务**。

**支付系统**用于处理金融交易结算，转移货币价值。

---

## 步骤 1：理解问题并确定设计范围
 * 问：我们正在构建什么样的支付系统？
 * 答：电子商务系统的支付后端，类似于 Amazon.com。它处理与资金流动相关的一切。
 * 问：支持哪些支付方式——信用卡、PayPal、银行卡等？
 * 答：在现实中，系统应支持所有这些方式。就本次面试而言，我们可以使用信用卡支付。
 * 问：我们是否自己处理信用卡业务？
 * 答：不，我们使用第三方提供商，如 Stripe、Braintree、Square 等。
 * 问：我们是否在系统中存储信用卡数据？
 * 答：出于合规原因，我们不直接在系统中存储信用卡数据。我们依赖第三方支付处理商。
 * 问：应用程序是面向全球的吗？我们需要支持不同的货币和国际支付吗？
 * 答：应用程序是面向全球的，但就本次面试而言，我们假设只使用一种货币。
 * 问：我们每天支持多少笔支付交易？
 * 答：每天 100 万笔交易。
 * 问：我们需要支持付款流程吗，例如每月向付款人付款？
 * 答：是的，我们需要支持这一点。
 * 问：还有其他我应该注意的事项吗？
 * 答：我们需要支持对账（reconciliation），以修复与内部和外部系统通信时出现的任何不一致。

### **功能需求**
 * 收款流程——支付系统代表商户从客户处接收资金
 * 付款流程——支付系统向世界各地的卖家发送款项

### **非功能需求**
 * 可靠性和容错性。失败的支付需要被仔细处理
 * 需要在内部和外部系统之间建立对账机制

### **粗略估算（Back-of-the-envelope estimation）**
系统需要每天处理 100 万笔交易，即每秒 10 笔交易。

对任何数据库系统来说，这都不是高吞吐量，因此这不是本次面试的重点。

### **收款流程**
以下是收款流程的高层级概览：

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="收款流程高层级" width="500" />
</div>

 * 支付服务（Payment service）——接受支付事件并协调支付过程。它通常还会使用第三方提供商进行风险检查，以识别反洗钱（AML）违规或犯罪活动。
 * 支付执行器（Payment executor）——通过支付服务提供商（PSP）执行单个支付订单。支付事件可能包含多个支付订单。
 * 支付服务提供商（PSP）——将资金从一个账户转移到另一个账户，例如从买家的信用卡账户转移到电子商务网站的银行账户。
 * 卡组织（Card schemes）——处理信用卡业务的组织，例如 Visa、MasterCard 等。
 * 账本（Ledger）——记录所有支付交易的财务记录。
 * 钱包（Wallet）——保存所有商户的账户余额。

以下是一个示例收款流程：
 * 用户点击"提交订单"（place order），一个支付事件被发送到支付服务
 * 支付服务将事件存储在其数据库中
 * 支付服务针对该支付事件中的全部支付订单调用支付执行器
 * 支付执行器将支付订单存储在其数据库中
 * 支付执行器调用外部 PSP 处理信用卡支付
 * 支付执行器处理完支付后，支付服务更新钱包，以记录卖家有多少资金
 * 钱包服务将更新后的余额信息存储在其数据库中
 * 支付服务调用账本来记录所有资金流动

### **支付服务的 API**
```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```

示例 `payment_order`（支付订单）：
```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```

注意事项：
 * `payment_order_id` 会被转发给 PSP 用于支付去重，即它是幂等键（idempotency key）。
 * 金额字段是 `string` 类型，因为 `double` 不适合表示货币值。

```
GET /v1/payments/{:id}
```

该端点基于 `payment_order_id` 返回单笔支付的执行状态。

### **支付服务数据模型**
我们需要维护两张表——`payment_events` 和 `payment_orders`。

对于支付而言，性能通常不是重要因素。但强一致性很重要。

选择数据库时的其他考虑：
 * 有大量的 DBA 人才市场可供雇佣来管理数据库
 * 数据库有被其他大型金融机构使用过的良好记录
 * 支持工具的丰富程度
 * 相比 NoSQL/NewSQL，传统 SQL 具有 ACID 保证

以下是 `payment_events` 表所包含的内容：
 * `checkout_id`——字符串，主键
 * `buyer_info`——字符串（个人备注——也许用外键指向另一张表更合适）
 * `seller_info`——字符串（个人备注——同上）
 * `credit_card_info`——取决于卡提供商
 * `is_payment_done`——布尔值

以下是 `payment_orders` 表所包含的内容：
 * `payment_order_id`——字符串，主键
 * `buyer_account`——字符串
 * `amount`——字符串
 * `currency`——字符串
 * `checkout_id`——字符串，外键
 * `payment_order_status`——枚举（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）
 * `ledger_updated`——布尔值
 * `wallet_updated`——布尔值

注意事项：
 * 一个给定的支付事件关联多个支付订单
 * 收款流程不需要 `seller_info`。付款流程才需要
 * `ledger_updated` 和 `wallet_updated` 在调用相应服务记录支付结果时被更新
 * 支付状态流转由一个后台作业管理，它检查进行中支付的状态更新，并在支付未能在合理时间内完成时触发告警

### **复式记账账本系统**
复式记账（double-entry accounting）机制是任何支付系统的关键。它是一种通过始终对两个账户应用资金操作来跟踪资金流动的机制，其中一个账户的余额增加（贷记，credit），另一个减少（借记，debit）：

| 账户 | 借记 | 贷记 |
|---------|-------|--------|
| 买家（buyer） | $1    |        |
| 卖家（seller） |       | $1     |

所有交易条目的总和始终为零。该机制为系统内的所有资金流动提供了端到端的可追溯性。

## 步骤 3：深入设计
本节重点关注使系统更快、更健壮、更安全。

### **PSP 集成**
如果我们的系统能够直接连接银行或卡组织，就可以在无需 PSP 的情况下完成支付。
这类连接非常罕见，通常只有能够证明投资价值的大型公司才会这样做。

如果我们走传统路线，可以通过以下两种方式之一集成 PSP：
 * 通过 API，如果我们的支付系统可以收集支付信息
 * 通过托管支付页面，以避免处理支付信息法规问题

以下是托管支付页面的工作流程：

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="托管支付页面工作流程" width="500" />
</div>

 * 用户在浏览器中点击"结算"（checkout）按钮
 * 客户端携带支付订单信息调用支付服务
 * 支付服务收到支付订单信息后，向 PSP 发送支付注册请求
 * PSP 接收货币、金额、有效期等支付信息，以及用于幂等的 UUID。通常就是支付订单的 UUID
 * PSP 返回一个唯一标识支付注册的令牌（token）。令牌存储在支付服务数据库中
 * 一旦令牌存储完成，用户会看到一个由 PSP 托管的支付页面。该页面使用令牌以及用于成功/失败的重定向 URL 进行初始化
 * 用户在 PSP 页面上填写支付详情，PSP 处理支付并返回支付状态
 * 用户现在被重定向回 redirectURL（重定向 URL）。示例重定向 URL——`https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * 异步地，PSP 通过 webhook 调用我们的支付服务，通知后端支付结果
 * 支付服务根据收到的 webhook 记录支付结果

### **对账（Reconciliation）**
前一节解释了支付的成功路径（happy path）。不成功路径会通过后台对账过程被检测出来并进行对账。

每天晚上，PSP 会发送一份结算文件（settlement file），我们的系统用它来将外部系统的状态与内部系统的状态进行比较。

<div style="margin-left:3rem">
    <img src="./images/settlement-report.png" alt="结算报告" width="500" />
</div>

这个过程也可以用于检测内部不一致，例如账本服务和钱包服务之间的不一致。

不匹配由财务团队手动处理。不匹配会按以下方式处理：
 * 可分类，因此是已知的不匹配，可以使用标准程序进行调整
 * 可分类，但无法自动化。由财务团队手动调整
 * 不可分类。由财务团队手动调查和调整

### **处理支付处理延迟**
有些情况下，一笔支付可能需要数小时才能完成，尽管通常只需要几秒钟。

这可能是由于以下原因：
 * 一笔支付被标记为高风险，需要有人手动审查
 * 信用卡需要额外保护，例如 3D Secure 身份验证（3D Secure Authentication），这需要持卡人提供额外信息才能完成

这些情况通过以下方式处理：
 * 等待 PSP 在支付完成时向我们发送 webhook，或者如果 PSP 不提供 webhook，则轮询其 API
 * 向用户显示"处理中"（pending）状态，并给他们一个可以查看支付更新进度的页面。我们也可以在支付完成后给他们发送电子邮件

### **内部服务之间的通信**
服务之间相互通信有两种通信模式——同步和异步。

同步通信（即 HTTP）在小型系统中效果良好，但随着规模扩大会出现问题：
 * 性能低——随着更多服务参与调用链，请求-响应周期变长
 * 故障隔离性差——如果 PSP 或任何其他服务失败，用户将无法收到响应
 * 强耦合——发送方需要知道接收方
 * 难以扩展——由于没有缓冲区，很难支持突发流量

异步通信可以分为两类。

单接收者——多个接收者订阅同一个主题，但消息只被处理一次：

<div style="margin-left:3rem">
    <img src="./images/single-receiver.png" alt="单接收者" width="500" />
</div>

多接收者——多个接收者订阅同一个主题，消息会转发给所有接收者：

<div style="margin-left:3rem">
    <img src="./images/multiple-receiver.png" alt="多接收者" width="500" />
</div>

后一种模式非常适合我们的支付系统，因为一笔支付可能触发多个副作用，由不同的服务处理。

简而言之，同步通信更简单，但无法让服务自治。
异步通信以简单性和一致性换取可扩展性和弹性。

### **处理失败的支付**
每个支付系统都需要处理失败的支付。以下是我们将使用的一些机制：
 * 跟踪支付状态——每当支付失败时，我们可以根据支付状态决定是重试还是退款
 * 重试队列——我们将要重试的支付发布到重试队列中
 * 死信队列——已最终失败的支付被推送到死信队列，在这里可以对失败的支付进行调试和检查

### **精确一次投递（Exactly-once delivery）**
我们需要确保一笔支付被精确处理一次，以避免向客户重复收费。

如果一个操作同时满足至少一次（at-least-once）和至多一次（at-most-once），那么它就是被精确一次执行的。

为了实现至少一次的保证，我们将使用重试机制：

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="重试机制" width="500" />
</div>

以下是决定重试间隔的一些常见策略：
 * 立即重试——失败后客户端立即发送另一个请求
 * 固定间隔——重试支付前等待固定的时间
 * 递增间隔——每次重试之间逐渐增加重试间隔
 * 指数退避（exponential back-off）——在连续重试之间将重试间隔加倍
 * 取消——客户端取消请求。当错误是终结性的或达到重试阈值时，会发生这种情况

经验法则：默认采用指数退避重试策略。一个良好的实践是让服务器使用 `Retry-After` 响应头指定重试间隔。

重试的一个问题是服务器有可能处理两次支付：
 * 客户端两次点击"支付按钮"，因此被扣款两次
 * 支付被 PSP 成功处理，但下游服务（账本、钱包）没有成功处理。重试导致支付被 PSP 再次处理

为了解决双重支付问题，我们需要使用幂等机制（idempotency）——即一个操作即使被应用多次也只处理一次的特性。

从 API 的角度来看，客户端可以进行多次调用，产生相同的结果。
幂等性由请求中的一个特殊头部（例如 `idempotency-key`）来管理，通常是 UUID。

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="幂等示例" width="500" />
</div>

幂等性可以通过数据库添加唯一键约束的机制来实现：
 * 服务器尝试在数据库中插入一行新记录
 * 插入因违反唯一键约束而失败
 * 服务器检测到该错误，转而将现有对象返回给客户端

幂等性也应用于 PSP 端，使用之前讨论过的 nonce（随机数）。PSP 会确保不使用相同的 nonce 处理两次支付。

### **一致性**
在一个支付的生命周期中，会调用多个有状态服务——PSP、账本、钱包、支付服务。

任何两个服务之间的通信都可能失败。
我们可以通过实现精确一次处理和对账，来确保所有服务之间的最终数据一致性。

如果我们使用复制（replication），就必须处理复制延迟，这也可能导致用户在主数据库和副本数据库之间观察到不一致的数据。

为了缓解这一点，我们可以让所有读写都从主数据库进行，仅将副本用于冗余和故障转移。
或者，我们可以使用共识算法（如 Paxos 或 Raft）确保副本始终同步。
我们也可以使用基于共识的分布式数据库，例如 YugabyteDB 或 CockroachDB。

### **支付安全**
以下是我们可以用来确保支付安全的一些机制：
 * 请求/响应窃听——我们可以使用 HTTPS 保护所有通信
 * 数据篡改——强制加密和完整性监控
 * 中间人攻击——使用带证书固定（certificate pinning）的 SSL
 * 数据丢失——跨多个区域复制数据，并进行数据快照
 * DDoS 攻击——实现限流（rate limiting）和防火墙
 * 卡片被盗——使用令牌，而不是在我们的系统中存储真实的卡信息
 * PCI 合规——针对处理品牌信用卡的组织的安全标准
 * 欺诈——地址验证、卡片验证码（CVV）、用户行为分析等
