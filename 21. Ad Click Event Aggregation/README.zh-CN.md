# 第 21 章：广告点击事件聚合

## 引言
随着 Facebook、YouTube、TikTok 等的崛起，**数字广告**已经成为一个庞大的产业。

因此，跟踪广告点击事件十分重要。在本章中，我们将探讨如何设计一个 Facebook/Google 规模级别的**广告点击事件聚合**系统。

数字广告有一个称为**实时竞价（Real-Time Bidding，RTB）**的过程，在这个过程中，数字广告库存被买卖：

<div style="margin-left:3rem">
    <img src="./images/digital-advertising-example.png" alt="数字广告示例" width="500" />
</div>

RTB 的速度非常重要，因为它通常在一秒内完成。
数据的准确性也非常重要，因为它影响着广告主需要支付的金额。

基于广告点击事件聚合的结果，广告主可以做出诸如调整目标受众和关键词等决策。

## 步骤 1：理解问题并确定设计范围
 - C：输入数据的格式是什么样的？
 - I：每天有 10 亿次广告点击，总共有 200 万个广告。广告点击事件数量每年同比增长 30%。
 - C：我们的系统需要支持的最重要的查询有哪些？
 - I：需要考虑的核心查询：
   - 返回广告 X 在过去 Y 分钟内的点击事件数量
   - 返回过去 1 分钟内被点击次数最多的前 100 个广告。两个参数都应可配置。聚合每分钟执行一次。
   - 支持按 `ip`、`user_id`、`country` 对上述查询进行数据过滤
 - C：我们需要担心边界情况吗？我能想到的一些情况：
   - 可能有事件比预期到达得更晚
   - 可能有重复的事件
   - 系统的不同部分可能出现故障，所以我们需要考虑系统恢复
 - I：列得很好，把这些情况考虑进去
 - C：延迟要求是什么？
 - I：广告点击聚合的端到端延迟为几分钟。对于 RTB，延迟应小于一秒。广告点击聚合允许这样的延迟是可以接受的，因为这些数据通常用于计费和报告。

### **功能需求**
 - 聚合 `ad_id` 在过去 Y 分钟内的点击次数
 - 每分钟返回被点击次数最多的前 100 个 `ad_id`
 - 支持按不同属性进行聚合过滤
 - 数据规模处于 Facebook 或 Google 级别

### **非功能需求**
 - 聚合结果的正确性很重要，因为它用于 RTB 和广告计费
 - 妥善处理延迟或重复的事件
 - 健壮性——系统应对部分故障具有弹性
 - 延迟——端到端延迟最多为几分钟

### **粗略估算**
 - 10 亿 DAU
 - 假设每个用户每天点击 1 个广告 -> 每天有 10 亿次广告点击
 - 广告点击 QPS = 10,000
 - 峰值 QPS 是该数字的 5 倍 = 50,000
 - 一次广告点击占用 0.1KB 存储。每日存储需求为 100gb
 - 每月存储 = 3tb

## 步骤 2：提出高层设计并取得共识
在本节中，我们讨论查询 API 设计、数据模型和高层设计。

### **查询 API 设计**
API 是客户端与服务器之间的契约。在我们的场景中，客户端是仪表盘用户——数据科学家/分析师、广告主等。

以下是我们的功能需求：
 - 聚合 `ad_id` 在过去 Y 分钟内的点击次数
 - 返回在过去 M 分钟内被点击次数最多的前 N 个 `ad_id`
 - 支持按不同属性进行聚合过滤

我们需要两个端点来实现这些需求。过滤可以通过其中一个端点上的查询参数来完成。

**聚合 ad_id 在过去 M 分钟内的点击次数**：

```
GET /v1/ads/{:ad_id}/aggregated_count
```

查询参数：
 - from - 开始分钟。默认是当前时间 - 1 分钟
 - to - 结束分钟。默认是当前时间
 - filter - 不同过滤策略的标识符。例如 001 表示"非美国地区的点击"。

响应：
 - ad_id - 广告标识符
 - count - 开始分钟和结束分钟之间的聚合计数

**返回在过去 M 分钟内被点击次数最多的前 N 个 ad_id**

```
GET /v1/ads/popular_ads
```

查询参数：
 - count - 被点击次数最多的前 N 个广告
 - window - 聚合窗口大小，以分钟为单位
 - filter - 不同过滤策略的标识符

响应：
 - ad_id 列表

### **数据模型**
在我们的系统中，有原始数据和聚合数据。

原始数据如下所示：

```
[AdClickEvent] ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA
```

以下是一个结构化格式的例子：
| ad_id | click_timestamp     | user  | ip            | country |
|-------|---------------------|-------|---------------|---------|
| ad001 | 2021-01-01 00:00:01 | user1 | 207.148.22.22 | USA     |
| ad001 | 2021-01-01 00:00:02 | user1 | 207.148.22.22 | USA     |
| ad002 | 2021-01-01 00:00:02 | user2 | 209.153.56.11 | USA     |

以下是聚合版本：
| ad_id | click_minute | filter_id | count |
|-------|--------------|-----------|-------|
| ad001 | 202101010000 | 0012      | 2     |
| ad001 | 202101010000 | 0023      | 3     |
| ad001 | 202101010001 | 0012      | 1     |
| ad001 | 202101010001 | 0023      | 6     |

`filter_id` 帮助我们实现过滤需求。
| filter_id | region | IP        | user_id |
|-----------|--------|-----------|---------|
| 0012      | US     | *         | *       |
| 0013      | *      | 123.1.2.3 | *       |

为了支持快速返回过去 M 分钟内被点击次数最多的前 N 个广告，我们还将维护以下结构：
| most_clicked_ads   |           |                                                  |
|--------------------|-----------|--------------------------------------------------|
| window_size        | integer   | 聚合窗口大小（M），以分钟为单位                   |
| update_time_minute | timestamp | 上次更新时间戳（以 1 分钟为粒度）                 |
| most_clicked_ads   | array     | JSON 格式的广告 ID 列表。                         |

存储原始数据和存储聚合数据各有什么优缺点？
 - 原始数据可以使用完整的数据集，并支持数据过滤和重新计算
 - 另一方面，聚合数据使我们的数据集更小，查询更快
 - 原始数据意味着更大的数据存储和更慢的查询
 - 然而，聚合数据是派生数据，因此会有一些数据丢失。

在我们的设计中，我们将结合使用这两种方法：
 - 保留原始数据用于调试是一个好主意。如果聚合过程中出现了 bug，我们可以发现 bug 并进行回填。
 - 聚合数据也应该存储起来，以获得更快的查询性能。
 - 原始数据可以存储在冷存储中，以避免额外的存储成本。

说到数据库，有几个因素需要考虑：
 - 数据是什么样的？是关系型、文档还是 blob？
 - 工作负载是读密集、写密集还是两者兼有？
 - 需要事务吗？
 - 查询是否依赖 OLAP 函数，如 SUM 和 COUNT？

对于原始数据，我们可以看到平均 QPS 为 10k，峰值 QPS 为 50k，所以系统是写密集型的。
另一方面，读流量较低，因为原始数据主要用作出问题时的备份。

关系型数据库可以胜任这项工作，但扩展写入可能具有挑战性。
或者，我们可以使用 Cassandra 或 InfluxDB，它们对高写入负载有更好的原生支持。

另一个选择是使用 Amazon S3，并配合 ORC、Parquet 或 AVRO 等列式数据格式。由于这种方案不太熟悉，我们将坚持使用 Cassandra。

对于聚合数据，工作负载是读写双密的，因为聚合数据不断被查询用于仪表盘和告警。
由于聚合服务每分钟都会对数据进行聚合和写入，它也是写密集型的。
因此，这里我们也使用相同的数据存储（Cassandra）。

## 步骤 3：深入设计
让我们深入探讨一些更有趣的话题。

### **流处理 vs. 批处理**
我们提出的高层架构是一种流处理系统。
以下是三种系统之间的比较：
|                         | 服务（在线系统）                  | 批处理系统（离线系统）                            | 流处理系统（近实时系统）     |
|-------------------------|-----------------------------------|---------------------------------------------------|------------------------------|
| 响应性                  | 快速响应客户端                   | 不需要对客户端做出响应                            | 不需要对客户端做出响应       |
| 输入                    | 用户请求                         | 有界输入，大小有限。数据量大                      | 输入没有边界（无限流）        |
| 输出                    | 对客户端的响应                   | 物化视图（materialized views）、聚合指标等。      | 物化视图、聚合指标等。       |
| 性能衡量指标             | 可用性、延迟                     | 吞吐量                                            | 吞吐量、延迟                 |
| 示例                    | 在线购物                         | MapReduce                                         | Flink [13]                   |

在我们的设计中，我们混合使用了批处理和流处理。

我们使用流处理在数据到达时进行处理，并近实时地生成聚合结果。
另一方面，我们使用批处理进行历史数据备份。

一个同时包含两条处理路径——批处理路径和流处理路径——的系统，这种架构称为 lambda 架构。
它的一个缺点是你有两条处理路径、两套不同的代码库需要维护。

Kappa 是一种替代架构，它将批处理和流处理合并为一条处理路径。
其核心思想是使用单一的流处理引擎。

Lambda 架构：

</div>

Kappa 架构：

每当我们不得不重新计算聚合数据时（例如由于聚合逻辑中的重大 bug），我们可以从存储的原始数据中重新计算聚合。
 - 重新计算服务从原始存储中检索数据。这是一个批处理作业。
 - 检索到的数据被发送到一个专门的聚合服务，这样实时处理的聚合服务就不会受到影响。
 - 聚合结果被发送到第二个消息队列，之后我们更新聚合数据库中的结果。

### **时间**
我们需要一个时间戳来执行聚合。它可以在两个地方产生：
 - 事件时间（event time）——广告点击发生的时间
 - 处理时间（processing time）——服务器处理事件时系统的时间

由于使用异步处理（消息队列）和网络延迟，事件时间和处理时间之间可能会有显著差异。
 - 如果我们使用处理时间，聚合结果可能不准确
 - 如果我们使用事件时间，我们必须处理延迟事件

没有完美的解决方案，我们需要权衡取舍：
|                 | 优点                          | 缺点                                                                                 |
|-----------------|-------------------------------|--------------------------------------------------------------------------------------|
| 事件时间        | 聚合结果更准确                | 客户端可能有错误的时间，或者时间戳可能由恶意用户生成 |
| 处理时间        | 服务器时间戳更可靠            | 如果事件延迟到达，时间戳不准确                                       |

由于数据准确性很重要，我们将使用事件时间进行聚合。

为了缓解延迟事件的问题，可以利用一种称为"水印（watermark）"的技术。

### **投递保证**
由于我们聚合的数据将用于计费，数据准确性是首要考虑因素。

因此，我们需要讨论：
 - 如何避免处理重复事件
 - 如何确保所有事件都被处理

有三种投递保证可供使用——最多一次（at-most-once）、至少一次（at-least-once）和精确一次（exactly-once）。

在大多数情况下，当少量重复是可以接受时，至少一次就足够了。
但对于我们的系统并非如此，因为很小的百分比差异就可能导致数百万美元的出入。
因此，我们需要使用精确一次的投递语义。

### **数据去重**
最常见的数据质量问题之一是重复数据。

它可能来自多种来源：
 - 客户端——客户端可能会多次重新发送同一个事件。出于恶意意图发送的重复事件最好由风险引擎（risk engine）处理。
 - 服务器故障——聚合服务节点在聚合过程中宕机，上游服务没有收到确认，因此事件被重新发送。

### **系统的扩展**
让我们讨论如何随着系统增长对它进行扩展。

我们有三个独立的组件——消息队列、聚合服务和数据库。
由于它们是解耦的，我们可以独立地扩展它们。

如何扩展消息队列：
 - 我们不对生产者设置限制，因此可以轻松扩展它们
 - 消费者可以通过将它们分配到消费者组并增加消费者数量来进行扩展。
 - 为此，我们还需要确保预先创建足够的分区
 - 此外，当有数千个消费者时，消费者再平衡（consumer rebalancing）可能需要一段时间，因此建议在非高峰时段进行
 - 我们还可以考虑按地理位置对主题（topic）进行分区，例如 `topic_na`、`topic_eu` 等。

### **容错**
在聚合节点内部，我们在内存中处理数据。如果一个节点宕机，已处理的数据就会丢失。

我们可以利用 Kafka 中的消费者偏移量，在另一个节点接手后从上次中断的地方继续。
然而，还有额外的中间状态需要维护，因为我们正在聚合"过去 M 分钟内被点击最多的前 N 个广告"。

### **数据监控与正确性**
由于我们聚合的数据是关键的，因为它用于计费，因此建立严格的监控以确保正确性非常重要。

一些我们可能想要监控的指标：
 - **延迟（Latency）**：可以跟踪不同事件的时间戳，以了解系统的端到端延迟
 - **消息队列大小**：如果队列大小突然增加，我们需要添加更多的聚合节点。由于 Kafka 是通过分布式提交日志实现的，我们需要转而跟踪 records-lag 指标。
 - **聚合节点上的系统资源**：CPU、磁盘、JVM 等。

我们还需要实现一个对账（reconciliation）流程，它是一个批处理作业，在一天结束时运行。
它根据原始数据计算聚合结果，并将它们与聚合数据库中存储的实际数据进行比较：
