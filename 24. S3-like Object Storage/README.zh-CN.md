# 第 24 章：类 S3 对象存储

## 简介

在本章中，我们将设计一个**对象存储**服务，类似于 **Amazon S3**。

存储系统可分为三大类：
- **块存储（Block storage）**
- **文件存储（File storage）**
- **对象存储（Object storage）**

**块存储**是设备，出现于 20 世纪 60 年代。HDD 和 SSD 就是这样的例子。
这些设备通常物理连接到服务器上，不过也可以通过高速网络协议进行网络连接（network-attached）。
服务器可以将原始块格式化并用作文件系统，也可以直接将这些块的控制权交给应用程序使用。

**文件存储**构建在块存储之上。它提供了更高层次的抽象，使文件夹和文件的管理更加容易。

**对象存储**以牺牲性能为代价，换取高持久性、超大容量和低成本。
它面向"冷"数据，主要用于归档和备份。
它没有分层的目录结构，所有数据都以对象的形式存储在扁平结构中。
与其他存储类型相比，它的速度相对较慢。大多数云服务商都提供对象存储产品——Amazon S3、Google GCS 等。

<div style="margin-left:3rem">
    <img src="./images/storage-comparison.png" alt="存储对比" width="500" />
</div>

|                 | 块存储                          | 文件存储                                    | 对象存储                         |
|-----------------|----------------------------------|---------------------------------------------|----------------------------------|
| 可变内容        | 是                              | 是                                         | 否（具备对象版本控制）           |
| 成本            | 高                              | 中到高                                     | 低                              |
| 性能            | 中到高、非常高                  | 中到高                                     | 低到中                          |
| 一致性          | 强一致性                        | 强一致性                                   | 强一致性 [5]                     |
| 数据访问        | SAS/iSCSI/FC                    | 标准文件访问、CIFS/SMB 和 NFS              | RESTful API                      |
| 可扩展性        | 中等可扩展性                    | 高可扩展性                                 | 超大可扩展性                     |
| 适用于          | 虚拟机（VM）、数据库            | 通用文件系统访问                           | 二进制数据、非结构化数据         |

一些与对象存储相关的术语：
- **存储桶（Bucket）**——对象的逻辑容器。名称全局唯一。
- **对象（Object）**——存储在存储桶中的单个数据片段。包含对象数据和元数据。
- **版本控制（Versioning）**——在同一存储桶中保留对象多个版本的功能。
- **统一资源标识符（URI）**——每个资源都由 URI 唯一标识。
- **服务等级协议（SLA）**——服务提供商与客户之间的契约。

Amazon S3 标准-低频访问（Standard-Infrequent Access）存储类的 SLA：
- 跨多个可用区的持久性为 99.999999999%
- 即使在某个可用区被完全摧毁的情况下，数据仍然安全
- 设计可用性为 99.9%

## 步骤 1：理解问题并确定设计范围

- C：应该包含哪些功能？
- I：存储桶创建、对象上传/下载、版本控制、列出存储桶中的对象
- C：典型的数据大小是多少？
- I：我们需要高效地存储超大对象和小对象
- C：我们每年存储多少数据？
- I：100 PB
- C：我们可以假设数据持久性为 6 个 9（99.9999%）、服务可用性为 4 个 9（99.99%）吗？
- I：可以，听起来很合理

### **非功能性需求**

- **100 PB 数据**
- **6 个 9 的数据持久性**
- **4 个 9 的服务可用性**
- 存储效率。在保持高可靠性和高性能的同时降低存储成本

### **粗略估算**

对象存储的瓶颈很可能出现在磁盘容量或每秒 I/O 数（IOPS，input/output operations per second）上。

假设：
- 我们有 20% 的小对象（小于 1mb）、60% 的中等对象（1-64mb）和 20% 的大对象（大于 64mb），
- 一块硬盘（SATA，7200rpm）每秒能够执行 100-150 次随机寻道（100-150 IOPS）

基于这些假设，我们可以估算系统能够持久化的对象总数。
- 为简化计算，我们使用每种对象类型的中位大小——小对象 0.5mb、中等对象 32mb、大对象 200mb。
- 给定 100PB（10^11 MB）的存储空间，且存储使用率为 40%，可得到约 0.68bil（6.8 亿）个对象
- 如果我们假设每条元数据为 1kb，那么我们需要 0.68tb 的空间来存储元数据信息

## 步骤 2：提出高层设计并获得认可

在深入设计之前，让我们先探索对象存储的一些有趣的特性：
- **对象不可变性**——对象存储中的对象是不可变的（其他存储系统则不然）。我们可以删除或替换它们，但不能更新。
- **键值存储**——对象 URI 就是它的键，我们可以通过发起 HTTP 调用来获取其内容。
- **一次写入、多次读取**——数据访问模式是一次写入、多次读取。根据 LinkedIn 的一些研究，95% 的操作是读取。
- 同时支持小对象和大对象

对象存储的设计理念与 UNIX 类似——当我们保存一个文件时，它会在一个名为 inode 的数据结构中记录文件名，而文件数据存储在不同的磁盘位置。
inode 包含一个文件块指针列表，这些指针指向磁盘上不同的位置。

访问文件时，我们首先从 inode 获取其元数据，然后才获取文件内容。

对象存储的工作方式与此类似——元数据存储用于保存文件信息，而内容存储在磁盘上：

</div>

### **高层设计**

<div style="margin-left:3rem">

- **负载均衡器**——将 API 请求分发到服务的多个副本上
- **API 服务**——无状态服务器，协调对元数据存储和对象存储以及 IAM 服务的调用。
- **身份与访问管理（IAM）**——认证、授权、访问控制的中心位置。
- **数据存储**——存储和检索实际数据。操作基于对象 ID（UUID）。
- **元数据存储**——存储对象元数据

### **上传对象**

<div style="margin-left:3rem">
    <img src="./images/uploading-object.png" alt="上传对象" width="500" />
</div>

- 通过 HTTP PUT 请求创建一个名为 "bucket-to-share" 的存储桶
- API 服务调用 IAM 以确保用户已获得授权并拥有写权限
- API 服务调用元数据存储来创建存储桶条目。创建完成后，返回成功响应。
- 存储桶创建后，发送 HTTP PUT 请求以创建名为 "script.txt" 的对象
- API 服务验证用户身份并确保用户拥有写权限
- 验证通过后，对象负载通过 HTTP PUT 发送到数据存储。数据存储将其持久化并返回一个 UUID。
- API 服务调用元数据存储，创建一个包含 object_id、bucket_id 和 bucket_name 以及其他元数据的新条目。

对象上传请求示例：

```
PUT /bucket-to-share/script.txt HTTP/1.1
Host: foo.s3example.org
Date: Sun, 12 Sept 2021 17:51:00 GMT
Authorization: authorization string
Content-Type: text/plain
Content-Length: 4567
x-amz-meta-author: Alex

[4567 bytes of object data]
```

### **下载对象**

存储桶没有目录层级，但我们可以通过拼接存储桶名称和对象名称来创建逻辑层级，以模拟文件夹结构。

用于获取对象的 GET 请求示例：

```
GET /bucket-to-share/script.txt HTTP/1.1
Host: foo.s3example.org
Date: Sun, 12 Sept 2021 18:30:01 GMT
Authorization: authorization string
```

<div style="margin-left:3rem">

</div>

- 客户端向负载均衡器发送 HTTP GET 请求，即 `GET /bucket-to-share/script.txt`
- API 服务查询 IAM，以验证用户是否拥有读取该存储桶的正确权限
- 验证通过后，从元数据存储中检索对象的 UUID
- 根据 UUID 从数据存储中检索对象负载，并返回给客户端

## 步骤 3：深入设计

### **数据存储**

以下是 API 服务与数据存储的交互方式：

<div style="margin-left:3rem">
    <img src="./images/data-store-interactions.png" alt="数据存储交互" width="500" />
</div>

数据存储的主要组件：

<div style="margin-left:3rem">
    <img src="./images/data-store-main-components.png" alt="数据存储主要组件" width="500" />
</div>

数据路由服务提供 RESTful 或 gRPC API 来访问数据节点集群。
它是一个无状态服务，通过添加更多服务器来实现扩展。

它的主要职责是：
- 查询放置服务（placement service），以获取存储数据的最佳数据节点
- 从数据节点读取数据并将其返回给 API 服务
- 将数据写入数据节点

放置服务决定哪些数据节点应该存储某个对象。
它维护一张虚拟集群映射表（virtual cluster map），用于确定集群的物理拓扑。

<div style="margin-left:3rem">
    <img src="./images/virtual-cluster-map.png" alt="虚拟集群映射" width="500" />
</div>

该服务还向所有数据节点发送心跳（heartbeat），以确定是否应将某些节点从虚拟集群中移除。

由于这是一个关键服务，建议维护一个由 5 或 7 个副本组成的集群，通过 Paxos 或 Raft 共识算法进行同步。
例如，一个 7 节点集群可以容忍 3 个节点发生故障。

数据节点存储实际的对象数据。
通过将数据复制到多个数据节点来确保可靠性和持久性。

每个数据节点都运行着一个守护进程，向放置服务发送心跳。

心跳包含以下信息：
- 数据节点管理着多少块磁盘驱动器（HDD 或 SSD）？
- 每块驱动器上存储了多少数据？

#### 数据持久化流程

<div style="margin-left:3rem">
    <img src="./images/data-persistence-flow.png" alt="数据持久化流程" width="500" />
</div>

- API 服务将对象数据转发给数据存储
- 数据路由服务将数据发送到主数据节点
- 主数据节点在本地保存数据，并将其复制到两个次级数据节点。复制成功后返回响应。
- 对象的 UUID 被返回给 API 服务。

注意事项：
- 给定一个对象 UUID，其复制组通过一致性哈希（consistent hashing）确定性地选择
- 在第 4 步中，主数据节点先复制对象数据，再返回响应。这更倾向于强一致性，而非更低的延迟。

<div style="margin-left:3rem">
    <img src="./images/consistency-vs-latency.png" alt="一致性与延迟" width="500" />
</div>

#### 数据如何组织

管理数据的一种简单方法是将每个对象存储在一个单独的文件中。

这虽然可行，但在文件系统中有大量小文件时性能不佳：
- HDD 上的数据块会被浪费，因为每个文件都占用了完整的块大小。典型的块大小为 4kb。
- 文件多意味着 inode 多。操作系统无法很好地处理过多的 inode，而且 inode 也有数量上限。

这些问题可以通过预写日志（WAL，write-ahead log）将许多小文件合并成较大的文件来解决。一旦文件达到其容量上限（通常为几 GB），就会创建新文件：

<div style="margin-left:3rem">
    <img src="./images/wal-optimization.png" alt="WAL优化" width="500" />
</div>

这种方法的缺点是，对文件的写入访问需要串行化。多个核心访问同一文件时必须互相等待。
为了解决这个问题，我们可以将文件限定到特定的核心上，以避免锁竞争（lock contention）。

#### 对象查找

为了支持在同一文件中存储多个对象，我们需要维护一张表，它告诉数据节点：
- `object_id`
- `filename`，对象存储所在的文件名
- `file_offset`，对象开始的文件偏移量
- `object_size`

我们可以将此表部署在基于文件的数据库（如 RocksDB）中，或部署在传统的关系型数据库中。
由于访问模式是低写入、高读取，关系型数据库表现更好。

我们应该如何部署它？
我们可以将数据库单独部署在集群中并独立扩展，供所有数据节点访问。

缺点：
- 我们需要大力扩展集群以服务所有请求
- 数据节点与数据库集群之间存在额外的网络延迟

另一种方案是利用这样一个事实：数据节点只关心与自身相关的数据，
因此我们可以将关系型数据库部署在数据节点内部。

SQLite 是一个不错的选择，因为它是一个轻量级的基于文件的关系型数据库。

#### 更新后的数据持久化流程

<div style="margin-left:3rem">
    <img src="./images/updated-data-persistence-flow.png" alt="更新后的数据持久化流程" width="500" />
</div>

- API 服务发送保存新对象的请求
- 数据节点服务将新对象追加到名为 "/data/c" 的文件末尾
- 在对象映射表中插入该对象的新记录

#### 持久性

数据持久性是设计中的一项重要需求。为了达成 6 个 9 的持久性，我们需要仔细审查每一种故障场景。

首先要解决的是硬件故障问题。我们可以通过复制数据节点来降低故障概率。
但除此之外，我们还应该跨不同的故障域（failure domain）进行复制（跨机架、跨数据中心、分离网络等）。
一次严重事件可能导致同一故障域内的多个硬件同时故障：

<div style="margin-left:3rem">
    <img src="./images/failure-domain-isolation.png" alt="故障域隔离" width="500" />
</div>

假设典型 HDD 的年故障率为 0.81%，那么制作三份副本可使我们获得 6 个 9 的持久性。

像这样复制数据节点可以带给我们想要的持久性，但我们也可以利用纠删码（erasure coding）来降低存储成本。

纠删码使我们能够使用校验位（parity bits），在发生故障时可以重建丢失的比特：

<div style="margin-left:3rem">
    <img src="./images/erasure-coding.png" alt="纠删码" width="500" />
</div>

假设这些比特就是数据节点。如果其中两个宕机，可以用剩余的四个来恢复它们。

纠删码有不同的方案。在我们的场景中，可以使用 8+4 纠删码，并将其分布到不同的故障域中以最大化可靠性：

<div style="margin-left:3rem">
    <img src="./images/erasure-coding-across-failure-domains.png" alt="跨故障域的纠删码" width="500" />
</div>

纠删码使我们能够显著降低存储成本（提升 50%），但代价是访问速度下降，因为数据路由服务需要从多个位置收集数据：

<div style="margin-left:3rem">
    <img src="./images/erasure-coding-vs-replication.png" alt="纠删码与复制对比" width="500" />
</div>

其他注意事项：
- 复制需要 200% 的存储开销（以 3 个副本为例），而纠删码只需 50%
- 纠删码[可以带来 11 个 9 的持久性](https://github.com/Backblaze/erasure-coding-durability)，而复制只有 6 个 9
- 纠删码需要更多的计算来生成和存储校验数据

总而言之，复制对延迟敏感的应用更有用，而纠删码则在存储成本效率和持久性方面更具吸引力。
此外，纠删码的实现难度也高得多。

#### 正确性校验

如果磁盘完全损坏，则故障很容易被发现。但如果磁盘存储的部分区域出现损坏，检测起来就不那么直接了。

为了检测这种情况，我们可以使用校验和（checksum）——即文件内容的哈希值，可用于验证文件的完整性。

在我们的场景中，我们将为每个文件和每个对象存储校验和：

<div style="margin-left:3rem">

</div>

在纠删码（8+4）的情况下，我们需要分别获取 8 份数据中的每一份，并逐一验证它们的校验和。

### **元数据数据模型**

表结构：

<div style="margin-left:3rem">
    <img src="./images/metadata-data-model.png" alt="元数据数据模型" width="500" />
</div>

我们需要支持的查询：
- 通过名称查找对象 ID
- 根据名称插入/删除对象
- 列出存储桶中具有相同前缀的对象

用户可创建的存储桶数量通常有限，因此存储桶表（buckets table）规模很小，可以放入单个数据库服务器中。
但为了读取吞吐量，我们仍然需要对服务器进行扩展。

不过，对象表很可能无法放入单个数据库服务器中。因此，我们可以通过分片（sharding）来扩展该表：
- 按 `bucket_id` 分片会导致热点（hotspot）问题，因为一个存储桶可能有数十亿个对象
- 按 `bucket_id` 分片使负载分布更均匀，但我们的查询会变慢
- 我们选择按 `hash(bucket_name, object_name)` 分片，因为大多数查询都基于对象/存储桶名称

不过，即使采用这种分片方案，列出存储桶中的对象仍然会很慢。

### **列出存储桶中的对象**

在单个数据库中，根据前缀（看起来像一个目录）列出对象的过程如下：

```
SELECT * FROM object WHERE bucket_id = "123" AND object_name LIKE `abc/%`
```

当数据库被分片后，实现这一点就具有挑战性了。要做到这一点，我们可以在每个分片上运行查询，并在内存中聚合结果。
但这给分页带来了挑战，因为不同的分片包含不同大小的结果集，我们需要为每个分片维护独立的 limit/offset。

我们可以利用这样一个事实：对象存储通常不会针对列出对象进行优化，因此我们可以牺牲列表查询的性能。
我们还可以创建一个用于列出对象的反规范化表，按 bucket ID 分片。
这将使我们的列表查询足够快，因为它被隔离在单个数据库实例中。

### **优化大文件上传**

上传大文件可以通过分片上传（multipart upload）来优化——将大文件拆分成多个分块，独立上传：

<div style="margin-left:3rem">
    <img src="./images/multipart-upload.png" alt="分片上传" width="500" />
</div>

- 客户端调用服务以发起分片上传
- 数据存储返回一个唯一标识该上传的上传 ID
- 客户端将大文件拆分成多个分块，使用上传 ID 独立上传
- 当一个分块上传完成时，数据存储返回一个 etag，它是对该分块进行标识的 md5 校验和
- 所有分块上传完成后，客户端发送一个完成分片上传的请求，其中包含 upload_id、分块编号和所有 etag
- 数据存储从各分块重新组装对象。这个过程可能需要几分钟。之后，成功响应被返回给客户端。

此时，不再有用的旧分块可以被移除。我们可以引入一个垃圾回收器（garbage collector）来处理。

### **垃圾回收**

垃圾回收是回收不再使用的存储空间的过程。数据变成垃圾有几种方式：
- **惰性对象删除（lazy object deletion）**——对象被标记为已删除，但实际上并未删除
- **孤儿数据（orphan data）**——例如上传中途失败，需要删除旧的分块
- **损坏的数据（corrupted data）**——未通过校验和验证的数据

垃圾回收器还负责回收副本中的未使用空间。
对于复制，数据会同时从主节点和副本节点中删除。对于纠删码（8+4），数据会从全部 12 个节点中删除。

为便于删除，我们将使用一个名为压缩（compaction）的过程：
- 垃圾回收器将未删除的对象从 "data/b" 复制到 "data/d"
- 复制完成后，使用数据库事务更新 `object_mapping` 表
- 为避免产生过多的小文件，压缩会在文件增长超过一定阈值时进行
