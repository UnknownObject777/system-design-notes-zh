# 第 2 章：估算（Back-of-the-Envelope Estimation）

## 简介
估算是系统设计面试中的一项关键技能。它涉及进行快速、粗略的计算，以评估系统容量或性能。据 Google 资深研究员 Jeff Dean 所说，这些估算有助于通过思维实验和常见的性能基准来评估设计是否满足需求。

本章涵盖关键概念、方法论和示例，帮助你熟练掌握可扩展性与估算。

### 每个程序员都应知晓的延迟数据
延迟数据表示计算系统中各种操作所花费的时间。它们提供了对相对性能的洞察：

| 操作                   | 延迟（2020 年） |
|--------------------------|----------------|
| L1 缓存访问             | 0.5 ns         |
| L2 缓存访问             | 7 ns           |
| 主内存访问              | 100 ns         |
| SSD 随机读取            | 150 µs         |
| HDD 随机寻道            | 10 ms          |
| 数据中心内往返          | 500 µs         |
| 跨区域数据中心往返      | 150 ms         |

**关键洞察：**
- 内存快，磁盘慢。
- 尽可能避免磁盘寻道。
- 在通过互联网传输之前压缩数据，以节省带宽。


---

### 可用性指标
高可用性（High Availability，HA）确保停机时间最小化。可用性通常用**几个 9（nines）** 表示：
- **99%（两个 9）：** 每年约 3.65 天停机
- **99.9%（三个 9）：** 每年约 8.8 小时停机
- **99.99%（四个 9）：** 每年约 52 分钟停机
- **99.999%（五个 9）：** 每年约 5.3 分钟停机
- **99.9999%（六个 9）：** 每年约 31.56 秒停机


Amazon、Google、Microsoft 等云服务提供商的目标是提供**99.9% 或更高**的服务等级协议（SLA，Service Level Agreement）。

## 第 2 节：估算示例 —— Twitter 的 QPS 与存储需求

### 假设条件
- **每月 3 亿活跃用户（MAU，Monthly Active Users）。**
- **50% 的日活跃用户（DAU，Daily Active Users）。**
- **每用户每天平均发布推文数：** 2 条。
- **10% 的推文包含媒体内容。**
- **数据保留期限：** 5 年。

### 估算过程
1. **每秒查询数（QPS，Query Per Second）：**
   - DAU = \( 300M x 50\% = 150M \)
   - 推文 QPS = \( 150M x 2 条推文 / 24 小时 / 3600 秒 = ~3500 \)
   - 峰值 QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小构成：**
     - `tweet_id`：64 字节
     - `text`：140 字节
     - `media`：1 MB
   - **每日媒体存储量：** \( 150M x 2 x 10\% x 1MB = 每天 30TB \)
   - **5 年存储量：** \( 30TB x 365 x 5 = ~55PB \)

## 第 3 节：高效估算的技巧

### 1. 四舍五入与近似计算
精确度并不重要，重要的是估算过程。使用整数简化复杂计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 写下假设条件
清晰地记录假设条件，以便日后参考。

### 3. 标注单位
通过标注单位避免歧义（例如用 `5 MB` 而不是 `5`）。

### 4. 常见估算场景
- **QPS（每秒查询数）：** 衡量流量强度。
- **峰值 QPS：** 考量流量峰值。
- **存储需求：** 估算总数据量需求。
- **缓存需求：** 评估缓存在内存方面的需求。
- **服务器数量：** 根据工作负载计算硬件需求。
