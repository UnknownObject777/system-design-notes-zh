# 第 6 章：设计键值存储

## 引言
**键值存储（key-value store）** 是一种非关系型数据库，数据以键值对（key-value pair）的形式存储。每个键都是唯一的，值通过键来访问。本章详细介绍如何设计一个可扩展、高可用的分布式键值存储系统，支持以下操作：
- `put(key, value)` 用于插入数据。
- `get(key)` 用于检索数据。

### 设计的特性
- 键值对较小（<10 KB）。
- 支持大数据量，具备高可用性和可扩展性。
- 自动扩缩容与可调一致性。
- 低延迟。

---

## 单服务器键值存储
### 实现
- 使用**哈希表（hash table）**在内存中存储键值对。
- 优化手段：
  - 数据压缩。
  - 将不常访问的数据存储在磁盘上。

### 局限性
单台服务器的内存有限，因此需要**分布式方案**来实现可扩展性。

---

## 分布式键值存储
**分布式键值存储**将数据分布到多台服务器上，并且必须应对 **CAP 定理** 所描述的各种权衡取舍。

### CAP 定理
1. **一致性（Consistency）：** 所有客户端同时看到相同的数据。
2. **可用性（Availability）：** 即使部分节点宕机，系统仍能响应用户的每个请求。
3. **分区容错性（Partition Tolerance）：** 即使发生网络分区，系统仍能继续运行。

**权衡取舍：** 根据 CAP 定理，上述三个保证中只能同时实现两个。

<p align="center">
  <img src="./images/cap.png" alt="CAP" width="400">
</p>

#### 系统类型：
- **CP 系统：** 保证一致性和分区容错性，牺牲可用性（例如银行系统）。
- **AP 系统：** 保证可用性和分区容错性，牺牲一致性（例如最终一致性）。
- **CA 系统：** 保证一致性和可用性，牺牲分区容错性。

    **由于网络故障不可避免，分布式系统必须容忍网络分区。因此，CA 系统在现实应用中并不存在。**

    在分布式系统中，网络分区是不可避免的。当发生分区时，我们必须在一一致性与可用性之间做出选择。例如，如果节点 n3 宕机，写入节点 n1 或 n2 的任何数据都无法传播到 n3。反之，如果数据已写入 n3 但尚未传播到 n1 和 n2，则 n1 和 n2 上的数据将是过期的。

    <p align="center">
    <img src="./images/server-down.png"  alt="服务器宕机" width="400">
    </p>
    
- 如果我们选择 CP 系统，就必须阻塞对 n1 和 n2 的所有写操作，以避免数据不一致。
- 如果我们选择 AP 系统，系统会持续接受读取请求，即使返回的可能是过期数据。
对于写操作，n1 和 n2 会持续接受写入，当网络分区恢复后，数据将同步到 n3。

## 系统组件
### 1. 数据分区
- **技术：** 使用一致性哈希（Consistent Hashing）将数据均匀地分布到多台服务器上。
- **优点：**
  - 服务器增减时可自动扩缩容。
  - 通过虚拟节点实现异构性。一台服务器的虚拟节点数量与其容量成正比。

### 2. 数据复制
- 将数据复制到 `N` 台服务器以实现高可用性。
- 这 N 台服务器的选择方式是：从服务器所在位置开始沿环顺时针遍历，选取环上的前 N 台服务器来存储数据副本。将副本放置在不同的数据中心，以提高虚拟节点情况下的可靠性。

    <p align="center">
    <img src="./images/data-replication.png" alt="数据复制" width="300">
    </p>

### 3. 一致性
由于数据被复制到多个节点，因此必须在各个副本之间同步数据。
- **法定人数共识（Quorum Consensus）：**
  - `N`：副本总数。
  - `W`：写法定人数（write quorum）大小。一次写操作必须得到 W 个副本的确认，才被视为成功。
  - `R`：读法定人数（read quorum）大小。一次读操作必须等待至少 R 个副本的响应，才被视为成功。
  - **规则：** `W + R > N` 可保证强一致性。
  - W、R 和 N 的配置是延迟与一致性之间的典型权衡。

    <p align="center">
    <img src="./images/quorum-consensus.png"   alt="法定人数共识" width="400">
    </p>
    
    - 如果 R = 1 且 W = N，系统针对快速读取进行优化。
    - 如果 W = 1 且 R = N，系统针对快速写入进行优化。
    - 如果 W + R > N，则保证强一致性（通常 N = 3，W = R = 2）。
    - 如果 W + R <= N，则无法保证强一致性。

- **模型**：
  - **强一致性（Strong Consistency）：** 读操作返回的值与最新更新的写入数据结果一致。
  - **弱一致性（Weak Consistency）：** 后续的读操作可能看不到最新的值。
  - **最终一致性（Eventual Consistency）：** 只要给予足够的时间，所有更新都会被传播，所有副本最终达成一致。


### 4. 不一致性解决
复制带来了高可用性，但也导致了副本之间的不一致。版本控制（versioning）和向量锁（vector lock）用于解决不一致问题。
- **版本控制：** 
    - 使用**向量时钟（vector clock）**跟踪数据版本并解决冲突。
    - 版本控制是指将每次数据修改视为一个不可变的新数据版本。
        <div>
        <img src="./images/consistent-server.png"   alt="一致性哈希" width="400">
        <img src="./images/inconsistent-server.png"   alt="不一致的服务器" height="230">
        </div>
    
    - 服务器 1 修改了名称，服务器 2 也修改了名称。这两个修改是同时进行的。此时，我们得到了相互冲突的值，称为版本 v1 和 v2。


- **向量时钟**
    1. **设置**：向量时钟是与数据项关联的 [服务器, 版本] 对。它可用于检查一个版本是领先于、落后于还是与其他版本冲突。
        - 假设一个向量时钟表示为 D([S1, v1], [S2, v2], …, [Sn, vn])。如果数据项 D 被写入服务器 Si，系统必须执行以下任务之一。
        - 其中：`D` 是数据项，`Si` 是服务器标识符，`vi` 是数据在服务器 `Si` 上的版本计数器。

    2. **更新向量时钟：** 当数据项在某台服务器上被修改时：
        - 如果该服务器已存在于向量时钟中，则其版本计数器加 1。
        - 否则，在向量时钟中新增一个条目。

    3. **冲突检测：**
        - **无冲突：** 如果版本 X 中的所有计数器都小于或等于版本 Y 中的对应计数器，则版本 X 是版本 Y 的祖先。
        - **存在冲突：** 如果版本 Y 中至少有一个计数器小于版本 X 中对应的计数器，则两个版本互为兄弟版本（sibling）。

    4. **冲突解决：** 当检测到冲突（兄弟版本）时，系统依赖应用程序特定的逻辑或客户端干预来调和数据。

        <p align="center">
        <img src="./images/vector-clock.png"  alt="服务器哈希" width="500">
        </p>

- **挑战：**
  - 增加了客户端的复杂度。
  - 随着大量更新，向量时钟的大小可能不断增长，需要采用裁剪（trimming）策略来限制其大小。


### 5. 故障处理

#### a. 故障检测
仅仅因为另一台服务器声称某台服务器宕机，就认定其宕机是不够的。通常，需要至少两个独立的信息来源才能将一台服务器标记为宕机。
- **Gossip 协议：**
    <div style="margin-left:3rem">
        <img src="./images/gossip-protocol.png"  alt="Gossip 协议" width="600">
    </div>

    - 每个节点维护成员 ID 和心跳计数器（heartbeat counter）。
    - 每个节点定期递增自己的心跳计数器。
    - 每个节点定期向一组随机节点发送心跳。
    - 如果心跳在超过预定义的时间段内没有增加，则该成员被视为离线。



#### b. 临时故障
- **宽松法定人数（Sloppy Quorum）：** 使用健康节点临时维持读写操作。
        <p align="center">
        <img src="./images/sloppy-quorum.png"   alt="宽松法定人数" width="400">
        </p>

    - 检测到故障后，系统需要部署某些机制来确保可用性。
    - 系统不强制执行法定人数要求，而是在哈希环上选择前 W 个健康服务器处理写操作、前 R 个健康服务器处理读操作。
    - 离线服务器被忽略。如果某台服务器不可用，另一台服务器将临时处理请求。


- **带提示的移交（Hinted Handoff）：** 离线服务器恢复后追赶变更。
    - 当宕机服务器恢复上线时，变更会被推送回去，以实现数据一致性。

#### c. 永久故障
- 使用 **Merkle 树（Merkle Tree）** 在副本之间进行高效同步。
    **Merkle 树**（又称哈希树）是一种数据结构，用于在永久故障期间高效地检测并解决副本之间的不一致性。

- 工作原理
    1. **结构：**
        - **叶子节点**存储各数据块的哈希值。
        - **非叶节点**存储其子节点的哈希值。
        - **根哈希（root hash）**表示树中所有数据的组合状态。

    2. **构建 Merkle 树：**
        - **第 1 步：** 将键空间划分为多个桶（bucket）。
            
            <img src="./images/key-bucket.png"   alt="键桶" width="500">

        - **第 2 步：** 使用均匀哈希（uniform hashing）对桶中的每个键进行哈希。

            <img src="./images/hash-key-bucket.png"   alt="哈希键桶" width="500">

        - **第 3 步：** 为每个桶生成一个单一的哈希值。
        
            <img src="./images/hash-bucket.png"   alt="哈希桶" width="500">

        - **第 4 步：** 合并桶的哈希值以计算更上层的哈希值，最终得到根哈希。

            <img src="./images/merkel-tree.png"   alt="Merkle 树" width="500">



    3. **同步：**
        - 要同步两个副本：
            - 比较它们的根哈希。
            - 如果根哈希匹配，则副本是一致的。
            - 如果根哈希不同，则递归比较子哈希，以识别不一致的桶。
        - 只同步不一致的数据。

- 优点
    - **高效：** 只同步不一致的数据，减少数据传输量。
    - **可扩展：** 对大规模数据集有效，同步开销最小。
    - **可靠：** 确保副本之间的数据一致性。


### 6. 处理数据中心故障
- 将数据复制到多个数据中心，以确保在故障期间仍可用。

## 最终架构

<p align="center">
<img src="./images/final-architecture.png"   alt="哈希桶" width="500">
</p>


- 客户端通过简单的 API 与键值存储通信：get(key) 和 put(key, value)。
- 协调器（coordinator）是充当客户端与键值存储之间代理的节点。
- 节点通过一致性哈希分布在环上。
- 系统完全去中心化，因此节点的添加和移动可以自动进行。
- 数据在多个节点上复制。
- 每个节点都承担相同的一组职责，因此不存在单点故障。
