# 第 27 章：数字钱包

## 简介
**支付平台**通常都会有一个**钱包服务**，允许客户端在应用内存放资金，之后可以将其取出。

你还可以用它来支付商品与服务，或向同样使用**数字钱包**服务的其他用户转账。这比通过常规支付通道（payment rails）更快、更便宜。

## 步骤 1：理解问题并确定设计范围
 * C：我们应该只关注数字钱包之间的转账吗？是否还需要支持其他操作？
 * I：目前先聚焦于数字钱包之间的转账。
 * C：系统需要支持每秒多少笔交易（TPS）？
 * I：假设为 100 万 TPS。
 * C：数字钱包有严格的正确性要求。我们可以假设具备事务性保证就足够了吗？
 * I：没问题。
 * C：我们需要证明正确性吗？
 * I：我们可以通过对账（reconciliation）来实现，但这只能发现差异，而无法告诉我们差异的根本原因。相反，我们希望能够从头开始重放数据，以重建历史。
 * C：我们可以假设可用性要求为 99.99% 吗？
 * I：可以。
 * C：需要考虑外汇因素吗？
 * I：不需要，这不在范围内。

总结一下我们需要支持的内容：
 * 支持两个账户之间的余额转账
 * 支持 100 万 TPS
 * 可靠性为 99.99%
 * 支持事务
 * 支持可重现性

### **粗略估算**
传统的云上关系型数据库大约支持 ~1000 TPS。

要达到 100 万 TPS，我们需要 1000 个数据库节点。但如果每笔转账包含两笔分录（leg，即借贷两端的余额变动），那么我们实际上需要支持 200 万 TPS。

我们的设计目标之一是提高单个节点所能处理的 TPS，这样可以减少所需的数据库节点数量。

| 单节点 TPS | 节点数 |
|--------------|-------------|
| 100          | 20,000      |
| 1,000        | 2,000       |
| 10,000       | 200         |

## 步骤 2：提出高层级设计并获得认可

### **API 设计**
本次面试我们只需要支持一个端点：
```
POST /v1/wallet/balance_transfer - 将一个钱包的余额转账到另一个钱包
```

请求参数 - from_account、to_account、amount（使用字符串以避免精度丢失）、currency、transaction_id（幂等键）。

示例响应：
```
{
    "status": "success"
    "transaction_id": "01589980-2664-11ec-9621-0242ac130002"
}
```

### **内存分片方案**
我们的钱包应用为每个用户账户维护账户余额。

表示这一数据的一个好数据结构是 `map<user_id, balance>`，可以使用内存 Redis 存储来实现。

由于单个 Redis 节点无法承受 100 万 TPS，我们需要将 Redis 集群分区为多个节点。

示例分区算法：
```
String accountID = "A";
Int partitionNumber = 7;
Int myPartition = accountID.hashCode() % partitionNumber;
```

可以使用 Zookeeper 来存储分区数量和 Redis 节点的地址，因为它是一个高可用的配置存储。

最后，钱包服务是一个无状态（stateless）服务，负责执行转账操作。它可以轻松地水平扩展：

尽管该方案解决了可扩展性问题，但它不允许我们原子地执行余额转账。

### **分布式事务**
处理事务的一种方法是在标准的分片关系型数据库之上使用两阶段提交（two-phase commit，2PC）协议：

<div style="margin-left:3rem">
    <img src="./images/distributed-transactions-relational-dbs.png" alt="分布式事务-关系型数据库" width="500" />
</div>

两阶段提交（2PC）协议的工作方式如下：

<div style="margin-left:3rem">
    <img src="./images/2pc-protocol.png" alt="2PC 协议" width="500" />
</div>

 * 协调者（钱包服务）像往常一样对多个数据库执行读写操作
 * 当应用准备好提交事务时，协调者要求所有数据库准备（prepare）该事务
 * 如果所有数据库都回复"是"，那么协调者要求数据库提交事务。
 * 否则，要求所有数据库中止事务

2PC 方案的缺点：
 * 由于锁争用（lock contention）导致性能不佳
 * 协调者是单点故障（single point of failure）

### **使用 Try-Confirm/Cancel（TC/C）的分布式事务**
TC/C 是 2PC 协议的一种变体，配合补偿性事务（compensating transactions）工作：
 * 协调者要求所有数据库为事务预留资源
 * 协调者收集数据库的回复 - 如果是"是"，则要求数据库尝试确认（try-confirm）。如果是"否"，则要求数据库尝试取消（try-cancel）。

TC/C 与 2PC 的一个重要区别在于，2PC 执行的是单个事务，而在 TC/C 中，存在两个独立的事务。

以下是 TC/C 分阶段的工作方式：

| 阶段 | 操作 | A                   | C                   |
|-------|-----------|---------------------|---------------------|
| 1     | 尝试（Try）       | 余额变动：-$1 | 不执行任何操作          |
| 2     | 确认（Confirm）   | 不执行任何操作          | 余额变动：+$1 |
|       | 取消（Cancel）    | 余额变动：+$1 | 不执行任何操作          |

阶段 1 - 尝试（try）：

<div style="margin-left:3rem">
    <img src="./images/try-phase.png" alt="尝试阶段" width="500" />
</div>

 * 协调者在 A 的数据库中启动本地事务，将 A 的余额减少 1 美元
 * C 的数据库收到一条 NOP 指令，该指令不执行任何操作

阶段 2a - 确认（confirm）：

<div style="margin-left:3rem">
    <img src="./images/confirm-phase.png" alt="确认阶段" width="500" />
</div>

 * 如果两个数据库都回复"是"，确认阶段开始。
 * A 的数据库收到 NOP，而 C 的数据库被指示将 C 的余额增加 1 美元（本地事务）

阶段 2b - 取消（cancel）：

<div style="margin-left:3rem">
    <img src="./images/cancel-phase.png" alt="取消阶段" width="500" />
</div>

 * 如果阶段 1 中的任何操作失败，取消阶段开始。
 * A 的数据库被指示将 A 的余额增加 1 美元，C 的数据库收到 NOP

以下是 2PC 与 TC/C 的对比：

|      | 第一阶段                                            | 第二阶段：成功              | 第二阶段：失败                        |
|------|--------------------------------------------------------|------------------------------------|-------------------------------------------|
| 2PC  | 事务尚未完成                          | 提交/取消所有事务     | 取消所有事务                   |
| TC/C | 所有事务均已完成 - 已提交或已取消 | 如果需要，执行新事务 | 反转已提交的事务 |

TC/C 也被称为补偿式分布式事务。高层级操作在业务逻辑中处理。

TC/C 的其他特性：
 * 与数据库无关，只要数据库支持事务即可
 * 分布式事务的细节和复杂性需要在业务逻辑中处理

### **TC/C 故障模式**
如果协调者在执行中途崩溃，它需要恢复其中间状态。
这可以通过维护阶段状态表（phase status tables）来实现，这些表在数据库分片内被原子地更新：

<div style="margin-left:3rem">
    <img src="./images/phase-status-tables.png" alt="阶段状态表" width="500" />
</div>

该表包含什么：
 * 分布式事务的 ID 和内容
 * 尝试阶段的状态 - 未发送、已发送、已收到响应
 * 第二阶段名称 - 确认或取消
 * 第二阶段的状态
 * 乱序标志（稍后解释）

使用 TC/C 的一个注意事项是，当分布式事务在途（in-flight）时，会有一个短暂的时刻，账户状态之间彼此不一致：

<div style="margin-left:3rem">
    <img src="./images/unbalanced-state.png" alt="不一致状态" width="500" />
</div>

只要我们总能从这个状态中恢复，并且用户不能利用中间状态（例如用来消费），这就可以接受。
通过始终先执行扣减再执行增加，可以保证这一点。

| 尝试阶段的选择  | 账户 A | 账户 C |
|--------------------|-----------|-----------|
| 选择 1           | -$1       | NOP       |
| 选择 2（无效） | NOP       | +$1       |
| 选择 3（无效） | -$1       | +$1       |

请注意，上表中的选择 3 是无效的，因为如果不在不同数据库之间依赖 2PC，我们就无法保证事务的原子执行。

需要解决的另一个边界情况是乱序执行：

<div style="margin-left:3rem">
    <img src="./images/out-of-order-execution.png" alt="乱序执行" width="500" />
</div>

数据库有可能在收到尝试（try）操作之前先收到取消（cancel）操作。这个边界情况可以通过在阶段状态表中添加乱序标志来处理。
当我们收到尝试操作时，首先检查乱序标志是否被设置，如果是，则返回失败。

### **使用 Saga 的分布式事务**
另一种流行的方法是使用 Saga - 一种在微服务架构中实现分布式事务的标准。

它的工作方式如下：
 * 所有操作按顺序排列成一个序列。所有操作在各自的数据库中独立执行。
 * 操作从头到尾依次执行
 * 当一个操作失败时，整个过程开始回滚，直到回滚到起点，并执行补偿操作

<div style="margin-left:3rem">
    <img src="./images/saga.png" alt="Saga" width="500" />
</div>

我们如何协调工作流？有两种方法可以采用：
 * 编排（Choreography） - saga 中涉及的所有服务订阅相关事件，并完成它们在 saga 中的职责
 * 编配（Orchestration） - 单个协调者指示所有服务按正确顺序完成各自的工作

使用编排的挑战在于，业务逻辑被拆分到多个服务中，并通过异步方式相互通信。
编配方式能很好地处理复杂性，因此通常是数字钱包系统中的首选方法。

以下是 TC/C 与 Saga 的对比：

|                                           | TC/C            | Saga                     |
|-------------------------------------------|-----------------|--------------------------|
| 补偿动作                       | 在取消阶段 | 在回滚阶段        |
| 集中协调                      | 是             | 是（编配模式） |
| 操作执行顺序                 | 任意             | 线性                   |
| 并行执行的可能性            | 是             | 否（线性执行）    |
| 可能看到部分不一致的状态 | 是             | 是                      |
| 应用逻辑还是数据库逻辑             | 应用     | 应用              |

主要区别在于 TC/C 可以并行化，因此我们的决策基于延迟要求 - 如果我们需要实现低延迟，就应该选择 TC/C 方案。

无论我们采用哪种方案，我们仍然需要支持审计和重放历史，以从失败状态中恢复。

### **事件溯源**
在现实中，数字钱包应用可能会被审计，我们必须回答某些问题：
 * 我们能知道任意时刻的账户余额吗？
 * 我们如何知道历史余额和当前余额是正确的？
 * 代码变更后，我们如何证明系统逻辑是正确的？

事件溯源（event sourcing）是一种帮助我们回答这些问题的技术。

它由四个概念组成：
 * 命令（command） - 来自现实世界的预期操作，例如将 1 美元从账户 A 转账到 B。需要有一个全局顺序，因此它们被放入 FIFO 队列中。
   * 与事件不同，命令可能会失败，并且可能因为例如 IO 或无效状态而产生一些随机性。
   * 命令可以产生零个或多个事件
   * 事件生成可能包含随机性，例如外部 IO。这将在后面重新讨论
 * 事件（event） - 系统中发生的事件的史实，例如"已将 1 美元从 A 转账到 B"。
   * 与命令不同，事件是已在我们系统内发生的事实
   * 与命令类似，它们也需要有序，因此被放入 FIFO 队列中
 * 状态（state） - 事件导致的变化结果。例如账户与其余额之间的键值存储。
 * 状态机（state machine） - 驱动事件溯源过程。它主要验证命令并应用事件来更新系统状态。
   * 状态机应该是确定性的，因此它不应读取外部 IO 或依赖随机性。

<div style="margin-left:3rem">
    <img src="./images/event-sourcing.png" alt="事件溯源" width="500" />
</div>

这是事件溯源的动态视图：

<div style="margin-left:3rem">
    <img src="./images/dynamic-event-sourcing.png" alt="动态事件溯源" width="500" />
</div>

对于我们的钱包服务，命令就是余额转账请求。我们可以将它们放入 FIFO 队列中，例如 Kafka：

<div style="margin-left:3rem">
    <img src="./images/command-queue.png" alt="命令队列" width="500" />
</div>

这是完整的架构图：

<div style="margin-left:3rem">
    <img src="./images/wallet-service-state-macghine.png" alt="钱包服务状态机" width="500" />
</div>

 * 状态机从命令队列中读取命令
 * 从数据库读取余额状态
 * 验证命令。如果有效，则为每个账户生成两个事件
 * 读取下一个事件，并通过更新数据库中的余额（状态）来应用它

使用事件溯源的主要优点是它的可重现性。在这种设计中，所有状态更新操作都被保存为所有余额变更的不可变历史。

历史余额总是可以通过从头重放事件来重建。
由于事件列表是不可变的，且状态机是确定性的，我们保证能够成功重放任何中间状态。

<div style="margin-left:3rem">
    <img src="./images/historical-states.png" alt="历史状态" width="500" />
</div>

本节开头提出的所有与审计相关的问题，都可以通过依赖事件溯源来解决：
 * 我们能知道任意时刻的账户余额吗？ - 可以重放从开始到我们感兴趣的时间点的事件
 * 我们如何知道历史余额和当前余额是正确的？ - 可以通过从头开始重新计算所有事件来验证正确性
 * 代码变更后，我们如何证明系统逻辑是正确的？ - 我们可以针对这些事件运行不同版本的代码，并验证它们的结果是否一致

解答客户端对自身余额的查询可以使用 CQRS 架构 - 可以有多个只读状态机，负责基于不可变事件列表查询历史状态：

## 步骤 3：设计深潜
在本节中，我们将探索一些性能优化，因为我们仍然需要扩展到 100 万 TPS。

### **高性能事件溯源**
我们要探索的第一个优化是将命令和事件保存到本地磁盘存储，而不是像 Kafka 这样的外部存储。

这避免了网络延迟，而且由于我们只做追加（append）操作，该操作对 HDD 来说通常很快。

下一个优化是在内存中缓存最近的命令和事件，以节省从磁盘重新加载它们的时间。

在底层，我们可以利用一个名为 mmap 的命令来实现上述优化，它既将数据存储在本地磁盘上，又将其缓存在内存中：

<div style="margin-left:3rem">
    <img src="./images/mmap-optimization.png" alt="mmap 优化" width="500" />
</div>

我们可以做的下一个优化是使用 SQLite（一种基于文件的本地关系型数据库）将状态也存储在本地文件系统中。RocksDB 也是另一个不错的选择。

出于我们的目的，我们会选择 RocksDB，因为它使用日志结构合并树（log-structured merge-tree，LSM），该结构针对写操作进行了优化。
读性能通过缓存进行优化。

<div style="margin-left:3rem">

为了优化可重现性，我们可以定期将快照保存到磁盘，这样我们就不必每次从头重现特定状态。我们可以将快照作为大型二进制文件存储在分布式文件存储中，例如 HDFS：

### **可靠的高性能事件溯源**
到目前为止所做的所有优化都很好，但它们使我们的服务变成了有状态服务。出于可靠性目的，我们需要引入某种形式的复制。

在此之前，我们应该分析在我们的系统中，哪些类型的数据需要高可靠性：
 * 状态和快照总是可以通过从事件列表重现来重新生成。因此，我们只需要保证事件列表的可靠性。
 * 有人可能认为我们总是可以从命令列表重新生成事件列表，但事实并非如此，因为命令是非确定性的。
 * 结论是，我们只需要确保事件列表的高可靠性。

为了实现事件的高可靠性，我们需要将列表复制到多个节点。我们需要保证：
 * 没有数据丢失
 * 日志文件内数据的相对顺序在副本之间保持一致

为了实现这一点，我们可以采用一致性算法，例如 Raft。

使用 Raft 时，有一个活跃的领导者（leader）和若干被动的跟随者（follower）。如果领导者崩溃，某个跟随者会接任。
只要有超过一半的节点在线，系统就会继续运行。

<div style="margin-left:3rem">
    <img src="./images/raft-replication.png" alt="Raft 复制" width="500" />
</div>

使用这种方法，所有节点都基于事件列表更新状态。Raft 确保领导者和跟随者具有相同的事件列表。

### **分布式事件溯源**
到目前为止，我们已经设法设计出一个具有高单节点性能且可靠的系统。

我们必须解决的一些限制：
 * 单个 Raft 组的容量有限。在某个时候，我们需要对数据进行分片并实现分布式事务
 * 在 CQRS 架构中，请求/响应流程很慢。客户端需要定期轮询系统，才能得知他们的钱包何时被更新

轮询不是实时的，因此用户可能需要一段时间才能得知其余额的更新。此外，如果轮询频率过高，可能会使查询服务过载：

<div style="margin-left:3rem">
    <img src="./images/polling-approach.png" alt="轮询方案" width="500" />
</div>

为了减轻系统负载，我们可以引入一个反向代理（reverse proxy），它代表用户发送命令，并代表用户轮询响应：

<div style="margin-left:3rem">
    <img src="./images/reverse-proxy.png" alt="反向代理" width="500" />
</div>

这减轻了系统负载，因为我们可以使用单个请求获取多个用户的数据，但仍然不能满足实时通知的需求。

我们可以做的最后一个改动是，让只读状态机在响应可用时立即将响应推送回反向代理。这可以给用户一种更新是实时的感觉：

最后，为了进一步扩展系统，我们可以将系统分片为多个 Raft 组，并通过编排者（orchestrator）使用 TC/C 或 Saga 在它们之上实现分布式事务：

以下是我们最终系统中一笔余额转账请求的生命周期示例：
 * 用户 A 向 Saga 协调者发送一个包含两个操作的分布式事务 - `A-1`（A 扣减 1）和 `C+1`（C 增加 1）。
 * Saga 协调者在阶段状态表中创建一条记录以跟踪事务的状态
 * 协调者确定需要将命令发送到哪些分区。
 * 分区 1 的 Raft 领导者收到 `A-1` 命令，验证它，将其转换为事件，并在 Raft 组内的其他节点上复制
 * 事件结果被同步到只读状态机，状态机将响应推回给协调者
 * 协调者创建一条记录，表明该操作成功，并继续执行下一个操作 - `C+1`
 * 下一个操作与第一个操作类似地执行 - 确定分区、发送命令、执行、只读状态机推回响应
 * 协调者创建一条记录，表明操作 2 也成功了，最后将结果告知客户端

## 步骤 4：总结
以下是我们设计的演进过程：
 * 我们从使用内存 Redis 的方案开始。这种方法的问题在于它不是持久化存储。
 * 我们转向使用关系型数据库，在其之上使用 2PC、TC/C 或分布式 Saga 执行分布式事务。
 * 接下来，我们引入事件溯源，以使所有操作可审计
 * 我们一开始使用外部数据库和队列将数据存储在外部存储中，但性能不佳
 * 我们转而将数据存储在本地文件存储中，利用追加写入操作的高性能。我们还使用缓存来优化读路径
 * 前一种方法虽然性能好，但不持久。因此，我们引入了带复制的 Raft 共识，以避免单点故障
 * 我们还采用了 CQRS 和反向代理，以便代表我们的用户管理事务的生命周期
 * 最后，我们将数据分布到多个 Raft 组中，这些组使用分布式事务机制（TC/C 或分布式 Saga）进行编排
