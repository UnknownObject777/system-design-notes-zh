# 第 1 章：从零扩展至百万级用户

## 简介
将系统扩展以支撑百万级用户是一项复杂且迭代的过程，需要不断地优化与调整。本章概述了如何从单台服务器的架构起步，逐步扩展以支撑百万级用户。

---

## 第 1 节：单服务器架构
最初，所有组件（Web 应用、数据库、缓存）都运行在同一台服务器上。

<div style="margin-left:3rem">
   <img src="./images/single-server.png" width="400" />
</div>

### 请求流程
1. 用户通过域名（如 `api.mysite.com`）访问应用，域名由 DNS 解析为 IP 地址。
2. Web 服务器的 IP 地址返回给浏览器或移动应用。
3. HTTP 请求被发送到 Web 服务器，服务器返回 HTML 或 JSON 响应。

### 流量来源
1. **Web 应用：** 使用服务器端语言（如 Python、Java）处理业务逻辑，使用客户端语言（如 JavaScript、HTML）负责页面呈现。
2. **移动应用：** 通过 HTTP 和 JSON 与 Web 服务器通信，实现轻量级的数据交换。

---

## 第 2 节：数据库分离
随着用户规模的增长，数据库被迁移到独立的服务器上，以便 Web 层和数据库层能够独立扩展。

<div style="margin-left:3rem">
   <img src="./images/database.png" width="400" />
</div>

### 数据库选型

1. **关系型数据库（SQL）：** 以表结构存储结构化数据。例如：MySQL、PostgreSQL。
2. **非关系型数据库（NoSQL）：** 适用于非结构化数据或低延迟需求的场景。常见类型包括：
   - 键值存储（Key-Value Store）
   - 图数据库（Graph Database）
   - 列式存储（Column Store）
   - 文档存储（Document Store）

- 以下情况可能更适合选择非关系型数据库：
   - 应用需要极低延迟。
   - 数据是非结构化的，或者不存在关联关系。
   - 只需要对数据进行序列化和反序列化（JSON、XML、YAML 等）。
   - 需要存储海量数据。

---

## 第 3 节：垂直扩展与水平扩展
### 垂直扩展（Vertical Scaling）
- 向现有服务器添加更多资源（CPU、内存）。
- 受硬件限制，且缺乏冗余。

### 水平扩展（Horizontal Scaling）
- 向服务器池中增加更多服务器，更适合大规模系统。
- 使用负载均衡器在服务器之间进行请求路由。
---

## 第 4 节：负载均衡器

<div style="margin-left:3rem">
   <img src="./images/load-balancer.png" width="400" />
</div>

**负载均衡器（load balancer）** 将流量分发到多台服务器之间。其优点包括：
1. 冗余：如果某台服务器下线，流量会被重新路由。
   - 如果服务器 1 下线，所有流量都会被路由到服务器 2。
2. 可扩展性：可以方便地添加服务器以应对流量高峰。
   - 如果网站流量快速增长，可以添加更多服务器来处理额外的流量。

## 第 5 节：数据库复制

<div style="margin-left:3rem">
   <img src="./images/database-replication.png" width="400" />
</div>

### 主从模型（Master-Slave Model）
- **主数据库（Master Database）：** 处理写操作。
   - 所有修改数据的命令，如 insert、delete 或 update，都必须发送到主数据库。
- **从数据库（Slave Database）：** 处理读操作，提升性能与可靠性。
   - 由于大多数应用中读操作与写操作的比例更高，因此系统中的从数据库
数量通常多于主数据库。

### 优点
1. 通过并行读操作提升性能。
2. 通过冗余实现高可用性与数据可靠性。


### 故障处理
- 如果系统中只有一个从数据库且它下线了，读操作将暂时
被导向主数据库。
- 如果存在多个从数据库，读操作会被
重定向到其他健康的从数据库，同时新服务器将替换旧服务器。
- 如果主数据库下线，将从数据库中提升一台作为新的
主数据库。
- 在生产系统中，被选中的从数据库的数据可能不是最新的，因此需要通过运行数据
恢复脚本更新数据（多主复制和循环复制等方法可提供帮助）。

## 第 6 节：缓存
**缓存（cache）** 将频繁访问的数据存储在内存中，以减轻数据库负载。缓存层是一个临时数据存储层，比数据库快得多。

<div style="margin-left:3rem">
   <img src="./images/cache.png" width="500" />
</div>

### 缓存的考量因素
1. **适用场景**：当数据读取频繁但修改较少时，应考虑使用缓存。
2. **过期策略**：缓存数据一旦过期，就会被从缓存中移除。如果没有设置过期策略，缓存
数据将永久保存在内存中。
3. **一致性**：这意味着保持数据存储与缓存的同步。由于对数据存储和缓存的修改操作
不在单个事务中，因此可能产生不一致。
4. **故障缓解**：单个缓存服务器可能成为单点故障源，建议在不同
数据中心部署多台缓存服务器以避免 SPOF。
5. **淘汰策略**：一旦缓存已满，就需要淘汰部分条目以释放内存。LRU 是最常用的缓存淘汰策略。

---

## 第 7 节：内容分发网络（CDN）
**CDN** 通过在地理上分布的服务器上缓存静态内容（图片、CSS、JavaScript），来缩短加载时间。

<div style="margin-left:3rem">
   <img src="./images/cdn.png" width="400" />
</div>

### 工作流程
1. 用户向最近的 CDN 服务器请求内容。
2. 如果内容不可用，则从源服务器获取并缓存。


### CDN 的考量因素
1. **成本**：CDN 由第三方提供商运营，对进出 CDN 的数据传输收费。
2. **缓存过期**：缓存过期时间不应太长，也不应太短。
3. **CDN 回源（fallback）**：如果 CDN 暂时故障，客户端应能检测到问题
并从源服务器请求资源。
4. **文件失效**：如果文件被更新，应使缓存失效，使其指向更新后的文件。

## 第 8 节：无状态 Web 层
通过将会话数据迁移到共享的数据存储中，Web 服务器变为无状态。这带来了以下好处：
1. 更容易进行水平扩展。
2. 支持基于流量的自动扩缩容。

</div>

## 第 9 节：多数据中心架构
跨多个数据中心部署可以提高可用性并降低延迟。相关策略包括：

<div style="margin-left:3rem">
   <img src="./images/data-center.png" width="400" />
</div>

1. **GeoDNS 路由：** 将用户引导至最近的数据中心。
2. **数据复制：** 在各数据中心之间同步数据，防止数据不一致。

### 关键考量
- **流量重定向：** 需要使用有效的工具将流量引导到正确的数据中心。
- **数据同步：** 常见的策略是在多个数据中心之间复制数据。
- **测试与部署：** 自动化部署工具对于保证所有数据中心的服务一致性至关重要。

---

## 第 10 节：消息队列
**消息队列（message queue）** 是一个持久化组件，存储于内存中，支持异步
通信。它充当缓冲区并分发异步请求。

<div style="margin-left:3rem">
   <img src="./images//message-queue.png" width="500" />
</div>

- 输入服务称为生产者/发布者（producers/publishers），它们创建消息并发布到消息队列中。
- 其他服务称为消费者/订阅者（consumers/subscribers），它们连接队列并执行消息定义的动作。

## 第 12 节：数据库扩展
### 垂直扩展
- 增加硬件资源，但存在物理和成本上的限制。
- 存在多个缺点：
   - 单点故障的风险更高。
   - 垂直扩展的总体成本较高

### 水平扩展（分片 Sharding）

<div style="margin-left:3rem">
   <img src="./images/horizontal-scaling.png" width="400" />
</div>

- 使用键（如 `user_id`）将数据划分到多个分片上。
   - 分片将大型数据库划分为更小、更易于管理的部分，即分片（shard）。
   - 每个分片共享相同的表结构，但每个分片上的实际数据是各自唯一的。
- 分片键（sharding key）在实施分片策略时至关重要。选择分片键时，重要的是选择一个能够均匀分布数据的键。

#### 挑战
1. **重新分片（Resharding）：** 在以下情况下需要对数据重新分片：
   - 单个分片因数据快速增长而无法容纳更多数据。
   - 由于数据分布不均，某些分片可能比其他分片更快耗尽容量。
   - 一致性哈希（Consistent Hashing）用于解决这些问题。

2. **热点问题（Celebrity problem）：** 对特定分片的过度访问可能导致服务器过载。
   - 为解决该问题，我们可能需要为每个热点用户分配一个分片。

3. **Join 与反规范化（De-normalization）：** 一旦数据库被分片到多台服务器上，跨分片执行 join 操作就会变得困难。
   - 常见的解决方案是对数据库进行反规范化，使查询能够在单张表内完成。

---

## 结语
### 关键要点
1. 保持 Web 层无状态。
2. 在每一层构建冗余。
3. 使用缓存和 CDN 优化性能。
4. 通过分片扩展数据层。
5. 解耦组件以保证灵活性。

本章为构建能够支撑百万级用户的可扩展系统奠定了坚实基础。
