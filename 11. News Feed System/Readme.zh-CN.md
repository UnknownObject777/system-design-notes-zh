# 第 11 章：设计一个信息流系统

## 简介
**信息流系统**（news feed system）会展示一个持续更新的帖子列表（状态更新、照片、视频和链接），这些内容来自用户的社交关系。例如 Facebook 的信息流、Instagram 的信息流以及 Twitter 的时间线。本章探讨如何设计一个可扩展的信息流系统。

---

## 步骤 1：理解问题

### 需求
1. **平台：** 系统需要同时支持 Web 端和移动端应用。
2. **功能：**
   - 用户能够发布帖子。
   - 用户能够在自己的信息流中查看好友发布的帖子。
3. **排序：** 为了简单起见，信息流按照**逆时间顺序**（reverse chronological order）排序。
4. **规模：**
   - 每个用户最多可有 5,000 个好友。
   - 1000 万日活跃用户（DAU）。
   - 信息流中可以包含文本、图片和视频。

---

## 步骤 2：高层设计

### 概览
该设计包含两条主要流程：
1. **信息流发布（Feed Publishing）：** 用户发布一条帖子，写入数据库并推送给好友的信息流。
2. **信息流构建（News Feed Building）：** 用户按逆时间顺序聚合好友的帖子，构建自己的信息流。

---

### 信息流 API
1. **信息流发布 API：**
   - **端点：** `POST /v1/me/feed`
   - **参数：** `content`（帖子文本）和 `auth_token`（身份认证）。

2. **信息流检索 API：**
   - **端点：** `GET /v1/me/feed`
   - **参数：** `auth_token`（身份认证）。

### 信息流发布

1. **用户操作：** 用户通过信息流发布 API 发布帖子。
2. **负载均衡器：** 将流量分发到各 Web 服务器。
3. **Web 服务器：** 对请求进行身份认证，并将其转发到相应服务。
4. **帖子服务（Post Service）：** 将帖子存储到数据库和缓存中。
5. **扇出服务（Fanout Service）：** 将帖子推送到好友的信息流缓存中。
6. **通知服务（Notification Service）：** 向好友发送通知。

### 信息流构建

1. **用户操作：** 用户通过信息流检索 API 请求自己的信息流。
2. **负载均衡器：** 将流量分发到各 Web 服务器。
3. **Web 服务器：** 将请求转发到信息流服务。
4. **信息流服务（News Feed Service）：** 从信息流缓存中获取帖子 ID，并从数据库或缓存中检索完整的帖子详情。

## 步骤 3：深入设计

### 信息流发布的深入设计
1. **Web 服务器：**
   - 使用 `auth_token` 对用户进行身份认证。
   - 实施速率限制（rate limit）以防止垃圾信息。

2. **扇出服务（Fanout Service）：**
   - **写时扇出（Fanout on Write）：** 在写入时把帖子推送到好友的信息流。
     - **优点：** 实时更新，信息流检索速度快。
     - **缺点：** 对拥有大量好友的用户来说资源开销大。
   - **读时扇出（Fanout on Read）：** 在读取时拉取帖子。
     - **优点：** 对不活跃用户更高效。
     - **缺点：** 信息流检索速度较慢。
   - **混合方案（Hybrid Approach）：** 对大多数用户使用推送模型，对拥有大量社交连接的用户（如名人）使用拉取模型。

        <img src="./images/feed-publishing-deep-dive.png" alt="信息流发布深入设计" width="500">

    以下为**扇出服务**的工作流程：

    1. **获取好友 ID：** 从图数据库（graph database）中检索好友列表。
    2. **从缓存中过滤好友：** 访问缓存中的用户设置，排除某些好友（例如已屏蔽的好友或个人分享偏好设置）。
    3. **发送到消息队列：** 将过滤后的好友列表连同新帖子的 ID 一起发送到消息队列（message queue）进行处理。
    4. **扇出工作进程（Fanout Workers）：** 工作进程从消息队列中取出数据并更新信息流缓存。缓存存储 `<post_id, user_id>` 映射，而不是完整的用户和帖子对象，以节省内存。
    5. **存储到信息流缓存：** 将新的帖子 ID 追加到好友的信息流缓存中。由于大多数用户更关注最新内容，可配置的限制确保只保存最近的帖子，从而使缓存的内存消耗保持在可控范围内。

## 信息流检索的深入设计

### 缓存架构
缓存分为五层：
1. **信息流缓存（News Feed Cache）：** 存储帖子 ID，以便快速检索。
2. **内容缓存（Content Cache）：** 存储帖子详情（热门帖子存放在热缓存中）。
3. **社交图谱缓存（Social Graph Cache）：** 存储用户关系数据。
4. **操作缓存（Action Cache）：** 跟踪用户操作（点赞、回复、分享）。
5. **计数缓存（Counter Cache）：** 维护点赞、回复、粉丝等的计数。

## 关键优化

### 扩展性
1. **数据库扩展：**
   - 水平扩展和分片（sharding）。
   - 使用只读副本（read replica）处理高流量查询。
2. **无状态 Web 层：** 保持 Web 服务器无状态，以支持水平扩展。

### 缓存
1. 将频繁访问的数据存储在内存中。
2. 使用多层缓存以降低延迟并减轻数据库负担。

### 可靠性
1. **一致性哈希（Consistent Hashing）：** 将请求均匀地分发到各服务器。
2. **消息队列：** 解耦系统组件并缓冲流量。

### 监控
1. 跟踪关键指标，如 QPS（每秒查询数，queries per second）和延迟。
2. 监控缓存命中率，并据此调整配置。
