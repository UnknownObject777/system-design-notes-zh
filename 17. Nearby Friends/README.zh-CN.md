# 第 17 章：附近好友（Nearby Friends）

## 简介

本章专注于为一个应用设计可扩展的后端，该应用使用户能够分享自己的位置，并发现 **附近** 的好友。

本章与上一章（附近位置）的主要区别在于，在这个问题中，**位置不断变化**，而在上一章中，商家的地址或多或少保持不变。

---

## 步骤 1：理解问题并确定设计范围

一些用于引导面试的问题：
 * C：在地理上多近才算"附近"？
 * I：5 英里，这个数字应该可配置。
 * C：距离是按直线距离计算，还是需要考虑例如好友之间隔着一条河？
 * I：是的，这是一个合理的假设。
 * C：应用有多少用户？
 * I：10 亿用户，其中 10% 使用附近好友功能。
 * C：我们需要存储位置历史吗？
 * I：需要，它对例如机器学习很有价值。
 * C：我们能否假设不活跃的好友会在 10 分钟内从该功能中消失？
 * I：可以。
 * C：我们需要担心 GDPR 等问题吗？
 * I：不需要，为了简单起见。

### **功能需求**

 * 用户应能在移动应用上看到附近的好友。每个好友都有一个距离和时间戳，表明其位置更新的时间。
 * 附近好友列表应每隔几秒更新一次。

### **非功能需求**

- **低延迟**：及时接收位置更新很重要。
- **可靠性**：偶尔丢失个别数据点是可以接受的，但系统总体上应保持可用。
- **最终一致性**：位置数据存储不需要强一致性。不同副本之间位置数据接收延迟几秒是可以接受的。

### **粗略估算（Back-of-the-envelope）**

一些用于确定潜在规模的估算：
 * 附近好友指 5 英里半径内的好友。
 * 位置刷新间隔为 30 秒。人类步行速度较慢，因此无需过于频繁地更新位置。
 * 平均每天有 1 亿用户使用该功能，其中 10% 为并发用户，即 1000 万。
 * 平均而言，一个用户有 400 个好友，他们都使用附近好友功能。
 * 应用每页显示 20 个附近好友。
 * **位置更新 QPS** = 10mil / 30 ≈ 每秒约 33.4 万次更新。

## 步骤 2：提出高层设计并达成共识

在探讨 API 和数据模型设计之前，我们先研究将要使用的通信协议，因为它不像传统的请求-响应通信模型那样普遍。

### **高层设计**

在高层次上，我们希望在对等端（peer）之间建立高效的消息传递。这可以通过点对点（peer-to-peer）协议实现，但这对移动应用来说并不现实，因为移动应用连接不稳定，而且功耗约束严格。

更实际的方法是使用共享后端，作为向你想要触达的好友进行扇出（fan-out）的机制：

<div style="margin-left:3rem">
    <img src="./images/fan-out-backend.png" alt="fan-out-backend" width="500" />
</div>

后端做什么？
 * 接收所有活跃用户的位置更新。
 * 对于每次位置更新，找出所有应该接收该更新的活跃用户，并将其转发给他们。
 * 如果好友之间的距离超过配置的阈值，则不转发位置数据。

这听起来简单，但挑战在于为我们要面对的规模设计系统。

我们先从一个更简单的设计开始，并在深入探讨中讨论更高级的方法：

<div style="margin-left:3rem">
    <img src="./images/simple-high-level-design.png" alt="simple-high-level-design" width="500" />
</div>

- **负载均衡器**：将流量分发到 REST API 服务器以及双向 WebSocket 服务器。
- **REST API 服务器**：处理辅助任务，例如管理好友、更新资料等。
- **WebSocket 服务器**：有状态服务器，负责将位置更新请求转发给相应的客户端。它还负责在初始化时为移动客户端种子化（seed）附近好友的位置（后面会详细讨论）。
- **Redis 位置缓存**：用于存储每个活跃用户的最新位置数据。缓存中的每个条目都设置了 TTL。当 TTL 过期时，用户不再活跃，其数据将从缓存中移除。
- **用户数据库**：存储用户和好友关系数据。可以使用关系型数据库或 NoSQL 数据库。
- **位置历史数据库**：存储用户位置数据的历史记录，不一定直接在附近好友功能中使用，而是用于跟踪历史数据以供分析。
- **Redis pub/sub**：用作轻量级消息总线，为每个用户频道提供不同主题的位置更新。

<div style="margin-left:3rem">
    <img src="./images/redis-pubsub-usage.png" alt="redis-pubsub-usage" width="500" />
</div>

在上面的例子中，WebSocket 服务器订阅与其连接的用户的频道，并在收到位置更新时将其转发给相应的用户。

### **周期性位置更新**

周期性位置更新的流程如下：

<div style="margin-left:3rem">
    <img src="./images/periodic-location-update.png" alt="periodic-location-update" width="500" />
</div>

 * 移动客户端向负载均衡器发送位置更新。
 * 负载均衡器将位置更新转发到该客户端的 WebSocket 服务器持久连接。
 * WebSocket 服务器将位置数据保存到位置历史数据库。
 * 位置数据在位置缓存中更新。WebSocket 服务器还会在内存中保存位置数据，用于后续对该用户的距离计算。
 * WebSocket 服务器通过 redis pub/sub 在用户频道中发布位置数据。
 * Redis pub/sub 将位置更新广播给该用户频道的所有订阅者，即负责该用户好友的服务器。
 * 订阅的 WebSocket 服务器收到位置更新后，计算应将更新发送给哪些用户，然后发送出去。

平均而言，由于一个用户平均有 400 个好友，其中 10% 同时在线，因此需要转发 40 次位置更新。

### **API 设计**

我们需要支持的 WebSocket 例程：
 * 周期性位置更新——用户向 WebSocket 服务器发送位置数据。
 * 客户端接收位置更新——服务器发送好友的位置数据和时间戳。
 * WebSocket 客户端初始化——客户端发送用户位置，服务器返回附近好友的位置数据。
 * 订阅新好友——WebSocket 服务器发送一个好友 ID，移动客户端应跟踪该好友，例如好友首次上线时。
 * 取消订阅好友——WebSocket 服务器发送一个好友 ID，移动客户端应取消订阅该好友，例如好友离线时。

HTTP API——用于辅助职责的传统请求/响应负载。

### **数据模型**

 * 位置缓存将存储 `user_id` 与 `lat,long,timestamp` 之间的映射。Redis 是此缓存的不错选择，因为我们只关心当前位置，而且它支持我们的用例所需的 TTL 淘汰机制。
 * 位置历史表存储相同的数据，但以关系型表的形式存储上述四列。这类数据可以使用 Cassandra，因为它针对写多负载进行了优化。

## 步骤 3：深入设计

让我们讨论如何扩展高层设计，使其能够在我们目标规模下工作。

### **每个组件的扩展性如何？**

- **API 服务器**：可以通过自动扩缩组（autoscaling groups）和复制服务器实例轻松扩展。
- **WebSocket 服务器**：我们可以轻松地对 ws 服务器进行横向扩展，但在拆除服务器时，需要确保优雅地关闭现有连接。例如，我们可以在负载均衡器中将服务器标记为"排空（draining）"，在最终将其从服务器池中移除之前，不再向其发送新连接。
- **客户端初始化**：当客户端首次连接到服务器时，服务器获取用户的好友，在 redis pub/sub 上订阅他们的频道，从缓存中获取他们的位置，最后转发给客户端。
- **用户数据库**：我们可以根据 user_id 对数据库分片。通过专门的服务和 API 暴露用户/好友数据也很有意义，并由专门的团队管理。
- **位置缓存**：通过启动多个 redis 节点，我们可以轻松地对缓存分片。此外，TTL 限制了在任意时刻可能占用的最大内存。但我们仍然需要处理大量的写入负载。
- **Redis pub/sub 服务器**：我们利用这样一个事实：已初始化但未使用的频道不会消耗内存。因此，我们可以为所有使用附近好友功能的用户预分配频道，从而避免例如在用户上线时需要创建新频道并通知活跃的 WebSocket 服务器这类问题。

### **Redis pub/sub 组件的深入扩展**

我们将需要大约 200GB 的内存来维护所有 pub/sub 频道。这可以通过使用 2 台每台 100GB 的 redis 服务器来实现。

考虑到我们需要每秒推送约 1400 万次位置更新，假设单台服务器每秒可以处理约 10 万次推送，那么我们需要至少 140 台 redis 服务器来处理如此大的负载。

因此，我们需要一个分布式的 redis 服务器集群来应对高强度的 CPU 负载。

为了支持分布式 redis 集群，我们需要利用服务发现组件（如 zookeeper 或 etcd）来跟踪哪些服务器处于存活状态。

我们需要编码到服务发现组件中的数据如下：

<div style="margin-left:3rem">

WebSocket 服务器使用从 zookeeper 获取的编码数据来确定特定频道所在的位置。为了提高效率，可以在每个 WebSocket 服务器上将哈希环数据缓存在内存中。

在集群扩容或缩容方面，我们可以设置每日任务，根据历史流量数据按需扩缩集群。我们还可以对集群进行超量配置（overprovision），以应对负载峰值。

redis 集群可被视为有状态存储服务器，因为频道需要维护一些状态，并且需要与订阅者协调，以便它们切换到集群中新增的节点。

在扩缩容操作期间，我们需要注意一些潜在问题：
 * 由于频道被移动，来自 WebSocket 服务器的大量重新订阅请求。
 * 操作期间可能会漏掉客户端的一些位置更新，对于这个问题而言这是可以接受的，但我们仍应尽量减少这种情况。可以考虑在一天中流量最低的点进行操作。
 * 我们可以利用一致性哈希（consistent hashing）来最大程度地减少在添加/移除服务器时移动的频道数量。

### **添加/移除好友**

每当添加/移除好友时，负责受影响用户的 WebSocket 服务器需要订阅/取消订阅该好友的频道。

由于"附近好友"功能是更大应用的一部分，我们可以假设，当任何这些事件发生时，都可以在移动客户端注册一个回调，然后客户端会向 WebSocket 服务器发送消息以执行相应的操作。

### **好友很多的用户**

我们可以对一个人可拥有的好友总数设置上限，例如 facebook 的好友上限为 5000。

处理"鲸鱼（whale）"用户的 WebSocket 服务器可能会承受更高的负载，但只要我们有足够的 WebSocket 服务器，就应该没有问题。

### **Redis pub/sub 的替代方案**

使用 Redis 进行 pub/sub 的一个替代方案是利用 Erlang——一种为分布式计算应用而优化的通用编程语言。

借助它，我们可以创建数百万个相互通信的小型 erlang 进程。我们可以在分布式 erlang 应用中同时处理 WebSocket 连接和 pub/sub 频道。

不过，使用 Erlang 的一个挑战是，它是一种小众编程语言，可能很难找到优秀的 erlang 开发者。

## 步骤 4：总结

我们成功设计了一个支持附近好友功能的系统。

核心组件：
- **WebSocket 服务器**：客户端与服务器之间的实时通信。
- **Redis**：位置数据的快速读写 + pub/sub 频道。

我们还探讨了如何扩展 RESTful API 服务器、WebSocket 服务器、数据层、redis pub/sub 服务器，并探讨了使用 Redis Pub/Sub 的替代方案。我们还探讨了"附近随机陌生人"功能。
