# 第 10 章：设计通知系统

## 引言
**通知系统**是现代应用的重要组成部分，用于提供产品通知、活动、优惠和告警等及时提醒。通知可以通过以下方式发送：
1. **推送通知（Push notification）**（移动端或桌面端）、
2. **短信（SMS）**、以及
3. **电子邮件（Email）**。

本章重点介绍如何设计一个可扩展的系统，使其能够每天发送数百万条通知。

---

## 步骤 1：理解问题
### 需求
- **通知类型：** 推送通知、短信和电子邮件。
- **投递：** 软实时（soft real-time）系统，延迟最小。
- **平台：** iOS、Android 和桌面端。
- **触发方式：** 通知可以由客户端应用程序触发，也可以在服务器上定时触发。
- **规模：**
  - **推送通知：** 1000 万条/天、
  - **短信：** 100 万条/天、
  - **电子邮件：** 500 万条/天。
- **退订支持：** 用户可以禁用特定类型的通知。

---

## 步骤 2：高层设计

### 组件

1. **通知类型：**
   - **iOS 推送通知：** 使用**苹果推送通知服务（APNS）**。
   - **Android 推送通知：** 使用 **Firebase Cloud Messaging（FCM）**。
   - **短信：** Twilio 或 Nexmo 等第三方服务。
   - **电子邮件：** SendGrid 或 Mailchimp 等商业电子邮件服务。

2. **联系信息收集：**
   <div style="margin-left:3rem">
      <img src="./images/contact-info-gathering.png" alt="联系信息收集" width="500">
   </div>

   - 在应用安装或用户注册时收集设备令牌（device token）、电话号码或电子邮件地址。
   - 将联系信息存储在数据库中：
     - **设备令牌表：** 用于推送通知。
     - **用户表：** 用于电子邮件和电话号码。


3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="高层设计" width="500">
   </div>

   - **触发服务：**
      - 生成事件以发起通知（例如账单提醒、物流更新）。
      - 服务可以是微服务、定时任务（cron job），也可以是触发通知发送事件的分布式系统。
   - **通知服务器：**
      - 为服务提供发送通知的 API。
      - 执行基本校验，验证电子邮件、电话号码是否有效。
      - 查询数据库或缓存，获取渲染通知所需的数据。
   - **第三方服务：** 负责将通知投递给用户。

     

### 初始设计中的挑战
- **单点故障（SPOF）：** 一台通知服务器故障就可能导致整个系统崩溃。
- **可扩展性问题：** 数据库、缓存和处理组件难以独立扩展。
- **性能瓶颈：** 发送通知需要大量资源。

### 改进后的设计

   <div style="margin-left:3rem">
      <img src="./images/improved-design.png" alt="改进后的设计" width="500">
   </div>

- 将数据库和缓存从通知服务器中分离出去。
- 引入**水平扩展**，部署多个通知服务器。
- 使用**消息队列（message queue）** 解耦系统组件。
   - 当需要发送大量通知时，消息队列可作为缓冲。
- 增加从消息队列中拉取通知事件并将其发送到相应第三方服务的工作线程（worker）。

   

---

## 步骤 3：深入设计

### 可靠性
1. **防止数据丢失：** 
   <div style="margin-left:3rem">
   <img src="./images/data-loss.png" alt="数据丢失" width="400">
   </div>

   - 将通知数据持久化到数据库中，并实现重试机制。
   - 引入通知日志数据库以实现数据持久化。


2. **去重：** 
   - 检查事件 ID 以避免发送重复的通知。
   - 当通知事件首次到达时，通过检查事件 ID 判断它之前是否已被处理过。
如果之前已处理过，则将其丢弃；否则，发送该通知。


### 其他组件
   <div style="margin-left:3rem">
   <img src="./images/events-tracking.png" alt="事件追踪" width="400">
   </div>

1. **通知模板：** 预格式化模板，用于生成一致且高效的通知。
2. **通知设置：**
   - 用户可以为特定渠道（推送、短信或电子邮件）选择接收或退订。
   - 存储在专门的“通知设置表”中。
3. **限流（Rate Limiting）：** 限制发送给用户的通知频率。
4. **重试机制：** 如果第三方服务失败，则重试发送通知。
5. **监控队列：** 跟踪已排队的通知，以便动态扩展工作线程。
6. **事件追踪：** 收集打开率、点击率和用户参与度等指标。


### 安全性
- 使用 **AppKey** 和 **AppSecret** 为推送通知的 API 进行身份验证和保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="./images/updated-design.png" alt="更新后的设计" width="500">
   </div>

1. 触发服务调用 API 发送通知。
2. 通知服务器校验请求，并从缓存或数据库中获取元数据。
3. 通知事件被发送到消息队列。
4. 工作线程处理事件并与第三方服务交互。
5. 第三方服务将通知投递给用户。


---

## 关键优化
1. **水平扩展：** 增加更多的通知服务器来分担负载。
2. **消息队列：** 解耦处理流程，以应对高并发量。
3. **缓存：** 通过缓存频繁访问的数据来降低延迟。
4. **分布式投递（Distributed Crawling）：** 在地理上优化消息投递，以获得更好的性能。
