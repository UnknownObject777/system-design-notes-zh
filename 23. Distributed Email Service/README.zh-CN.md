# 第 23 章：分布式电子邮件服务

## 简介

在本章中，我们将设计一个**分布式电子邮件服务**，类似于 **Gmail**。

2020 年，**Gmail** 拥有 18 亿活跃用户，而 **Outlook** 在全球有 4 亿用户。

---

## 步骤 1：理解问题并确定设计范围

- C：系统有多少用户？
- I：10 亿用户
- C：我认为以下功能很重要——认证、发送/接收电子邮件、提取电子邮件、过滤电子邮件、搜索电子邮件、反垃圾邮件保护。
- I：列得不错。暂时先不考虑认证。
- C：用户如何连接到电子邮件服务器？
- I：通常，电子邮件客户端通过 SMTP、POP、IMAP 连接，但在本题中我们使用 HTTP。
- C：电子邮件可以有附件吗？
- I：可以

### **非功能性需求**

- **可靠性（Reliability）**——我们不能丢失数据
- **可用性（Availability）**——我们应该使用副本（replication）来防止出现单点故障。我们还应该容忍部分系统故障。
- **可扩展性（Scalability）**——随着用户群的增长，我们的系统应该能够应对。
- **灵活性与可扩展性（Flexibility and extensibility）**——系统应该足够灵活，易于扩展新功能。这也是我们选择 HTTP 而不是 SMTP 或其他邮件协议的原因之一。

### **粗略估算**

- **10 亿用户**
- 假设每人每天发送 10 封电子邮件 -> **每秒 10 万封电子邮件**。
- 假设每人每天接收 40 封电子邮件，每封电子邮件平均有 50kb 元数据 -> **每年存储约 730pb**。
- 假设 20% 的电子邮件带有存储附件，平均大小为 500kb -> **每年约 1,460pb**。

## 步骤 2：提出高层设计并获得认可

### **电子邮件基础知识**

用于发送和接收电子邮件的协议多种多样：
- **SMTP**——在一台服务器向另一台服务器发送电子邮件时使用的标准协议。
- **POP**——用于从远程邮件服务器接收并下载电子邮件到本地客户端的标准协议。一旦取回，电子邮件会从远程服务器上删除。
- **IMAP**——与 POP 类似，用于从远程服务器接收并下载电子邮件，但它会将电子邮件保留在服务器端。
- **HTTPS**——严格来说并不是邮件协议，但可以用于基于 Web 的电子邮件客户端。

除了邮件协议之外，我们还需要为电子邮件服务器配置一些 DNS 记录——MX 记录：

电子邮件附件以 base64 编码发送，大多数邮件服务的附件大小通常限制为 25mb。
该限制是可配置的，个人账户和企业账户有所不同。

### **传统邮件服务器**

当用户数量有限且都连接到一个单独的服务器时，传统邮件服务器运行良好。

<div style="margin-left:3rem">
    <img src="./images/traditional-mail-server.png" alt="传统邮件服务器" width="500" />
</div>

- Alice 登录她的 Outlook 邮箱并点击"发送"。电子邮件被发送到 Outlook 邮件服务器。通信通过 SMTP 进行。
- Outlook 服务器查询 DNS 以找到 gmail.com 的 MX 记录，并将电子邮件传输到他们的服务器。通信通过 SMTP 进行。
- Bob 通过 IMAP/POP 从 gmail 服务器获取电子邮件。

在传统邮件服务器中，电子邮件存储在本地文件系统上。每封电子邮件都是一个单独的文件。

</div>

随着规模的增长，磁盘 I/O 成为瓶颈。此外，它也无法满足我们对高可用性和可靠性的要求。
磁盘可能会损坏，服务器也可能会宕机。

### **分布式邮件服务器**

分布式邮件服务器旨在支持现代用例并解决现代可扩展性问题。

这些服务器仍然可以支持面向原生电子邮件客户端的 IMAP/POP，以及用于服务器之间邮件交换的 SMTP。

但对于功能丰富的基于 Web 的邮件客户端，通常使用基于 HTTP 的 RESTful API。

API 示例：
- `POST /v1/messages`——向 To、Cc、Bcc 头字段中的收件人发送消息。
- `GET /v1/folders`——返回某个电子邮件账户的所有文件夹

响应示例：

```
[{id: string        文件夹的唯一标识符。
  name: string       文件夹的名称。
                     根据 RFC6154 [9]，默认文件夹可以是以下之一：All、Archive、Drafts、
                     Flagged、Junk、Sent 和 Trash。
  user_id: string    账户所有者的引用
}]
```

- `GET /v1/folders/{:folder_id}/messages`——返回某个文件夹下带分页的所有消息
- `GET /v1/messages/{:message_id}`——获取某条特定消息的所有信息

响应示例：

```
{
  user_id: string                      // 账户所有者的引用。
  from: {name: string, email: string}  // 发件人的 <name, email> 组合。
  to: [{name: string, email: string}]  // <name, email> 组合的列表
  subject: string                      // 电子邮件的主题
  body: string                         // 消息正文
  is_read: boolean                     // 指示消息是否已读。
}
```

- **Webmail（网页邮箱）**——用户使用 Web 浏览器发送/接收电子邮件
- **Web 服务器**——面向公众的请求/响应服务，用于管理登录、注册、用户资料等。
- **实时服务器**——用于将新邮件更新实时推送给客户端。我们使用 WebSocket 进行实时通信，但对于不支持 WebSocket 的旧浏览器，则回退到长轮询（long-polling）。
- **元数据库**——存储邮件元数据，如主题、正文、发件人、收件人等。
- **附件存储**——对象存储（例如 Amazon S3），适合存储大文件。
- **分布式缓存**——我们可以在 Redis 中缓存最近的电子邮件，以改善用户体验。
- **搜索存储**——分布式文档存储，用于支持全文搜索。

电子邮件发送流程如下：

<div style="margin-left:3rem">
    <img src="./images/email-sending-flow.png" alt="电子邮件发送流程" width="500" />
</div>

- 用户撰写一封电子邮件并点击"发送"。电子邮件被发送到负载均衡器。
- 负载均衡器对过量的邮件发送进行限流（rate limiting），并将其路由到某个 Web 服务器。
- Web 服务器执行基本的邮件校验（例如邮件大小），如果收件人域名与发件人相同，则直接短路外发流程。但首先会进行垃圾邮件检查。
- 如果基本校验通过，电子邮件将被发送到消息队列（附件从对象存储中引用）
- 如果基本校验失败，电子邮件将被发送到错误队列
- SMTP 外发工作进程从外发队列中拉取消息，进行垃圾邮件/病毒检查，并将其路由到目标邮件服务器。
- 电子邮件存储在"已发送"（Sent Emails）文件夹中

我们还需要监控外发消息队列的大小。队列增长过大可能表明存在以下问题：
- 收件人的邮件服务器不可用。我们可以稍后使用指数退避（exponential backoff）重试发送电子邮件。
- 处理负载的消费者不够，我们可能需要对消费者进行扩容。

电子邮件接收流程如下：

<div style="margin-left:3rem">
    <img src="./images/email-receiving-flkow.png" alt="电子邮件接收流程" width="500" />
</div>

- 传入的电子邮件到达 SMTP 负载均衡器。邮件被分发到 SMTP 服务器，在那里执行邮件接收策略（例如直接丢弃无效的电子邮件）。
- 如果电子邮件的附件过大，我们可以将其放入对象存储（S3）中。
- 邮件处理工作进程进行初步检查，之后邮件被转发到存储、缓存、对象存储和实时服务器。
- 离线用户一旦重新上线，就可以通过 HTTP API 获取他们的新电子邮件。

## 步骤 3：深入设计

现在让我们更深入地探讨一些组件。

### **元数据库**

以下是电子邮件元数据的一些特征：
- 头字段通常很小且被频繁访问
- 正文大小从很小到很大不等，但通常只被读取一次
- 大多数邮件操作都局限于单个用户——例如获取电子邮件、标记为已读、搜索。
- 数据的时效性影响数据的使用。用户通常只阅读最近的电子邮件
- 数据具有高可靠性要求。数据丢失是不可接受的。

在 gmail/outlook 的量级下，数据库通常是定制开发的，以减少每秒输入/输出操作数（IOPS，input/output operations per second）。

让我们考虑一下有哪些数据库可选：
- **关系型数据库**——我们可以为头字段和正文构建索引，但这些数据库通常针对小块数据进行了优化。
- **分布式对象存储**——对于备份存储来说可能是个不错的选择，但无法高效地支持搜索/标记已读等操作。
- **NoSQL**——Gmail 使用了 Google BigTable，但它并未开源。

基于上述分析，很少有现成的解决方案能完美契合我们的需求。
在面试场景下，设计一个全新的分布式数据库方案是不现实的，但重要的是要提到以下特征：
- 单列可以达到个位数 MB
- 强数据一致性
- 设计目标为减少磁盘 I/O
- 高可用且容错
- 应易于创建增量备份

为了对数据进行分区，我们可以使用 `user_id` 作为分区键（partition key），这样单个用户的数据就存储在一个单独的分片上。
这使我们无法与多个用户共享一封电子邮件，但这不是本次面试的要求。

让我们定义数据表：
- 主键由分区键（数据分布）和聚类键（数据排序）组成
- 我们需要支持的查询——获取用户的所有文件夹、显示某个文件夹的所有电子邮件、创建/获取/删除电子邮件、获取已读/未读邮件、获取会话线程（加分项）

### **邮件送达率**

搭建一个用于发送电子邮件的服务器很容易，但由于垃圾邮件防护算法的存在，要让电子邮件进入收件人的收件箱却很难。

如果我们只是搭建一个新的邮件服务器并开始通过它发送邮件，我们的邮件很可能会最终进入垃圾邮件文件夹。

为了防止这种情况，我们可以这样做：
- **专用 IP**——使用专用 IP 发送电子邮件，否则收件人服务器不会信任你。
- **对电子邮件进行分类**——避免从同一台服务器发送营销邮件，以防止更重要的邮件被归类为垃圾邮件。
- 慢慢**预热你的 IP 地址**，以在大型电子邮件提供商那里建立良好的声誉。一个新 IP 需要 2 到 6 周的时间来预热。
- 快速**封禁垃圾邮件发送者**，以免损害你的声誉。
- **反馈处理**——与 ISP 建立反馈回路，以追踪投诉率并快速封禁垃圾邮件账户。
- **电子邮件认证**——使用常见的技术来对抗网络钓鱼，例如 SPF（Sender Policy Framework，发件人策略框架）、DKIM（DomainKeys Identified Mail，域名密钥识别邮件）等。

你不需要记住所有这些。只需要知道构建一个好的邮件服务器需要大量的领域知识。

### **搜索**

搜索包括基于电子邮件内容的全文搜索，或者基于发件人、收件人、主题、未读等过滤条件的更高级查询。

电子邮件搜索的一个特点是它局限于单个用户，并且写操作多于读操作，因为每次操作我们都需要重新建立索引，而用户很少使用搜索选项卡。

让我们比较一下谷歌搜索与电子邮件搜索：

|               | 范围                | 排序                               | 准确性                                          |
|---------------|----------------------|---------------------------------------|---------------------------------------------------|
| 谷歌搜索      | 整个互联网           | 按相关性排序                         | 索引需要一些时间，因此结果并非即时返回。         |
| 电子邮件搜索  | 用户自己的邮箱       | 按时间、日期等属性排序               | 索引应该快速，且结果准确。                       |

Elasticsearch 是最流行的搜索引擎数据库之一，并且非常擅长支持电子邮件的全文搜索。

另外，我们也可以尝试开发自己的定制搜索方案，以满足我们的特定需求。

设计这样的系统超出了本次讨论的范围。构建它时面临的核心挑战之一是如何针对写密集（write-heavy）的工作负载进行优化。

为了实现这一点，我们可以使用日志结构合并树（LSM，Log-Structured Merge-Trees）来组织磁盘上的索引数据。写入路径仅针对顺序写入进行了优化。
这种技术被用于 Cassandra、BigTable 和 RocksDB。

其核心思想是先在内存中存储数据，直到达到预定义的阈值，之后将其合并到下一层（磁盘）：

<div style="margin-left:3rem">
    <img src="./images/lsm-tree.png" alt="lsm-tree" width="500" />
</div>

两种方法之间的主要权衡：
- Elasticsearch 在某种程度上可以扩展，而定制搜索引擎可以为电子邮件用例进行微调，从而可以进一步扩展。
- Elasticsearch 是我们需要与元数据存储一同维护的独立服务。而定制方案本身就可以作为数据存储。
- Elasticsearch 是现成的解决方案，而定制搜索引擎则需要投入大量的工程精力来构建。

## 步骤 4：总结

其他可讨论的要点：
- **容错（Fault tolerance）**——系统的许多部分都可能发生故障。值得我们考虑如何处理节点故障。
- **合规性（Compliance）**——鉴于欧洲的 GDPR 法规，个人身份信息（PII）需要以合理的方式存储。
- **安全性（Security）**——电子邮件加密、网络钓鱼防护、安全浏览等。
- **优化（Optimizations）**——例如防止同一附件被不同用户多次发送时产生的重复存储。
